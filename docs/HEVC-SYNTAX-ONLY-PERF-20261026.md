# Scheme C 性能实测：`syntax_only` 跳过像素重构 + 按切片并行的真实收益

| 项 | 内容 |
| :--- | :--- |
| **文档编号** | `HEVC-SYNTAX-ONLY-PERF-20261026` |
| **编制日期** | 2026-10-26 |
| **性质** | 语料级实测（release，16 线程主机，2 KiB 载荷）。主仓与 vendor fork **零净改动**（fork 为测量临时加的滤波跳过已回滚，主仓临时计时已移除）。 |
| **测量方式** | ① 解码器自带 `Ablate`（`RH265_ABLATE_MC/INTRA/RESIDUAL` 环境变量）+"跳过环路滤波"临时补丁；② 主仓 embed 内部阶段计时（record / STC / replay）；③ 墙钟对比（CLI） |

---

## 0. 结论摘要

1. **`syntax_only` 值：embed 墙钟 1.8~3.8 倍，槽池逐项相同**（证明解析不依赖重构样本）。但完整收益需要**同时跳过环路滤波**（去块 + SAO），否则只有一半：
   | 载体 | 仅 Ablate（内置） | Ablate + 跳过滤波 |
   | :--- | :---: | :---: |
   | iPhone 4K / iPhone MOV / 小米 1080p60 / 40 MB 大文件 | 2.05x / 1.87x / 1.45x / 1.55x | **4.23x / 3.30x / 1.81x / 2.01x**（capacity 记录通道） |
2. **rayon 按切片并行的空间很小**：真正独立可并行的只有 replay（回放重编码）阶段，实测只占 embed 的 **3%（小文件）~20%（40 MB 大文件）**；STC 求解只有 **2.5~3 ms**（代价只随载荷长度，不随槽池大小）。8 线程打满也只能再快 3%~15%。
3. **更大的一块在别处**：CLI 在非 `--quiet` 嵌入前会先跑一次**完整容量探测**（只为打印 advisory 警告），等于整条流水线扫两遍。iPhone 4K：引擎内 10.47 s，墙钟 20.36 s ≈ 2 × 10 s。**取消/复用这次预检即 ~2x 墙钟，零风险**。
4. 优先级：**P0 CLI 单次扫描 → P1 syntax_only → P2 日志/槽内存 → P3 帧级并行解码**。

## 1. 阶段拆分（主仓 embed 内部计时，2 KiB 载荷）

| 载体 | 模式 | record（解码+录日志+建槽） | STC 求解 | replay（回放重编码+回写） | 引擎内合计 | 墙钟 |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: |
| VID_20250228（iPhone 4K，228 帧） | 现状 | 9.82 s | 2.6 ms | 0.32 s | 10.47 s | **20.36 s** |
| 同上 | syntax_only | **2.26 s** | 2.7 ms | 0.32 s | 2.90 s | **5.30 s** |
| IMG_0033.MOV（385 帧） | 现状 | 6.62 s | 2.5 ms | 0.19 s | 7.01 s | **13.79 s** |
| 同上 | syntax_only | **1.91 s** | 2.6 ms | 0.19 s | 2.30 s | **4.33 s** |
| VID_20261007（816 帧，40 MB） | 现状 | 29.01 s | 2.5 ms | 4.69 s | 38.35 s | **68.55 s** |
| 同上 | syntax_only | **13.65 s** | 2.6 ms | 4.75 s | 23.07 s | **38.67 s** |

- **record 是绝对大头**（现状下 50%~80%），且正是 ablation 唯一能加速的阶段 → embed 整体 1.77x~3.84x（墙钟）。
- **replay 不受 ablation 影响**（它不解码），只在被翻转的子流上工作；它随载荷增大而增大（载荷越大翻转越多）。
- **STC 可忽略**：`StcTrellis::embed_with_deltas` 的成本随**消息长度**（needed_slots）走，不随 3800 万槽的池子走。
- **墙钟 ≫ 引擎内**：差值就是 CLI 那次额外的容量探测（见 §2）。

## 2. CLI 的双次扫描（最大的单项浪费）

`cli.rs` 在 `handle_embed` 里（非 `--quiet` 且 enforcement = Advisory 时）先调用 `probe_carrier_capacity_with_profile` 只为判断是否打印 `[WARN] Payload ... exceeds recommended safety threshold`，随后才 `embed_carrier_with_profile` —— 两次都完整走一遍"解析容器 + 全片解码 + 录日志 + 建槽池"。

| 载体 | 引擎内 embed | 墙钟 embed | 差（≈ 第二次扫描） |
| :--- | ---: | ---: | ---: |
| iPhone 4K | 10.47 s | 20.36 s | ~9.9 s |
| IMG_0033.MOV | 7.01 s | 13.79 s | ~6.8 s |
| VID_20261007 | 38.35 s | 68.55 s | ~30.2 s |

**修法（零风险）**：把 advisory 警告改成嵌入**之后**输出——`embed_hevc` 内部本来就要算 `needed_slots` 与 `total_slots`，把槽池规模一并返回（或提供 `embed_carrier_with_info`），CLI 用它算 bpp 并警告。`--dry-run` 同样适用；`--quiet` 不变。预期 **墙钟 ~2x**。

## 3. 并行（rayon）到底能拿多少

| 阶段 | 是否可并行 | 占比（典型 / 40 MB） | 8 线程收益 |
| :--- | :--- | :--- | :--- |
| 容器解析 | 是（但只几毫秒） | ~0% | 无意义 |
| **record（解码 + 录日志）** | ❌ 单一解码器状态机（RPS/POC/DPB 顺序推进） | **50%~80%** | 0（除非 fork 支持帧级并行） |
| STC 求解 | 部分（Viterbi 顺序） | ~0% | 无意义 |
| replay（重编码被翻转的子流） | ✅ 每切片独立、写互不重叠的字节区 | 3% / 20% | 整体再快 **3% ~ 15%** |
| 槽池/代价构建 | ✅ 随录制并行（需要录制也并行） | 含在 record | 同上 |

**结论**：仅在 replay 上用 rayon 是"工程上容易、收益很小"。真正的杠杆在 record，而 record 并行的前提是**帧级并行解码**：ablation 之后解析不再需要参考像素，理论上每帧可独立（DPB/RPS 记账只依赖头部），需要 fork 暴露"按帧复制解码状态"的能力 + 主仓按帧分批喂切片。这是解码器级改造（估 3~5 天），应单独立项，不与 MP4 容器层混在一起。

## 4. `syntax_only` 的正确落地方式（含风险核对）

- 解码器已内置 `pub ablate: Ablate { mc, intra, residual }` 且注释明确"Parsing is never ablated — HEVC 熵解码不依赖重构样本"；主仓只需在 `record_carrier_state` 里 `decoder.ablate = Ablate { mc: true, intra: true, residual: true }`。
- **环路滤波（去块 + SAO）目前无条件执行**，需 fork 在 `finish_picture` 里加 `if !self.ablate.any()` 守卫（1 行）→ 这才是完整收益（实测 1.45x → 2.01x）。
- 安全核对（已做）：三个语料在 ablation 开/关下**槽位数完全相同**（1,084,896 / 837,410 / 16,671,341 / 38,086,619），证明熵解析不受影响；槽池不变 ⇒ 线格式与既有载体兼容，无需 bump 方言。
- 注意：`verify_sei`（解码哈希 SEI 校验）在 ablation 下必然失败，主仓未启用，需在 fork 侧显式互斥或文档标注。

## 5. 建议排期

| 优先级 | 事项 | 预期 | 风险 |
| :--- | :--- | :--- | :--- |
| **P0** | CLI 取消嵌入前的重复容量探测（改为嵌入后按返回的槽池规模告警） | 墙钟 **~2x** | 极低 |
| **P1** | 主仓设 `ablate` + fork 跳过环路滤波 | 引擎内 **1.7~4.2x** | 低（槽池已验证一致） |
| **P2** | 日志内存瘦身（`BinOp` 24 B / 38 M 槽池的分配与释放可见于墙钟尾部） | 10~30% | 中（改动面大） |
| **P3** | 帧级并行解码（fork + 主仓分批） | 理论 4~8x 于 record | 高（解码器改造） |
| — | 仅 replay 并行 | +3%~15% | 低，但收益不值得单独立项 |
