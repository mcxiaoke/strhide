## 1. 现状问题与破绽实证分析

在目前的 Universal Binary Envelope (UBE v2.2) 规范中，信封在十六进制视图（WinHex/010 Editor）和取证扫描器（YARA、Suricata、strings、PE-bear 等）面前存在多处明显的特征指纹：

### 1.1 静态魔数暴露（ASCII 签名）
1. **标准头魔数**：`STANDARD_HEADER_MAGIC = b"\x89STRHIDE"`（8 字节：`89 53 54 52 48 49 44 45`），ASCII 明确显示 `‰STRHIDE`。
2. **标准尾标魔数**：`STANDARD_TRAILER_MAGIC = b"STH!"`（4 字节：`53 54 48 21`）。
3. **PE 代码信道魔数**：`CHANNEL_MAGIC = b"STHC"`（4 字节：`53 54 48 43`）。
* **破绽影响**：任何静态规则或字符串搜索，耗时 < 1 秒即可全量检出。

### 1.2 头部（112 字节）明文裸露与结构性指纹
虽然载荷与元数据支持 AES-256-GCM 加密，但目前的 **112 字节固定头部 (`EnvelopeHeader`) 全程裸露存储为明文**：
```
[0x00..0x08]  magic_header (8B)        -> 静态魔数或派生魔数
[0x08..0x0B]  version, flags, strat_id  -> 低熵小整数（如 02 09 01 00）
[0x0C..0x27]  salt, base_nonce (28B)    -> CSPRNG 高熵随机值
[0x28..0x2F]  orig_host_size (8B)       -> 宿主真实体积（LE 整数，高位充斥 00）
[0x30..0x4F]  orig_host_sha256 (32B)    -> 原始宿主全量 SHA-256 哈希！
[0x50..0x6F]  inject_offset, inject_sz  -> LE 64/32 位整数（大部分字节为 00）
```
* **破绽 1（原宿主 SHA-256 暴露）**：分析人员只需对载体主体（或切除可疑区域后）计算一次 SHA-256，与偏移 `0x30` 处的 32 字节哈希对比一致，**无需破解密码即可 100% 确证隐藏信封的存在及其绑定的原始载体**。
* **破绽 2（高低熵断层指纹）**：
  结构呈现出固定的 `4B低熵 | 28B高熵 | 8B小整数 | 32B高熵 | 40B全零填充`。无论是否使用随机魔数，这一结构在二进制特征检测（如基于机器学习或滑动熵的检测器）面前形同明文指纹。

### 1.3 尾标（24 字节）公开 CRC32 窗口指纹
* `EnvelopeTrailer` 包含 `ube_offset (8B) || ube_total_size (8B) || trailer_crc32 (4B) || trailer_magic (4B)`。
* 其中 `trailer_crc32` 使用标准 IEEE 802.3 CRC32 算法计算前 16 字节。
* 取证工具只需扫描任意 24 字节窗口，验证 `CRC32(window[0..16]) == window[16..20]`，即可无视魔数定位信封尾标。

## 2. 核心设计原则：100% 定性与可靠性红线

> **不可逾越的红线**：  
> 任何隐蔽性增强改动，绝不能以牺牲定性与可靠性为代价。在未经篡改的前提下，识别、提取与还原必须保持 **100% 成功率**，禁止使用任何概率性或启发式猜测。

1. **确定性边界（Deterministic Boundary）**：
   * 所有宿主格式（PNG、JPEG、PDF、MP4、ZIP、PE）均具有严格的格式规范。数据注入点必须依托宿主合规容器（Chunk Length、Marker Segment Length、Object Stream Length、PE Slack），保证载荷物理边界由宿主格式内生参数精准界定。
2. **密码学确证（Cryptographic Determinism）替代魔数**：
   * 废除字符串魔数后，信封的存在性与完整性由 **AEAD Tag 验证** 提供数学上的确定性证明（碰撞概率 $< 2^{-128}$，可靠性等同于 100%）。
3. **逐比特还原承诺（Bit-for-Bit Lossless Reversibility）**：
   * 宿主原始体积、哈希、时间戳、补丁偏移的还原必须严格保持完全一致，并通过全量回归测试套件验证。
4. **向后兼容（Backward Compatibility）**：
   * 新版读取引擎必须完整兼容并可识别历史 v2 版本的信封格式（包含旧魔数与明文头的载体），确保旧载体可无损提取与剥离。

## 3. 技术改造分步实施方案

```
+-----------------------------------------------------------------------------------+
| 阶段 1: 双层信封与头部敏感信息加密（消除 SHA-256 与结构指纹）                     |
|         - 外层公共头（Public Header）：仅暴露 Salt 与 Nonce (28B)                 |
|         - 内层核心头（Encrypted Header）：全量加密 SHA-256、尺寸、偏移量          |
+-----------------------------------------------------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 阶段 2: 密码学认证尾标与去明文 CRC32                                               |
|         - 尾标 CRC 改用密钥派生的 Auth Code 或截断 Tag                            |
|         - 消除公开 IEEE 802.3 CRC32 扫描窗口                                      |
+-----------------------------------------------------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 阶段 3: 试解密（Trial Decryption）与彻底的无魔数化（Zero-Magic）                   |
|         - 适配器依据合规切片边界提取密文                                          |
|         - 试解密内层头验证 Tag 判定信封存在，彻底消除静态与动态 Magic 字段         |
+-----------------------------------------------------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
| 阶段 4: 载体元数据语法伪装与熵平滑                                                |
|         - PNG 改用合规 zTXt / iTXt                                                |
|         - JPEG 改用 APP13 8BIM 标准段                                             |
|         - PDF 改用合规增量 Object Stream                                          |
+-----------------------------------------------------------------------------------+
```

### 3.1 阶段 1 实施细则：双层信封结构（Two-tier Envelope）

#### A. 外层公共头（Public Minimal Header，28 字节）
仅承载密钥派生必需参数，彻底剔除魔数、版本和明文尺寸：
```rust
#[repr(C)]
pub struct PublicHeader {
    pub salt: [u8; 16],        // CSPRNG 生成的随机盐
    pub base_nonce: [u8; 12],  // CSPRNG 生成的基础 Nonce
}
```
* **特征消除**：28 字节纯随机均匀高熵数据，没有任何小整数、版本号、魔数字符串或全零对齐区。

#### B. 内层核心加密头（Encrypted Internal Header，64 字节）
使用从口令与 Salt 派生的 `header_key`，经 AES-256-GCM 加密，并附加 16 字节 GCM Tag：
```rust
#[repr(C)]
pub struct EncryptedHeader {
    pub version: u8,               // 协议版本
    pub flags: u8,                 // 标志位
    pub strategy_id: u8,           // 策略 ID
    pub reserved: u8,              // 保留位
    pub orig_host_size: u64,       // 原始宿主大小（受密文保护）
    pub orig_host_sha256: [u8; 32],// 原始宿主 SHA-256（受密文保护）
    pub inject_offset: u64,        // 注入偏移（受密文保护）
    pub inject_size: u64,          // 注入大小（受密文保护）
    pub patch_offset: u32,         // 补丁偏移（受密文保护）
    pub orig_patch_val: u32,       // 补丁原值（受密文保护）
    pub meta_len: u32,             // 元数据长度（受密文保护）
    pub payload_len: u64,          // 载荷长度（受密文保护）
}
```
* **效果**：原宿主 SHA-256 和所有内部偏移量全盘加密，在载体内部呈现为完美的随机高熵分布。

---

### 3.2 阶段 2 实施细则：去明文 CRC32 与密码学尾标

#### A. 现有尾标改造
在加密模式下：
* 废除公开的 `IEEE 802.3 CRC32`。
* 尾标校验码改由 `HKDF-Expand(ikm, "strhide-trailer-auth")` 派生，或者直接将尾标纳入整体 AEAD 密文范围。
* 攻击者在没有密码的情况下，无法通过滑动窗口计算 CRC32 来定位 Trailer。

---

### 3.3 阶段 3 实施细则：基于 AEAD Tag 的试解密（Zero-Magic）

1. **定位流程**：
   * 适配器定位宿主内生切片（例如 PNG 的注入 Chunk、JPEG 的 APP 段、PDF 的增量 Object）。
   * 读取切片的前 28 字节获取 `salt` 与 `base_nonce`。
   * 派生 `header_key`，尝试解密接下来的密文核心头及 16 字节 Tag。
2. **定性判定准则**：
   * 若 Tag 校验成功：数学上以 $1 - 2^{-128}$ 的确定性判定找到有效信封，直接读取内部参数并解密元数据与载荷。
   * 若 Tag 校验失败：数学上判定此处非当前密码对应的隐藏数据。
   * **可靠性**：完全不依赖魔数字符串比对，可靠性达 100%。
