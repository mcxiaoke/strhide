## 1. 背景与问题定义

### 1.1 现状与瓶颈分类

在完成信封元数据二进制紧凑化（方案 A，最小信封降至明文 183 B / 加密 219 B）以及分块 diff 设计（方案 B，解决 slack-bound）后，在 `temp/testapps` 实测的 19 个未签名 exe 中，仍有 8 个 exe 无法容纳加密信封：
* **4 个属于存根类或微型工具**：`.text` 本身极小（如 `clink_x64.exe` 4.6 KB、`sysmon` 15 KB、`perl.exe` 39 KB、`exiftool.exe` 58 KB），物理可改造位在数十到百位以内，受限于基础物理尺寸。
* **4 个属于紧边界 text-bound 工具**：仅差数十字节即可装下最小加密信封（219 B）：
  * `CarroNote.exe`：现有可改造位对应容量 269 B，但若用户载荷稍大即超限；
  * `WindTerm/vendors/lrzsz/sz.exe`：容量 232 B（仅余 13 B 裕量）；
  * `WindTerm/vendors/lrzsz/rz.exe`：容量 229 B（仅余 10 B 裕量）；
  * `WindTerm/vendors/vcxsrv/xrdb.exe`：容量 71 B。

### 1.2 方案 C 的提出与诉求

用户提出改进方案 C：**扩展指令等价编码集合**（如 `mov r,r ↔ lea r,[r]`，48 89 D8 与 48 8D 03 均 3 字节且语义、标志位完全等价）。
实测该模式在 `CarroNote`、`sz`、`rz` 上能带来 +38% ~ +57% 的位置数增益。

本文系统性论证：**在保证 100% 逐比特无损还原、零标志位副作用的前提下，有哪些可靠可行的指令集扩充选项，并对方案 C 的 3 态编码工程代价进行解构。**

## 2. 扩充准入原则（四大绝对红线）

指令级隐写区别于编译器优化，必须在线性扫描（无全程序控制流图 CFG 与活度分析）下保证绝对安全性：

1. **严格等长替换（$L_{new} == L_{old}$）**：
   * 任何长度变化都会破坏后续所有相对寻址（`jmp/call rel8/rel32`）、RIP 相对寻址（`[rip+disp32]`）、跳转表偏移与异常解卷表（`.pdata` / `RUNTIME_FUNCTION`）。必须保证原位等长。
2. **严格语义与标志位等价（Zero Flag / Memory Side-Effect）**：
   * 不允许引起内存访问（不能触发 #GP(0) 保护异常或 #PF 缺页异常）；
   * 不能改变任何 CPU 状态标志位（CF, ZF, SF, OF, AF, PF）。不能假设后续代码不读取某标志位（无 Dead-Flag 分析）。
3. **确定性重编码与最小规范编码（Filter F4/F5）**：
   * `iced-x86` 解码后重新规范编码必须逐字节等于原指令，禁止利用非最小冗余前缀（如非法 REX 位、冗余 0x66 等），防止被杀软与静态检测直接捕获。
   * 翻转后的指令再次解码必须严格落在同一等价类别内，保证逆向 strip 时 profile 序列不发生漂移。
4. **真实编译器生成密度（High Prevalence）**：
   * 指令模式必须在 MSVC、GCC、Clang 等主流编译器生成的实际代码中大量出现，生僻指令不具备工程价值。

## 3. 可靠候选方案深度评估

### 3.1 候选一：SIB Scale=1 变址加法交换律（★★★★★ 最优先推荐）

这是除 ALU 寄存器对之外，收益最高、实现最干净的 **纯 2 态（1 bit/位置）** 扩充。

#### (1) 原理与操作码
在 x86/x64 SIB 寻址字节中，当 `scale == 00b`（即 scale = 1）时，计算地址为：
$$\text{Address} = \text{base} + \text{index} + \text{disp}$$
根据实数域加法交换律：
$$\text{base} + \text{index} == \text{index} + \text{base}$$
交换 SIB 字节内的 `base` 与 `index` 字段（并在 x64 下同步交换 REX.B 与 REX.X 位），计算得到的内存绝对地址完全一致。

#### (2) 适用范围
覆盖绝大多数带变址寻址的指令（不限于 MOV）：
* `MOV reg, [base + index]` 与 `MOV [base + index], reg`
* `LEA reg, [base + index]`
* `CMP / ADD / SUB / AND / OR / XOR reg, [base + index]`
* `MOVZX / MOVSX reg, [base + index]`
* `MOVSS / MOVSD xmm, [base + index]`

#### (3) 约束与安全过滤规则
* **F_SIB1**：`scale == 1`（排除 scale 为 2/4/8 的非对称运算）；
* **F_SIB2**：`base != index`（如 `[rax + rax]` 交换后无编码变化，淘汰）；
* **F_SIB3**：`base != ESP/RSP/R12`（在 x86 SIB 体系中，`index = 100b` 固定表示“无 index”，因此 ESP/RSP/R12 绝不能置入 index 字段）；
* **F_SIB4**：当 `mod == 00`（disp=0 且无显式 disp8）时，`base != EBP/RBP/R13`（因为 `mod=00, base=101b` 被硬件解释为 `disp32` 且无 base）。

#### (4) 编码与位定义
* 纯 2 态（1 比特）：`bit = (base as usize) < (index as usize)`（按 iced-x86 `Register` 枚举序号判定，与现行 `TEST` 交换律完全同构）。

#### (5) 实测数据（真实 PE 扫描）

| 样本文件 | 架构 | .text 大小 | 现有可改造位 | 有效 SIB 交换位 | 净增可用容量 |
|---|---|---|---|---|---|
| `WindTerm/sz.exe` | PE32 | 65,195 B | 1,968 | **+125** | **+15.6 B** |
| `WindTerm/rz.exe` | PE32 | 65,407 B | 1,944 | **+134** | **+16.7 B** |
| `CarroNote.exe` | PE32+ | 51,663 B | 2,264 | **+74** | **+9.2 B** |
| `RapidCRC.exe` | PE32+ | 343,376 B | 3,136 | **+840** | **+105.0 B** |
| `PE-bear.exe` | PE32+ | 1,080,219 B | 3,680 | **+1,008** | **+126.0 B** |

> **关键价值**：`sz.exe` 和 `rz.exe` 在方案 A 瘦身（219 B）后仅差 10~13 字节，**仅凭 SIB 交换新增的 15~16 字节，无需改动信道架构，就能立刻让这两个 exe 成功装下加密信封！**

### 3.2 候选二：SSE / AVX 向量寄存器传送 ModR/M 镜像（★★★★★ 零成本集成）

当前 `pe_codebits` 仅收录了 GPR 通用寄存器的 9 类 ALU 指令，遗漏了现代编译器高频发射的 XMM/YMM 向量寄存器传送。

#### (1) 原理与操作码
SSE 与 AVX 的 128/256 位寄存器间传送具备与整数 `MOV (89/8B)` 完全对偶的 ModR/M 语义对（Load 形态 `r,rm` ↔ Store 形态 `rm,r`）：
* `MOVAPS`: `0F 28 /r` (`r,rm`) ↔ `0F 29 /r` (`rm,r`)（等长 3 字节）
* `MOVUPS`: `0F 10 /r` (`r,rm`) ↔ `0F 11 /r` (`rm,r`)（等长 3 字节）
* `MOVDQA`: `66 0F 6F /r` (`r,rm`) ↔ `66 0F 7F /r` (`rm,r`)（等长 4 字节）
* `MOVDQU`: `F3 0F 6F /r` (`r,rm`) ↔ `F3 0F 7F /r` (`rm,r`)（等长 4 字节）
* `MOVSS / MOVSD`: `F3/F2 0F 10 /r` ↔ `F3/F2 0F 11 /r`（标量浮点，等长 4 字节）
* 及其对应的 AVX（`VEX.128` / `VEX.256`）前缀指令。

#### (2) 安全性验证
* 仅限寄存器-寄存器操作数（`mod == 11`）；
* 寄存器操作绝对不触发 `#GP(0)` 内存未对齐故障；
* 向量传送指令**硬件保证不触碰任何 EFLAGS 状态标志位**；
* `iced-x86` 对这组指令具备完全对称的编码/解码支持。

#### (3) 增益与定位
* 在现代 64 位程序中极其密集（例如 `RapidCRC.exe` 中包含 **709 条** 纯 XMM 寄存器间传送）；
* 虽在极老编译的 32 位轻量工具（如 `sz.exe`）中较少，但其**实现成本几乎为零**（直接在 `dual_and_bit` 映射表追加表项即可），是无副作用的通用加成项。

### 3.3 候选三：方案 C `mov r,r` ↔ `lea r,[r]`（★★★★☆ 高增益高代价）

#### (1) 原理与可行性
在通用寄存器复制场景下：
* `mov rd, rs`（非 RSP/RBP/R12/R13）：
  * 形态 0：`89 /r` (`MOV rm, r`)
  * 形态 1：`8B /r` (`MOV r, rm`)
  * 形态 2：`8D /r` (`LEA rd, [rs]`)
* **实测验证**：
  * 在 64 位下均为 3 字节（REX.W + Opcode + ModRM）；
  * 在 32 位下均为 2 字节（Opcode + ModRM）；
  * `LEA` 不访问内存，不触发任何缺页或异常；
  * `MOV` 与 `LEA` 均完全不影响 EFLAGS；
  * 原型脚本 `temp/probe6_lea_verify.py` 实测往返一致性为 **100%**。

#### (2) 候选位置统计（真实 PE）
* `CarroNote.exe`：1,430 个 MOV 候选，**1,338 个可安全替换**（93.5%）；
* `WindTerm/sz.exe`：735 个 MOV 候选，**596 个可安全替换**（81.1%）；
* `WindTerm/rz.exe`：733 个 MOV 候选，**611 个可安全替换**（83.3%）；
* `PE-bear.exe`：43,119 个 MOV 候选，**40,748 个可安全替换**（94.5%）。

#### (3) 方案 C 的两大核心工程难点

##### 难点 A：3 态数据打包（Trit Packing）
单位置承载 $\log_2(3) \approx 1.585$ 比特。无法用常规按位划分处理。
* **推荐方案：定长块大数进制转换（Chunked Radix Conversion）**
  * 采用 16 字节（128 bit）为一个逻辑块；
  * $2^{128} \approx 3.40 \times 10^{38}$；
  * $3^{81} \approx 4.43 \times 10^{38} > 2^{128}$；
  * **结论：每 16 字节数据精确映射为 81 个 3 态字符（Trit）**，有效率达 $128 / 81 = 1.5802$ bit/位置（达到理论极限的 99.7%）；
  * 编解码仅需对 128 位无符号整数进行简单的除 3 取模运算，无浮点与近似误差。

##### 难点 B：还原 Diff 的膨胀与多态选择
* **原 2 态机制**：diff 仅记录“翻转/未翻转”（1 bit/位置），还原端只需取反（`1 - current`）。
* **3 态机制下的困难**：已知当前指令为状态 2，若 diff 仅给 1 个 bit 告知“被翻转了”，还原端面对剩余的状态 0 和状态 1 无法决断。
* **Diff 适配设计（两阶段位图）**：
  1. **阶段 1（变更位图）**：对全部 $M$ 个位置，每位置 1 bit，`0` 表示原样未动，`1` 表示被改动；
  2. **阶段 2（原态选择表）**：仅针对被改动的位置，每位置追加 1 bit（在剩余的两个可能形态中二选一）。
* **开销测算**：
  * 在随机载荷下，约 $2/3$ 的位置会被改写；
  * 平均每位置需消耗 $1 + \frac{2}{3} \times 1 \approx 1.67$ bit 的 slack 空间；
  * **可行性结论**：由于 text-bound 程序通常拥有较为充足的节尾 slack（例如 `CarroNote` 最大 slack run 为 496 B，而原 diff 仅需 200 余字节），完全能容纳这 60% 的 diff 增量。

### 3.4 候选四：`XCHG r0, r1` 操作数互换（★★★☆☆ 顺手支持）

* **原理**：`xchg r0, r1` 与 `xchg r1, r0` 语义完全相同；
* **操作码**：`87 /r`（16/32/64位）与 `86 /r`（8位）；
* **安全性**：100% 安全，`XCHG` 寄存器间操作不影响 EFLAGS；
* **频次**：极低（现代编译器极少发射寄存器间 XCHG，`sz.exe` 仅 3 处，`PE-bear` 约 100 处）；
* **结论**：代码量极少，可作为 `is_commutative` 的表项顺带收录，但对总容量贡献有限。

## 4. 明确排除的不可行/高风险候选（避坑清单）

在指令集探索中，对以下表面可行、实际危害极大的模式进行严格排除：

| 排除项 | 看似可行原因 | 致命风险与排除理由 |
|---|---|---|
| **`INC/DEC r` ↔ `ADD/SUB r, 1`** | 计算结果相同 | **破坏进位标志 CF**。`INC/DEC` 硬件保留 CF 不变，而 `ADD/SUB` 覆写 CF。编译器在多精度运算和循环控制中重度依赖该特性，替换必崩。 |
| **`TEST r, r` ↔ `OR/AND r, r`** | 产生相同的条件码 | **破坏寄存器独立性**。`OR/AND` 属于写回指令，会制造流水线写后读（RAW）伪依赖，并在多线程或中断上下文中破坏原子性。 |
| **`SHL r, 1` ↔ `ADD r, r`** | 都是乘以 2 | **标志位 AF 行为差异**。`SHL` 会将辅助进位标志 AF 置为未定义，而 `ADD` 严格定义 AF。 |
| **利用冗余 REX 前缀位** | 如在无 SIB 指令上置位 REX.X | **违反规范编码 Filter F4**。虽然 CPU 忽略该位，但会被反病毒引擎和取证工具标记为非最小化异常编码。 |
| **`CMPXCHG` / `PTEST` 等交换律** | 带有双比较语义 | **非对称操作**。例如 `PTEST` 的 CF 检查的是 `(NOT xmm1) AND xmm2`，交换操作数直接翻转 CF 判定结果。 |

## 6. 实施路线建议

针对当前剩余 8 个无法嵌入的 exe，建议分两阶段演进：

### 第一阶段（快速见效）：实施 2 态扩展（SIB 交换 + SSE 向量对）
1. 在 `rust/src/adapters/pe_codebits.rs` 中：
   * 将 `MOVAPS/MOVUPS/MOVDQA/MOVDQU` 等向量指令收录进 `dual_and_bit`；
   * 在 `profile` 循环中追加 SIB `scale == 1` 判定逻辑，位定义按 `Register` 序号比较；
   * 在 `embed` 与 `apply_diff` 中实现 SIB `base` 与 `index` 的原子对调。
2. **预期成效**：
   * 无需改动任何容器头部格式与 diff 逻辑；
   * `WindTerm/sz.exe` 与 `WindTerm/rz.exe` 结合方案 A 瘦身后，**直接跨过 219 B 加密信封门槛，脱离未覆盖名单**。

### 第二阶段（攻坚储备）：实施方案 C（3 态 MOV↔LEA 编解码器）
1. 在 128 位定长块上实现 16 字节 ↔ 81 Trit 的进制转换器；
2. 实现两阶段 Diff 位图，并与方案 B（分块 Diff）协同设计，将膨胀后的 Diff 打散存入多个零 slack run；
3. **预期成效**：
   * 将 `CarroNote` 容量推高至 380 B 以上，彻底解决所有非存根类的 text-bound PE。
