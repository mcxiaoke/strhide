## 0. 结论摘要

| 工作包 | 内容 | 风险 | 建议顺序 |
| :--- | :--- | :--- | :--- |
| **A 体积对齐** | 按原 IDAT 实测尺寸选 zlib 级别，替代固定 `Compression::default()` | 低（只影响写出字节，不影响可解性） | 1 |
| **B 盲检误报** | 修 private/白名单判定顺序、修采样偏置、阈值标定 | 低~中（会改动扫描结论与 `batch_stego` 门禁） | 1（B1）→ 4（B2/B3） |
| **C 三通道 Body** | 槽位从"像素"改为"(像素, 通道)"，容量 ×2.3~3.6（实测，见 §7.2；不是 ×3 的固定倍数） | 中高（格式级改动，涉及 embed/extract/probe 三处一致性） | 3 |
| **D 槽位选择重构** | 排序改为 `(cost_bits, slot)` 全序 + `select_nth`，与旧稳定排序结果逐位一致 | 中（`SlotPlan` 是三个入口的共同前置） | 2（C 的前置） |

不建议把 B2/B3 放在 C 之前：三通道会改变嵌入的空间分布，先定阈值等于对着旧分布标定。

## 1. 本次实测的新事实

### 1.1 干净 APNG 被自家扫描器判为 100 / likely-hidden（已复现）

```
$ strhide scan temp/teststego/s_hair_gre_3_mo1.png --json
risk=100 likely-hidden
  png:private-chunk likely  Private ancillary chunk 'acTL' (8 bytes)
  png:private-chunk likely  Private ancillary chunk 'fcTL' (26 bytes)   ×N
  png:private-chunk likely  Private ancillary chunk 'fdAT' (68926 bytes) ×N
```

根因在 `analysis.rs:658-671`：先按命名规则判 `is_private`，`else` 分支才查 `PNG_STANDARD_CHUNKS`。而 `acTL/fcTL/fdAT` 的第二字母小写（`c/d`），按 RFC 2083 属 private，却**同时**在白名单 `analysis.rs:588-592` 里——白名单永远轮不到。每命中一条 `Likely` 加 60 分，三条即封顶 100。

这条误报与 P3 目标直接相关（P3 要评估盲检可信度），且修法只有三行，属于必须先修的"标尺先校准"项。

> 附带修正：`temp/docs/png_stego_matrix_analysis_and_eval_20261023.md` §二.2 把 `SSD20210218.png` 的 27 分归因于"苹果私有块 `iDOT`"。实测 `iDOT` 走的是 `png:unknown-chunk`/Info（+2），27 分实际来自 `spatial:spa` 恰好 0.050 越界（+25）。

### 1.2 体积波动的**主因是 zlib 级别失配**，不是行滤波被破坏

同一份 IDAT 用标准 zlib 重压（行滤波保持不变）：

| 载体 | 原 IDAT | 原 FLEVEL | L1 | L6（现用） | L7 | L8 | L9 |
| :--- | ---: | :---: | ---: | ---: | ---: | ---: | ---: |
| `file-03.png`（2560×1440 RGB） | 3,611,694 | 3 | +18.4% | **+3.89%** | +2.77% | +0.81% | −0.06% |
| `wallhaven-ogj615.png`（14.83 MP RGBA） | 18,507,615 | 2 | +21.6% | **+6.55%** | +5.40% | +3.20% | +2.45% |
| `ref_minimal_peach.png`（1920×1920 RGBA） | 4,472,487 | 0 | −12.5% | **−28.2%** | — | — | — |
| `file-02.png`（1024×1024 RGBA） | 1,163,037 | 2 | +20.2% | **+0.16%** | — | — | — |

结论：

1. `ref_minimal_peach` 的 −28% 与 `file-03` 的 +4.2% 都可由级别解释；`file-03` 用 L9 可回到 −0.06%，`file-03` 嵌入 8 KB 多出的 235 KB 里约 150 KB 是级别差。
2. **FLEVEL 不是可靠预测器**：`wallhaven` 的 FLEVEL=2（对应 L6），但实际最接近的是 L9（原图很可能是 zopfli/oxipng 级优化）；`ref_minimal_peach` 的 FLEVEL=0 但连 L1 都比原图小 12.5%（原图非标准实现）。所以必须**实测选级**，不能查表映射。
3. 真实代价必须计入：L9 比 L6 慢 **7.9×**（`wallhaven` 4.65 s → 36.66 s，`file-03` 0.88 s → 8.30 s，CPython/zlib 实测）。L8 也已 4.4×。因此"一律 L9"不可接受，级别只能在预算内按收益选。

### 1.3 扫描器的采样是"只看图顶部"

`analysis.rs:1316-1320` 取 `pixels[..4_000_000]`，各检测器再用 `rows = (len/stride).min(512)` 截断：

| 载体 | stride | 4 MB 覆盖行数 | 实际参与检测 | 占全图 |
| :--- | ---: | ---: | ---: | ---: |
| `file-03` 1440 行 | 7680 | 546 | 512 | 顶部 36% |
| `wallhaven` 4774 行 | 12424 | 321 | 321 | 顶部 **6.7%** |

对竖构图/长图，结论完全取决于顶部那条带（常是天空/留白）。这与 `stego_remediation_plan` §1 对 JPEG "64 KiB 样本不代表全图"的裁定是同一个问题，只是 PNG 侧尚未修。

### 1.4 三通道容量增益实测上限 **2.7~2.8×**，不是 3×

按引擎现行规则（`val ∈ [8,247]` 且 `class_rule=1` 时 `val%8 ∈ [1,6]`）逐通道统计可嵌入比例（HILL 的 30% 排除按比例作用，不改变比值）：

| 载体 | R | G（现用） | B | 合计 / G |
| :--- | ---: | ---: | ---: | ---: |
| `file-03` | 56.2% | 73.4% | 70.6% | **2.73×** |
| `Special11`（RGBA，高光/暗部占 49~63%） | 38.3% | 36.8% | 28.2% | **2.81×** |

这是按边际比例推出的下界；实测（§7.2）因为"绿通道可嵌"的像素里 B 通道往往更宽松，实际增益 2.28~3.63×，`file-02` 的 37.3 KiB → 135.5 KiB。**推荐安全容量不变**（`bpp_limit` 按像素计，见 §3.4），符合上游文档"不承诺三倍安全容量"的要求。

### 1.5 现行容量与耗时基线（用于回归对比）

| 载体 | 总像素 | 载荷槽位 | 最大原始载荷 | 推荐容量 |
| :--- | ---: | ---: | ---: | ---: |
| `file-02.png` | 1,048,576 | 298,725 | 37,318 B | 5,390 B |
| `file-03.png` | 3,686,400 | 1,785,402 | 223,153 B | 32,323 B |
| `wallhaven-ogj615.png` | 14,828,044 | 7,406,073 | 925,737 B | 134,146 B |

## 2. 工作包 A：体积对齐（zlib 级别实测选级）

### 2.1 数据流改动

1. `RawImage` 增加 `idat: Option<IdatInfo>`：
   ```rust
   pub struct IdatInfo { pub flevel: u8, pub orig_len: usize }
   ```
   `decode_png` 在 IDAT 累积完成后填：`orig_len = idat.len()`，`flevel = (idat[1] >> 6) & 3`（先断言 `idat[0] & 0x0F == 8` 且 `idat[1] & 0x20 == 0`，不满足则不填、退回默认）。
2. `encode_png` 用它替换 `Compression::default()`（`spatial/engine.rs:332`）。

### 2.2 选级算法（探测 + 一次全量压缩）——已按 §6 决定收窄

```
candidates = {1, 6}                        // 用户决定：不加 7/8/9
bands      = 24 条等距，每条 B 行，B = clamp(height/96, 2, 16)
probe(L)   = 24 条带拼成一段后 deflate(L) 的字节数
est(L)     = probe(L) / probe_raw * total_raw
选 L* = argmin |est(L) - orig_len|，并列取 L6（保持历史行为）
全量压缩一次，得到 final_len
```

- **为什么从 3 段改成 24 段**：3 段（顶/中/底）在真实图上的投影误差达 −25%…+16%（`wallhaven` 顶部是天空、底部是细节），足以把级别选反；24 段等距采样把 5 张样本的误差压到 2% 以内（实测见 §7.2）。
- 探测只跑 24×16 = 384 行：`wallhaven` 8%、`file-03` 27%、小图接近全量；探测成本 0.1~0.4 s，远小于一次全量压缩。
- 级别不清求"最佳压缩"，只求"最接近原图尺寸"——原图越长越可疑，越短越可疑，两个方向都要压。
- **不做 FLEVEL→级别查表映射**：实测 miniz 的 L1 与 zlib 的 L1 相差 14.5%（§7.3），查表会系统性偏大；只做尺寸比较。
- `RawImage` 无 `IdatInfo`（测试里手工构造）→ 保持 `Compression::default()`，行为不变。
- 保留原 row filter、原 IDAT 分块数（分块逻辑不动）。

### 2.3 埋点与验收（实测结果见 §7.2）

- `STRHIDE_STEGO_TRACE=1` 时输出一行：`[png] idat orig=… final=… delta=+x.x% level=6 flevel=2 probe_l1=… probe_l6=…`。
- 单测（合成图，可离线复现）：
  - `decode_captures_the_zlib_header`：L1/L6/L9 三种载体的 `FLEVEL` 与 IDAT 总长被正确记录；无提示时退回默认级别；
  - `level_choice_follows_the_measured_size`：把 `orig_len` 设成实测 L1/L6 尺寸，决策必须分别选 1 和 6。
  - 不做"整文件体积差 < X%"这类断言：本项目的 deflate 后端是 miniz，无法复现其它工具 level 1 的字节数，体积效果只能在真实语料上度量。
- 实测验收（本机，同 §1.2 语料）：
  - `ref_minimal_peach` 8 KiB 嵌入：−28.2% → **+0.18%**；
  - `file-02`（原本 L6 就对）不回退：+1.06% → +1.04%；
  - `file-03` / `wallhaven`（原图 L9/优化件，`{1,6}` 内选不到更近的级别）保持 +4.17% / +6.67%；
  - 14.83 MP 嵌入 7.6 s，相对改造前无退化。


### 2.4 不做的部分

- 不重选 row filter（会改变逐行滤波类型直方图，是取证特征）。`temp/docs/...eval` §三.2 提到"优化滤波预测器选择"，明确不做。
- 不做 IDAT 分块数重排（现状已按原始边界切分；若流变短会少几个块，仅为轻微结构差异，记录不修）。

## 3. 工作包 C：三通道 Body 扩容

### 3.1 槽位定义（唯一真相）

```rust
// 字节偏移即槽位号：slot = pixel * channels + channel
// 参与嵌入的通道：channels >= 3 → [0,1,2]；channels < 3 → [0]
```

- **Header / FeatureWord 不变**：仍在 Green（`channels >= 3` 时通道 1，否则 0）的 512 个像素上，`SlotPlan.candidates` 与 `permute_prefix` 逻辑、`used_by_header` 语义全部不动 → 头部读取路径零改动。
- **Body 槽位** = 所有 `(px, c)`，满足：该通道值 ∈ `[8,247]`、`class_rule` 过滤、像素不在 `used_by_header` 的 **Green 槽位**上。
- 头部像素的 R/B 仍可用于 Body：`±1` 类内移动不改变 `val & 0xF8`，而 HILL 的代价图只读 `val & 0xF8`（`hill.rs:193`），所以代价图在 cover/stego 间逐位不变，头部槽位派生不受 Body 写入影响。这是三通道方案能成立的关键前提，须写成断言测试。
- `channel_mode`（`header.rs:119`，已存在，现固定写 0）：`0 = Green only`，`1 = RGB`。extract 读取后校验：`1` 且图像通道数 < 3 → `NoHiddenData`；`> 1` → `NoHiddenData`（不新增错误信息，避免探测oracle）。

### 3.2 模式选择（推荐 auto）

```
pool0 = Green 槽位数
pool1 = 三通道槽位数
needed = slots_for_codec(bits, codec, h, u)
mode = if needed <= pool0 { 0 } else if needed <= pool1 { 1 } else { 超出容量 -> 报错 }
```

理由：

- 小载荷行为与现在**逐位相同**（现有 12 个 PNG 语料格、`batch_stego` 的期望值都不用改）。
- 只有超单通道容量时才付三通道的代价（排序规模 ×2.7、`rho` 计算 ×2.7、内存 ×2.7）。
- `probe` 报告 `available_slots` / `max_raw_payload_bytes` 用 **pool1**（可达上限），`recommended_max_bytes` 仍按 bpp 档位（§3.4），因此 probe 的"最大"与 embed 实际可达一致。

### 3.3 代价与排序（与工作包 D 合并实施）

现状 `SlotPlan::build`（`spatial/engine.rs:530-548`）对候选像素做 `sort_by(partial_cmp(cost))` 再 `truncate(70%)`。三通道后候选量 ×2.7（`wallhaven`：740 万 → 约 2000 万），但只用到前缀，因此改为：

- 排序键 `(cost.to_bits(), slot)`：HILL 代价恒为正有限值（`1/avg.max(eps)`），正浮点 `to_bits` 单调，可直接用 `u64` 全序；`slot` 二级键保证**无并列**，因此 `select_nth_unstable_by` 的结果唯一、与现行稳定排序**等价**（现行稳定排序的并列次序也是升序物理下标）。
- 流程：`select_nth_unstable_by(allowed-1)` → 前缀 `sort_unstable_by` → `truncate`。
- 必须做差分测试：同一载体下新旧两条路径产出的 `candidates` 前缀逐元素相同（含平坦区块，那里代价会大量精确相等，正是并列最危险的地方）。

> 说明：现在平坦区代价全部等于 `1/eps`，并列极多，旧 `sort_by` 的稳定性实际上参与了语义。切 `select_nth` 必须带 `slot` 二级键，否则会悄悄改变选槽集合。

### 3.4 bpp 语义与容量口径

- `safety_level.bpp_limit()` 继续按**像素**计（`total_elements = w*h` 不变）。三通道把同样 bpp 摊到 3 个通道，每通道 LSB 率约降 2/3，理论上更抗检，但**没有标定数据，不在本轮改口径、也不对外宣称**。
- `probe` 输出的 `estimated_change_rate` 仍按 codec 的理论值，不按通道数缩放。
- 大图预算：三通道下 `slot_vals`(`u8`) + `moves`(`u8`) + `rho_plus/rho_minus`(`f64`×2) ≈ 18 B/槽位，`wallhaven` 满载 2000 万槽位 ≈ 360 MB，另加两份单通道 `rho` 临时图各 118 MB。本轮只做**估算值日志**（trace 里打印），不做硬预算拦截；若实测 RSS 超 2 GiB 再补 `preflight`。

### 3.5 `direction_costs` 的内存处理

`direction_costs`（`traits.rs`）签名不变，按通道调用 3 次（`channel = 0/1/2`），每次得到长度 `w*h` 的 `(plus, minus)`，只把落在本通道槽位上的值填进 `rp/rm`，随后释放该通道的两张图。不要同时持有 3 个通道的 6 张图。extract 端不需要 `rho`（只读 LSB），无需对称实现，也就没有"两端不一致"的风险。

### 3.6 风险与明确记录

- **支持集耦合**：三通道共享同一张亮度代价图，同一像素的 3 个槽位代价完全相同，因此选中的槽位集合 ≈ "最纹理化的前 K/3 个像素的全部 3 通道"。逐通道 RS/SPA 的检测率会因分母变化而下降，但"R/G/B 三通道改动位置完全重合"本身是一个理论上的可疑特征（现无检测器利用）。**本轮按此实现，并在 §3.7 的测量里显式记录该风险**；若将来要解耦，需要按通道各跑一次 HILL（当前单线程 6.5 s/14.8 MP，×3 不可接受，须先做行并行）。
- 不做浮点通道乘子（上游 §1 已裁定）。通道差异只体现在 eligibility（真实存在，见 §1.4）与 `rho`。

### 3.7 测试

1. 单元：
   - `mode=0` 与当前实现 bit-exact（用同一载体、同一密码，比对输出 PNG 字节）；
   - `mode=1` roundtrip（三种 `codec`：Hamming / STC u=1 / STC u=3）；
   - 代价图不变性：`mode=1` 嵌入后重算 HILL，与 cover 逐位相同（扩展 `hill.rs` 现有测试到三通道写入）；
   - `channel_mode` 非法值（2/3）、灰度载体 + `mode=1` → `NoHiddenData`。
2. 集成：`batch_stego` 增加"超过单通道容量、三通道可容纳"的用例（`file-02` 用 60 KB），断言 probe 的 `max_raw` 与实际可嵌入一致。
3. 回归：`cargo test`、`batch_corpus 240/240`、`batch_stego` 22/22 不变。

## 4. 工作包 B：盲检（先修标尺，再谈阈值）

### 4.1 B1 private/白名单判定顺序（必做，3 行）

```rust
if is_standard {
    // 白名单优先：acTL/fcTL/fdAT 等标准但"私有形态"的块不再报警
} else if is_private {
    walk.private.push(...);
} else if ty != b"IEND" {
    walk.unknown.push(...);
}
```

验收：`s_hair_gre_3_mo1.png` 从 100/likely-hidden → 0/clean；新增单测覆盖"白名单块 + 第二字母小写"组合。

### 4.2 B2 分层采样（替换"只看顶部"）

- 行预算：总行数上限 768 行（原 512 行 + 4 MB 前缀两条限制合并为一条），按 3 段等分（顶/中/底），段内连续取行。
- 实现：检测器改为接一个行下标切片 `rows: &[usize]`，内部用 `row * stride + col * channels + ch` 取址；`plane` 构建按行列表循环。
- 采样后仍保持"每通道独立评估"的现状（`eval_channels = min(channels,3)`）。
- 验收：对 §1.5 语料重跑，记录 cover 集合上每个检测器的分布变化；**cover 误报不得增加**；`wallhaven` 因为采样从 6.7% 提升到 16% 而结论稳定性提高（记录前后对比，不预设好坏）。

### 4.3 B3 阈值标定与聚合（需要标签集）

现状两个结构性问题：

1. `aggregate_risk`（`analysis.rs:1735`）按"发现条数"加分：单条 `Suspicious` 就是 25 分，`Special11`/`SSD20210218` 靠 SPA 恰好 0.050 就进 `low`。阈值正好压在误报拐点上。
2. 三个检测器都取 **跨通道最大值**（`rs_analysis:1647-1659`、`spa_estimate_dww:1678-1728`、`ws_analysis:1255-1304`）。通道数 3 时，误报概率约是单通道的 3 倍；三通道嵌入后每通道速率又降到 1/3。两者叠加后，"取最大"的口径既不稳健也不可比。

标定流程（产物放 `temp/blind_calib/`，结论写回本文 §4.4）：

1. 标签集：22 个 cover（`temp/teststego`，剔除不可嵌入的 palette/APNG/interlace）+ 每个可嵌入 cover 的 3 档 stego（1 KiB、64 KiB、单通道满载/三通道满载），全部 `mode` 记录在案。
2. 对每个检测器输出逐图分值（WS/RS/SPA/chi²），分别在 cover 集与 stego 集上取分布。
3. 给出门限候选：取 cover 集的 P95/P99 作阈值，报告对应 TPR（**只报实测值，不承诺"0~2/100"这类数字**）。
4. 聚合改法（待标定后定稿，倾向）：单检测器越界 → `Info`；**≥2 个检测器同时越界**才升 `Suspicious`；结构性证据（私有块/尾部数据/工具签名）维持现有权重。

## 6. 已确定的取舍（2026-10-23 19:52 用户决定）

1. **C 的触发策略：`auto`**。小载荷仍走单通道，布局与输出逐位不变；只有单通道装不下时才切 RGB。不加 `--channel-mode` 开关。

4. **§3.6 通道支持集耦合：本轮接受**。三通道共享同一张亮度代价图，R/G/B 的改动位置高度重合；已在 §3.6 记录为已知残余风险，逐通道独立代价需要先做 HILL 行并行。

### 7.3 实施中发现的两点

1. **flate2（miniz）的 level 1 与 zlib 的 level 1 不是同一个东西**：同一张 `ref_minimal_peach`，zlib-L1 产出 3.91 MB，miniz-L1 产出 4.48 MB（差 14.5%）。所以"跟随原图 FLEVEL 查表映射级别"会系统性偏大；按实测尺寸比较是唯一可靠做法，这也是 `choose_deflate_level` 只做尺寸比较、不做级别映射的原因。
2. **包络会压缩载荷**：用 `0x5A` 重复字节做"满载"测试时，6.9 KiB 载荷被压到 134 B，实际只用了 1077 个槽位，看起来像容量算错。测试必须用不可压缩载荷（新增 `noise_payload` 辅助函数）。
