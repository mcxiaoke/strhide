### 2026-10-27 13:01:57 - 架构重构阶段 1（前半）：格式层 `formats` 落地 + 能力表 + 嗅探三处合一

**1. 新增 `rust/src/formats/`（第 2 层：共享格式层，无 feature 门控）**
- `sniff.rs`：`FileFormat` 枚举（Png/Jpeg/Webp/Heif/Mp4/Mkv/Wav/Zip/Pdf/Pe/HevcAnnexB）+ `sniff_bytes()` + `sniff_stream()`（读最多 64 KiB 前缀并恢复游标）。判定顺序按容器语义固定：JPEG → PNG → HEIF（`ftyp` 品牌）→ MP4（12 种顶层 box 白名单，排除 HEIF）→ WebP/WAV（`RIFF` + form type）→ MKV（EBML 头）→ ZIP（3 种 PK 魔数）→ PDF → PE（`MZ` + `e_lfanew` + `PE\0\0`）→ Annex-B（最后，因为容器载荷里可能含起始码）。
- `annexb.rs`：Annex-B 帧层判定（起始码 + 2 字节 NAL 头 + NAL 类型白名单）与全部 `NAL_*` 常量从 `stego/hevc/sniff.rs` 原样迁入。它属于"载体分类"而不是 HEVC 语法，`stego::hevc::sniff` 用 `pub use` 保持旧路径。
- `capability.rs`：能力表 `CAPABILITIES`（每格式一行：结构域策略、内容域引擎、扩展名）+ `FileFormat::supports_structure()/supports_stego()/extensions()`。这是"什么格式支持什么"的唯一出处。
- `mod.rs`：只做再导出，`formats` 不依赖 `structure`/`stego` 任何符号。

**2. 内容域三处 if-else 瀑布改为统一嗅探**
- `stego/mod.rs` 的 `embed_carrier_with_profile_info` / `extract_carrier` / `probe_carrier_capacity` 原先各自手写 5 个魔数比较（共 15 处），现在每个函数只调一次 `sniff_bytes()`，再用 `format == Some(FileFormat::X)` 分派；probe 的 MP4/Annex-B 合并分支用 `matches!`。
- 行为差异只有一处（有意）：MP4 判定从 `ftyp|moov|mdat` 三种扩到适配器本就认可的 12 种顶层 box，分片/CMAF 流（`styp`/`moof`/`sidx` 打头）不再被内容域直接判为不支持。基线 58 例无变化（语料里没有这类流）。

**3. 删除 `HostAdapter::supports_content_stego`（1 个默认实现 + 4 处覆写）**
- 适配器属于结构域，不该知道内容域存在。`engine.rs:1991` 改为 `router::supports_content_stego(adapter)`，内部查 `CAPABILITIES`；名字 → `FileFormat` 的往返由测试钉住。

**4. `src/sniff.rs` 变成兼容层**
- 实现迁到 `formats::sniff`，原 `strhide::sniff::{is_png_bytes, is_heif_bytes, HEIF_BRANDS, PNG_MAGIC, ...}` 全部保留为 `pub use`，`adapters/heif.rs` 的 `pub use crate::sniff::{HEIF_BRANDS, is_heif_bytes}` 无需改动。

**5. 新增一致性测试 `tests/test_lifecycle/sniff.rs`（5 项）**
- `sniff_bytes` 与 `router::find_adapter` 对 10 种格式给出同一答案（并断言 `sniff_stream` 恢复游标位置）；
- `CAPABILITIES.structure` 与每个适配器的 `supported_strategies()` 逐项相等（防两处漂移）；
- 声称支持结构域的格式必须有适配器；Annex-B 只属内容域且路由器仍拒绝它；ZIP/PDF/PE/WAV/WebP/MKV 不得声称内容域支持。

### 2026-10-27 12:19:44 - 重构阶段 0：字节级基线 + 三个独立缺陷（B1/B2/B3）+ CI 补 clippy 门禁

**0. 新增 `scripts/baseline_hash.py`（阶段 0 的硬验收工具）**
- 目的：阶段 1 要合并三份 ISOBMFF 解析、搬动格式嗅探，这些改动一旦让写入字节发生偏移，单测未必发现（还原会静默产出不可还原的载体）。脚本把每类载体的**可观测数字**冻结成 JSON，重构后逐项比对。
- 覆盖：`rust/tests/fixtures` + `rust/tests/assets` + `temp/testhevc` 共 **58 例**，release 二进制约 61 s。结构域 44 例成功（HEIF 24、MP4 12、JPEG 4、PNG 2、MKV 2；策略 `item_hidden`/`box_uuid`/`app_segment`/`chunk`/`ebml_void`），14 例按预期不支持（12 条 `.hevc` Annex-B + 1 条 `.hevc10` + 1 个 `.txt`）。
- 记录内容：原始 size/sha256；结构域的 `strategy`、`ube_total_size`、`stego_size`、读回载荷 sha256、**还原后 sha256（44/44 与原文件逐字节相等）**、`inspect --json` 的每策略容量；内容域的 `max/recommended` 容量、读回载荷 sha256。
- 内容域**逐字节比对**：基线用固定 `--seed`（见第 5 节）驱动每次 embed，因此 `content.stego_size` 与新增的 `content.stego_sha256` 都参与严格比对。结构域的 UBE 信封 nonce 始终随机、没有种子开关，那边只比对信封大小、策略、每策略容量与还原是否逐字节相等（44/44 通过）。`--no-seed` 时自动退回"只比大小、不比字节"。
- 用法：`python scripts/baseline_hash.py --write` 冻结，`--check` 比对，`--only <corpus> --limit N` 冒烟。结果在 `temp/baseline/`（gitignored，schema 2）。连续两次 `--check` 已验证 58/58 完全一致（含 5 个内容域产物的字节哈希）；种子与基线不一致时 `--check` 会在起跑前直接报错退出。

**1. B1：HEVC 分支丢掉 `SafetyEnforcement`，`--enforce-safety` 对 HEVC 完全无效**
- 根因：`stego/mod.rs` 的四个 HEVC 调用点传的是 `options.safety.level`，而 PNG/JPEG 传的是整个 `options.safety`；引擎签名 `embed_hevc_with_info(..., safety_level: SafetyLevel)` 也把 enforcement 从类型上抹掉了。
- 修复：签名改为 `safety: SafetyPolicy`（`stego/hevc/engine.rs`），把判定抽成 `enforce_safety(payload_len, recommended, max, policy)`，在容量信息算完之后立即检查；命中返回**新增**的 `StrHideError::SafetyThreshold`（`category()` 复用 `Msg::ErrRejection`，不新增 i18n 词条）。
- 连带修掉一个把错误吃掉的路径：HEIF 分支的兜底是 `Err(_) => heif::embed_heif_bridge(...)`，会把任何错误（含安全拦截、容量不足）替换成桥接器自己的 "No bridgeable image carrier"。改为 `Err(e @ SafetyThreshold(_)) => Err(e)` 直接上抛。
- 实测（`temp/testhevc/test.heic`，推荐 4788 B / 上限 16618 B，载荷 9216 B）：`--enforce-safety` → `[ERROR] 安全策略拦截: Payload (9216 bytes) exceeds safety threshold (4788 bytes) for tier 'high' (carrier maximum is 16618 bytes)`，退出码 1，不产生输出文件；不带该参数 → 照常嵌入并打印 `[WARN] ... Detection risk is elevated`。
- 新增回归测试 `stego::hevc::engine::safety_policy_tests`（3 项，无需语料）：advisory 不拦截、enforced 拦截且报文含两个边界值、等于推荐值时放行。

**2. B2：删除死代码 `stego::sniff::CarrierFormat`**
- 该枚举只有自身文件引用（全库 0 调用点），且缺 `Mp4` 变体，对 MP4 会答 "unsupported"。直接删除 `src/stego/sniff.rs` 与 `stego/mod.rs` 的 `pub mod sniff;`，不修补——阶段 1 会用 `formats::FileFormat` 作为唯一事实源。

**3. B3：门面无法覆盖已存在的输出文件**
- 根因：`facade.rs` 的 `read` / `restore` 把 `overwrite` 硬编码为 `false`，调用者只能退回 5 参数自由函数。
- 修复：新增 `StrHide::read_with(..., overwrite)` 与 `StrHide::restore_with(..., backup, overwrite)`，原 `read` / `restore` 委托过去（默认仍拒绝覆盖，行为不变）。
- 新增集成测试 `test_lifecycle/facade.rs::structure_read_and_restore_honour_the_overwrite_flag`：拒绝时**不得截断**已存在文件；`_with` 形式覆盖成功；还原结果与原 PNG 逐字节相等。

**4. CI：补上缺失的 clippy 门禁 + 非阻塞的最小 feature 构建**
- `ci.yml` 原先只有 `cargo fmt --all --check` 与 `cargo test`，与 `AGENTS.md` 声明的 "CI 硬性跑 clippy -D warnings" 不符，现补 `cargo clippy --all-targets --all-features -- -D warnings`。
- 新增 `Minimal feature builds (stage 0, non-blocking)`：`--no-default-features --features engine` 与 `--features stego`。两者当前**都能编过**，但 `engine`-only 会报 3 条告警（`MAX_CONTENT_STEGO_BYTES` 未使用、`OsString`/`PathBuf` 未使用），阶段 1 拆 feature 时一并清掉，届时转硬性。
- 基线脚本不进 CI：它依赖 gitignored 的 `temp/testhevc` 语料，只能本地跑。

**5. 新增 `--seed`：让内容域嵌入可复现（基线因此能比字节）**
- `Freshness::Seeded([u8; 32])` 一直在库里（`stego/envelope.rs:215`，注释写明用途是回归测试与可复现的 bug 报告），但 CLI 从未暴露它——`cli.rs` 里 0 处引用 `Freshness`，所以命令行产出永远带随机盐。
- 新增 `--seed <HEX64>`（挂在 `StegoTuningArgs`，因此 `embed` 与 `capacity` 都接受），解析失败直接报错而不是补零或哈希——否则"同一个种子"会产出不同文件。盐/nonce 由 `seed + SHA256(cover) + SHA256(payload)` 派生，换载体或换载荷不会复用同一对 `(key, nonce)`。
- 实测：同种子两次 embed 逐字节相同（sha256 均为 `c5cac5f1…`），换种子不同，不传种子仍然每次不同，种子化产物可正常 `extract`；`--seed zz` → 退出码 1 并提示需要 64 位十六进制。
- 新增集成测试 `test_cli/cli_unification.rs::embed_seed_is_reproducible_and_seed_dependent`（同种子相等 / 异种子不等 / 可提取 / 坏种子报错）。
