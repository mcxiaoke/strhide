**结论修正（重要）**：分组网格**确实能在改动数上赢 Hamming，但只在槽位充裕时成立**。同一载体 `ref_minimal_peach`（槽位池 ~3.2 M，u=2 仅用 16%）u=2 改动数 0.2758 < Hamming 0.2925，u=3 为 0.2276（低 22%）；而 `DC912sk1`（u=2 已占 82% 槽位池）为 0.3063，略高于 Hamming。原因不是实现，是占用率：STC 的收益来自"挑最便宜的槽"，满载时没有便宜槽可挑。设计文档 §11.1 原先的"等容量下必然赢"判断需要按本轮数据收紧为"**在给定载荷远小于载体容量时成立**"。
  离线 trellis 仿真（`temp/stc_sim.py`，n≈640–960、h=8/10，等槽位预算）给出的等容量插值与上表一致：u≈2.33 时改动率约 0.15/槽 vs Hamming 0.126/槽，等容量下 STC 仍略逊；只有在**载荷占载体容量的比例下降**时 STC 才反超。带宽（`h ≥ 10`）带来的边际收益很小（h=8→10 仅 −3%），瓶颈不在 `h`。

**验证**：`cargo fmt --check` / `cargo clippy --all-targets -- -D warnings` / `cargo test --all-targets` 全绿（364 项；本批新增 14 项：`isobmff` 4、`pdf` 2、`header` 3、trellis 3、引擎 1、JPEG 端到端 1）；STC `u=1` 的 Hamming 路径与既有 PNG/JPEG stego 载体**逐位兼容**。

**语料全量回归（`batch_stego`，19 例含 4 例按设计拒绝，`STRHIDE_STEGO_CODEC` 新增开关）**：

| codec | 往返还原 | 满载检出率（risk ≥ 10） |
|---|---:|---:|
| Hamming（默认） | 19/19 | 87%（13/15） |
| STC u=1 | 19/19 | 87%（13/15） |
| STC u=2 | 19/19 | 80%（12/15） |
| STC u=3 | 19/19 | **67%（10/15）** |

满载检出率随 `u` 单调下降，与 §12.4 的改动数一致——这是分组网格的**设计目标**，不是检测器退化。`batch_stego` 的 80% 门槛因此改为只对默认 codec 生效（非默认 codec 用 50% 的"检测器未坍塌"下限），否则 `u=3` 会因"藏得太好"而判失败。

**遗留**：`u` 未接入 `probe_carrier_capacity` 的"推荐值"语义（仍取上限一半），是否需要按 `u` 调整推荐比例留待更多语料后再定。

### 2026-10-21 01:12:38 - 新增 STC（综合征网格码）编码层：`--codec stc` 可选，加权失真降 408 倍，默认仍为 Hamming

依据 `docs/embed_png_jpeg_algorithm_review_20261020_db.md` §9.2.1（P1-a）与设计文档 `docs/stc_coding_design_20261021.md`。评审要求"STC 先写设计文档再实现"，文档与实现同批落地。

- **编码层（新增 `stego/coding/stc.rs`）**：`StcTrellis` 实现 Filler/Judas/Fridrich 2011 的带状校验矩阵 + Viterbi。`H` 为 `(n−h+1)×n`，`H[i][j] = ĥ[j−i]`，列 `j` 对行 `j−h+1..=j` 的系数是 `ĥ[h−1..0]`；状态 = 尚未定稿的 `h−1` 位综合症，每列 2 个候选（保持 / 翻转），翻转方向由 `ρ±` 与 `Move` 合法性决定，`ρ = ∞` 即湿槽。回溯用每（列, 状态）2 bit 位图，`n=60万, h=8` 约 9.6 MB。`ĥ` 首末位强制为 1（否则部分综合症不可达）。
- **正确性验证（穷举对拍）**：`embed_matches_exhaustive_optimum_and_round_trips` 用 `3^n` 全枚举求满足 `Hx=m` 的最小代价解，与 Viterbi 结果**代价逐位相等**（3 组 `(seed, h)`）；`trellis_shape_and_syndrome_match_the_formula` 对拍 `Hx` 公式；`wet_direction_is_never_used` 验证 `ρ=∞` 方向一次未被选中。
- **密钥化（`envelope.rs`）**：新增 `derive_stc_seed(perm_seed, salt)` —— 从已派生的 `perm_seed` 再做一次 HKDF（域分隔 `b"strhide-stc-trellis-v1"`），**避免第二次 10 万轮 PBKDF2**。校验矩阵与 payload 密钥同源，泄漏 `H` 等于把检测器交给对方。
- **参数登记（零格式变更）**：内容隐写 32 字节头部的第 32 位起那个字原本是"信封长度"，而长度受 64 MiB = 2^26 上限约束，**高 6 位恒为 0**。改为 `[26b 长度][2b codec][4b stc_h]`。旧载体那 6 位天然为 0 → 解码成 `Hamming`，**向后兼容是构造出来的而非补出来的**；头长度不变、无需版本位、不碰 `strategy_id`（评审 P0-7 的结构域风险面不扩大）。三种解码失败（codec id ≥ 2、STC 但 `h` 越界、长度越界）**全部折叠成同一句 `No valid payload found`**，不提供"信封存在但布局不对"的 oracle。
- **引擎（`stego/spatial/engine.rs`）**：`slots_for()` 按 codec 分派（Hamming 2.33 槽/bit、STC 1 槽/bit），嵌入/提取各加一个 `match`；提取端 codec 完全来自头部，`SpatialParams.codec` 在提取时被忽略（有测试 `stc_codec_roundtrips_and_stays_in_class` 专门用一个仍是 Hamming 的 extract params 反证）。`perm_seed` 的派生提前到容量检查之前，供 `stc_seed` 复用。
- **容量语义更正**：设计草稿主张"多分配槽位并填 0 以保持容量口径不变"是**错的**——填 0 的位仍是约束，等于让编码器解 2.33 倍大的问题。实际按 codec 报真值：`Special11.png` 由 16 825 B 变 39 285 B（2.33 倍），`recommended_max_bytes` 仍取一半。`estimated_change_rate` 相应改为 codec 相关（STC ~0.5，不好看但是真的）。
- **CLI**：`embed` 新增 `--codec hamming|stc`、`--stc-h 4..10`（默认 8）；非法值在参数装配处报明确错误（"Unknown codec 'bogus'"/"STC constraint height must be in 4..=10, got 12"）。`extract` 无对应 flag。
- **实测（`examples/codec_bench.rs`，33 000 B 随机载荷，`h=8`）**：

  | `DC912sk1` 960×960 | 77 216 / 131 945 | 1.14e10 | **2.78e7** | 298 / 369 | 25 LOW | **0 CLEAN** |
  | `SSD20210218` 1608×990 | 77 175 / 131 569 | 3.47e11 | **1.70e11** | 239 / 307 | 2 | 27（原图即 27） |

  加权失真 2/3 领先（408×、2.0×）、1/3 略差 12%（该图近均匀噪声，成本图方差小）；改动数稳定 +71%；检测分数从未更差；耗时 1.2–1.3 倍，最大载体 1.3 s（门槛 3 s）。

### 2026-10-21 02:34:07 - 库侧 M3（内存载体 API）+ M4（示例与文档）：`write/read/remove_carrier_bytes`

依据 `docs/library_api_practical_plan_20261020.md` §5（M3/M4）与 §8 的实施顺序（M1 全做、M3 紧跟）。M1 已于 2026-10-20 落地，本批补 M3/M4。

- **先抽核心（`engine.rs`）**：把三个入口拆成"协议核心 + 路径副作用"两层，核心全部与文件系统无关：
  - `write_core<H, W>(host, out, source, options, local, profile)`：信封组装、`inject`、header/trailer 回填、`finalize`。`H: Read + Seek`、`W: Read + Write + Seek` 用 **sized 泛型**而非 `&mut dyn`：适配器的 `inject`/`finalize` 分别要 `&mut dyn Write`/`&mut dyn SeekReadWrite`，传具体类型可避免依赖 trait object 上转。
  - `read_core(host, label, password, profile)`：定位 → 解头 → AEAD → 解压 → SHA-256 校验，返回 `ReadCore`。
  - `remove_core(host, out, label, ...)` + `verify_restored(reader, header, ...)`：剥离与还原校验分开，因为"校验需要重新读一遍输出"这件事对文件和内存的形态不同。
  - `verify_written(reader, &VerifyParams, ...)`：自校验从写侧提出，同样因为输出形态不同。
  - `no_hidden_data_error` 的 `carrier_path: &Path` 参数改为 `label: &str`（内存模式的标签是 `"<memory>"`）。
- **新增三个公开入口**：`write_carrier_bytes(&[u8], PayloadSource, &WriteOptions, &LocalParams, &Profile) -> (Vec<u8>, WriteResult)`、`read_carrier_bytes`、`remove_carrier_bytes`。三处**明确记录的退化**：无原子提交（调用方持有缓冲区）、无 `.bak`、无时间戳克隆（`options.backup`/`options.preserve_time` 被忽略）。
- **rejection 语义**：内存模式只跑 `rejection::check_content`（Authenticode/PDF/JAR 签名），跳过三个路径类检查（只读载体、目标目录写探针、`.apk`/`.sig` 文件名检查），因为它们描述的是文件系统而非载体。`local.rejection == Skip` 时同样跳过。
- **`output_path` 显式拒绝**：契约是"返回字节"，静默落盘会成为隐藏副作用，因此在入口处报错并点名该字段。
- **两处兼容性修正**：
  - `crypto::compute_stream_sha256` 的泛型由 `R: Read` 放宽为 `R: Read + ?Sized`，否则 `&mut dyn SeekRead` 传不进去（sized 约束排除 trait object）。
  - 暂存输出文件由 `File::create`（只写）改为 `OpenOptions.read(true).write(true)`：`finalize` 可能回读刚写的内容，Windows 下只写句柄读文件会直接 `os error 5 拒绝访问`。这个 bug 让 59 个 CLI 测试一次性失败，是本批唯一的回归。
- **测试（新增 `tests/api_bytes.rs`，9 项）**：内存往返、**字节 API 与文件 API 互相可读**（防止两条路径漂移）、`remove` 逐字节还原始载体、错误口令/无口令的失败形态、`output_path` 拒绝且不落盘、已含信封的载体被拒、stealth 在内存中生效且无口令必失败、**文件 remove 与内存 remove 结果一致**、**4 行 profile 兼容矩阵**（official↔official、private↔private 互通；private↔official 双向都必须是 `NoHiddenData`，不能是可区分的错误）。
- **示例（M4）**：`examples/in_memory.rs`（三步全内存 + 打印真实尺寸/策略）、`examples/private_profile.rs`（自定义 magic/secret/domain，并演示官方 profile 读私有载体时得到的是"没有数据"而非方言错误）。均实测跑通。
