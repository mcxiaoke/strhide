### 2026-10-21 09:05:08 - STC 分组网格（rows = n/u）+ JPEG/UERD 接入 + 修 STC 回溯缺陷；MP4 64-bit box 与 PDF `calc_prefix_len` 补测

3. **STC 回溯缺陷修复（既有实现）**：`embed` 的 Viterbi 在 warm-up 阶段（`row < 0`，前 `h−1` 行）**不做约束检查**，但回溯时按 `want == 0` 反推前一状态。两者在"warm-up 列发生翻转"时不一致，回溯路径偏离真实路径，写出**无法提取**的 stego（表现为 `No valid payload found`）。触发条件是 warm-up 期间任一列翻转，真实载体上概率不低但稀疏，此前 3 张语料的实测恰好没有踩中。修复为 warm-up 行同样按 `want == 0` 约束（`if (st1 & 1) != want` 不再带 `row >= 0` 前置条件），格式与提取语义不变。**这是一个已发布路径的 bug，不是本次新引入的**。
4. **STC 分组网格（`rows = n/u`，设计文档 §11.1）**：`StcTrellis` 增加 `u` —— 每 `u` 个元素共用一个综合症行，组内 `u` 个列向量由 seed 派生且**线性无关**（GF(2) 消元校验，`u <= h`）。状态 = `h−1` 位（行 `g..g+h−2`）+ 1 位 extra（行 `g+h−1`，`u > 1` 时需要）；`u = 1` 时状态位与转移与旧实现**完全同构**（性能不减半）。`message_bits = n/u − (h−1)`、`slots_for = u·(bits + h − 1)`。提取新增 `row_syndrome(row)`，按 `[max(0,r−h+1), r]` 的行窗口重算。验证：`3^n` 穷举对拍扩展到 `u ∈ {1,2,3}`（Oracle 判据改为**全矩阵**，含 warm-up 行）、往返、类内约束、湿槽、`u=2/u=3` 改动率递减。
5. **参数与线格式（零新增字节）**：`SpatialParams`/`JpegParams` 增加 `stc_u`（1..3，默认 1，serde default）。`u` 编码进 codec id：`0 = Hamming`、`1..3 = STC(u = id)`——`u=1` 仍是 1，**旧载体解码行为逐位不变**。头部字布局不变（`[26b 长度][2b codec][4b stc_h]`）。新增模块 `stego/header.rs` 集中承载该布局，`spatial::engine` 改为重导出（旧 API 路径仍可用），JPEG 引擎复用同一实现。
6. **JPEG/UERD 接入 STC（设计文档 §11.2）**：`JpegParams` 增加 `codec`/`stc_h`/`stc_u`；`embed_jpeg`/`extract_jpeg` 的槽位规划抽成 `plan_slots`（两侧原本是两份 60 行重复代码）。**关键约束**：±1 必须停在 `(2k, 2k+1)` 对内（保 `|c| & !1` 不变），否则 UERD 代价图在提取端不可复现——新增 `coding::dct_move`，正偶 → `+1`、正奇 → `−1`、负数镜像。编码层不接触 `i16` 量级：body 传给 trellis/Hamming 的是 **parity 载体 `{2,3}`**（`+1` 恒翻 LSB、不会溢出），真实方向由写回时 `dct_move` 决定。这使 Hamming 与 STC 在 JPEG 上共用同一套 `Move`/`ρ` 接口，且 Hamming 路径行为与改前等价。

### 2026-10-21 01:12:38 - 新增 STC（综合征网格码）编码层：`--codec stc` 可选，加权失真降 408 倍，默认仍为 Hamming

依据 `docs/embed_png_jpeg_algorithm_review_20261020_db.md` §9.2.1（P1-a）与设计文档 `docs/stc_coding_design_20261021.md`。评审要求"STC 先写设计文档再实现"，文档与实现同批落地。

- **编码层（新增 `stego/coding/stc.rs`）**：`StcTrellis` 实现 Filler/Judas/Fridrich 2011 的带状校验矩阵 + Viterbi。`H` 为 `(n−h+1)×n`，`H[i][j] = ĥ[j−i]`，列 `j` 对行 `j−h+1..=j` 的系数是 `ĥ[h−1..0]`；状态 = 尚未定稿的 `h−1` 位综合症，每列 2 个候选（保持 / 翻转），翻转方向由 `ρ±` 与 `Move` 合法性决定，`ρ = ∞` 即湿槽。回溯用每（列, 状态）2 bit 位图，`n=60万, h=8` 约 9.6 MB。`ĥ` 首末位强制为 1（否则部分综合症不可达）。
- **正确性验证（穷举对拍）**：`embed_matches_exhaustive_optimum_and_round_trips` 用 `3^n` 全枚举求满足 `Hx=m` 的最小代价解，与 Viterbi 结果**代价逐位相等**（3 组 `(seed, h)`）；`trellis_shape_and_syndrome_match_the_formula` 对拍 `Hx` 公式；`wet_direction_is_never_used` 验证 `ρ=∞` 方向一次未被选中。
- **密钥化（`envelope.rs`）**：新增 `derive_stc_seed(perm_seed, salt)` —— 从已派生的 `perm_seed` 再做一次 HKDF（域分隔 `b"strhide-stc-trellis-v1"`），**避免第二次 10 万轮 PBKDF2**。校验矩阵与 payload 密钥同源，泄漏 `H` 等于把检测器交给对方。
- **参数登记（零格式变更）**：内容隐写 32 字节头部的第 32 位起那个字原本是"信封长度"，而长度受 64 MiB = 2^26 上限约束，**高 6 位恒为 0**。改为 `[26b 长度][2b codec][4b stc_h]`。旧载体那 6 位天然为 0 → 解码成 `Hamming`，**向后兼容是构造出来的而非补出来的**；头长度不变、无需版本位、不碰 `strategy_id`（评审 P0-7 的结构域风险面不扩大）。三种解码失败（codec id ≥ 2、STC 但 `h` 越界、长度越界）**全部折叠成同一句 `No valid payload found`**，不提供"信封存在但布局不对"的 oracle。

### 2026-10-21 02:34:07 - 库侧 M3（内存载体 API）+ M4（示例与文档）：`write/read/remove_carrier_bytes`
