## 提取与失败

**Q1. 提取失败，提示"密码不正确或没有内容"，到底哪个原因？**
两者无法区分，这是设计如此。内容域在密钥、方言、suite、AAD 任一不匹配时统一返回 `NoHiddenData`；结构域在密码错误时表现为元数据解密失败。任何更细的错误都会泄露"这个文件确实藏了东西"。排查顺序：先用 `sth scan` 看是否有内容、是否加密，再确认密码、确认文件没有被转发/重编码过。

**Q2. 昨天还能读，今天读不出来，文件我"只是发了一下"。**
转发过程里被重编码了。聊天软件、图床、邮件客户端预览、图片查看器的"另存"都会重写像素或码流，内容域载荷随之永久丢失。结构域在重编码后同样无法 `restore`。**保留原始隐写文件**是唯一可靠做法。

**Q3. 为什么 `scan` 说"未发现"，但我确定有内容？**
`scan` 是无口令的黑盒启发式检测（卡方、RS 分析、JPEG 标定等），不是解密。stealth 模式、低载荷率、或者内容域写入都会让统计信号弱到无法判定。"未发现"只表示没有命中特征，不等于安全结论。

**Q4. 提取出来的文件名不是我原来的文件名。**
写入时用了 `--no-filename`，文件名就没进信封。此时提取会按兜底规则命名（桌面端为 `<载体名>_payload`，CLI 见 `read`/`extract` 的 `-o` 行为）。桌面端不提供匿名化开关，需要这个行为要用 CLI。想保留文件名就不要开 `--no-filename`。

## 还原与不可逆

**Q5. `restore` 报 `Restore verification failed`，原件还能救吗？**
通常不能。该命令对比原宿主的 size 与 SHA-256，不一致时**拒绝输出**而不是给你一个坏文件。两种成因：① 写入后载体被再次处理（重编码、或又做了一次内容域嵌入）；② 同一文件叠了两层信封——这种情况错误信息会提示"按写入逆序移除"。逆序移除后再 `restore` 才有可能成功。

**Q6. 内容域写入后能还原吗？**
不能。隐写改的就是像素/DCT/码流/采样本身，不存在"原始字节"可回退。需要可还原就用结构域（`write` / 界面上的「嵌入」）。

**Q7. 同一个文件能同时用两种方式写入吗？**
库层面可以叠加，但 CLI 在载体已有信封时会拒绝第二次写入，除非显式 `--overwrite`。注意：内容域一旦写入，结构域的 `restore` 保证就失效了（宿主字节已变）。

## 容量与性能

**Q8. `capacity` 报的数比"像素数 / 8"小很多，为什么？**
三个因素：① 信封框架（基础头 + 微头 + AEAD tag，`BODY_OVERHEAD = 22` 起）；② 安全档位限制载荷率（`paranoid < high < balanced`）；③ 工作内存预算——引擎会拒绝超出预算的写入，所以报告的上限是"一定能写成"的值。容量报告不含文件名；带文件名还要多 `1 + name_len` 字节。

**Q9. 为什么一张 12 MP 的 PNG 要 1.8 秒？**
内容域 PNG 需要重算整张图的代价图（HILL/S-UNIWARD/MiPOD 都是小波域滤波），成本与像素数成正比，与载荷大小几乎无关。对比：12 MP 的 HEIC 只需约 0.24 秒，因为走的是码流符号位而不是像素。完整数据见 [BENCHMARK.md](../BENCHMARK.md)。

**Q10. FLAC 为什么比其他引擎慢一个数量级？**
FLAC 要在残差域改值并且**保持 Rice 码字长度不变**，否则文件体积和帧结构都会变。这需要逐帧解析与重编码验证，成本远高于 PCM 采样位翻转。见 [CONTENT-AUDIO.md](api/spec/CONTENT-AUDIO.md)。

**Q11. HEVC 写入后文件大小完全没变，是真的吗？**
是真的，设计目标就是 Δ=0：只翻转 CABAC bypass 符号位，不新增字节。这也是它相对其他引擎的隐蔽性优势（体积比对失效）。

**Q12. 内存占用能控制吗？**
可以控制上限但不能无限调大：引擎有工作内存预算，超出会以 `Payload too large` 失败而不是 OOM。容量报告已经反映了这个上限。

## 密码与密钥

**Q13. `-p`、`--password-file`、`STRHIDE_PASSWORD`、`-e` 怎么选？**
`-p` 最快但会留在 shell 历史与进程列表里；`--password-file` 只读第一行，适合脚本；`STRHIDE_PASSWORD` 适合 CI；`-e` 交互式输入并二次确认，最不容易留痕。生产环境优先后三者。

**Q14. 想不用口令，直接用一个 32 字节密钥。**
用 `--key-file`：接受 32 字节原始二进制或 64 字符十六进制文本，跳过 PBKDF2 直接进 HKDF。这样省掉约 20 ms 的派生开销，也避免了弱口令。

**Q15. 不设密码会怎样？**
回落到公开默认常量（内容域 `PUBLIC_DEFAULT_SECRET`、结构域 `BUILTIN_DEFAULT_KEY`），**任何官方 strhide 构建都能读**。这是为互操作保留的行为，不是加密。

**Q16. `--stealth` 为什么强制要密码？**
无痕模式的魔数与头部掩码都是从口令派生的。没有口令就没有派生源，只能退回公开常量——那等于"无痕"两字失效。因此 CLI 与桌面端都会直接拒绝无密码的 stealth。

**Q17. `--stealth` 能让我躲过检测吗？**
不能。它只抹掉"可归因到 strhide"的固定特征（魔数、头字段明文），不改变统计面的可检测性。见 [PRIVATE_BUILD.md](PRIVATE_BUILD.md) §6 与 [THREAT_MODEL.md](THREAT_MODEL.md) §4。

## 文件与备份

**Q18. `.bak` 文件是什么？能删吗？**
`--in-place` 原地写入时默认生成的**未加密原件副本**。能删，但删之前想清楚：它是你唯一能拿回原件的路径之一（另一个是 `restore`）。不想生成就用 `--no-backup`。**桌面端不生成 `.bak`**，它总是写到目标目录。

**Q19. 桌面端为什么没有「还原」按钮？**
位精确还原需要原宿主哈希与逆序处理，语义复杂且容易误导（"还原失败"多半是用户已经把文件转发过）。当前版本只在 CLI 提供 `sth restore`。

**Q20. 输出文件已存在会覆盖吗？**
CLI 默认拒绝，报 `Refusing to overwrite existing file`，除非 `--overwrite`。桌面端不覆盖，自动加后缀或提示换目录。

## 平台与安装

**Q21. Windows 提示"Windows 保护了你的电脑"，macOS 说"无法验证开发者"。**
产物未做代码签名。绕过步骤见 [INSTALL.md](../INSTALL.md) §1。需要可验证来源就自己从源码构建。

**Q22. Linux 版是静态的吗？需要 glibc 吗？**
发布页的 Linux 产物是 musl 静态链接，不依赖 glibc；但如果从 `noexec` 挂载点（常见于 `/tmp`）运行会报 `Permission denied`，装到 `~/.local/bin` 即可。

**Q23. 有手机端 / 网页版吗？**
没有。仓库只有 CLI（`rust/`）与桌面端（`gui/`，Tauri 2）。

**Q24. 支持哪些格式？**
以当前构建为准：`sth list`（或 `sth list --json`）会列出这个版本支持的载体、策略、算法与容量上限。不要照文档里的清单硬记，格式支持随 feature 组合变化。

## 合法性与边界

**Q25. 我用它做 XX 合法吗？**
项目不做背书也不做限制，但明确列出了不接受的使用方式（非法内容、绕过 DRM、干扰取证、篡改你无权修改的文件）。见 [LEGAL.md](../LEGAL.md) §2。涉及 HEVC 的分发还要看专利提示（同文件 §4）。
