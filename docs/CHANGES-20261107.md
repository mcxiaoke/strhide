- **矩阵**：结构域 9 载体 × 5 档（4K/64K/256K/1M/4M）= 45 格；内容域按「格式 × 算法」全量展开 11 场景 × 4 档 = 40 格（PNG：HILL/S-UNIWARD/MiPOD；JPEG：UERD/J-UNIWARD/J-MiPOD；HEVC-MP4、HEIC、WAV；FLAC 21 MiB 三档 + 58 MiB 128 KiB 补测）。另含 KDF 拆分、文件 API I/O、可压缩载荷三组对照。
- **实测发现（仅记录，未改任何库代码）**：
  - 结构域 9 个载体一致出现「1 MiB 写入比 4 MiB 慢 5–9 ms」，原因是 `src/core/crypto.rs` 的 `COMPRESSION_PROBE_MIN_BYTES = 1 MiB`：`<=` 阈值走整段 Deflate，`>` 阈值只做 256 KiB 分层采样；建议列为已知优化项。
  - 结构域小载荷耗时由 PBKDF2（100 000 次，约 20 ms）主导，载荷每增 1 MiB 仅 +3 ms 左右。
  - WebP 全部回退 `eof`，PE 全部落到 `pe_overlay`；JPEG APP15 可承载 4 MiB（引擎拆多段）。
  - 内容域瓶颈不是 PBKDF2（200 000 次仅 13–20 ms，在 0.5–6 s 引擎耗时中被稀释），而是代价图与整码流重编码；KDF 拆分结论与方案预期相反。
  - HEVC 3.3 s 短片 128 KiB 在 High 档被槽位预算硬拒，按方案自动降 Balanced 测量；FLAC 128 KiB 需换 58 MiB 载体（占用物理上限 92%），单次嵌入 14.6 s。
  - **FLAC 慢的归因（报告 §5.6）**：不是容器比 HEVC 复杂，而是 `embed_flac` 每次嵌入做 5 遍全量 FLAC 解码（校验扫描 / 选槽 / 重建 CRC+MD5 / 漂移对比 / CRC 复检）、提取 2 遍，解码器为纯 Rust 无原生加速；同音频转 WAV 后嵌入快 13×（6.76 s → 0.52 s）。且报告里的 FLAC 是 240.5 s 音频、HEVC 只有 3.298 s，按时长归一化 HEVC 反而贵 22.5×。
- **验证**：`cargo build --release --all-features --example perf_bench`；`rustfmt --edition 2024 examples/perf_bench.rs` + `cargo fmt --check`；`cargo clippy --all-targets --all-features -- -D warnings`（本次返工修掉 9 项 clippy 告警，含 `collapsible_if` / `manual_is_multiple_of` / `field_reassign_with_default`）；`cargo test --all-features --all-targets`；`python scripts/import_lint.py` OK；冒烟 `perf_bench --domain structure --only zip --reps 2` 全绿。**未改动任何库代码**，字节级基线不受影响。

  - `ln`：`frexp` + 尾数归一到 `[√2/2, √2)` + `2·atanh` 级数到 `z^10/21`；
  - `ln_1p`：`|x|<2^-4` 走 12 项级数，否则回落 `ln(1+x)`；
  - `cos`：三词 `π/2` 归约（首词 33 位，`n·hi` 精确）+ 象限选择 + `r^16`/`r^17` 多项式。
  - 精度约 1 ulp（对比 libm 的测试容差 8e-16）；四组输出摘要固定为常量，改动即测试变红。
- **接入点**：`spatial_variance` 的 DCT 基（`cos`），`cost_calibration` 的 Newton 求解、熵计算、`ln` 分箱与插值表。HILL/S-UNIWARD 不受影响（它们本就不用超越函数）。
- **跨语言对照**：新增 `scripts/detmath/detmath.py` 与 `detmath.go`，同样四个摘要：
  - Rust（Windows/MSVC、Ubuntu/glibc）、Python（同两平台）、Go（Windows/amd64）**四组全部一致**；
  - `cost_vectors_check.py` 改为使用该 Python 实现，五段代价摘要与 Rust 逐一相同。
- **影响面**：`variance`/`fisher`/`smoothed` 三段摘要变了（libm → 自带实现），**`cost` 段摘要与 28 例字节基线完全不变**——量化把那点差异吸收掉了，等于零字节影响。
- **性能**：800×800 RGB，`hill` 227 ms、`mipod` 323 ms（`mipod` 含 32769 项插值表的 Newton 求解），无可感知退化。
- **未验证**：ARM 未实测；arm64 上 Go 可能把 `a*b + c` 融合成 FMA，需显式禁止后才谈逐位一致（已写进文档 §13.11.5 的"未验证"条目）。
- **文档**：`WIRE_SPEC_CONTENT.md` 新增 §13.11.5（做法、精度、三语言自检命令、已验证/未验证边界），附录 A.3 补一行指向两份移植。

## 2026-11-07 00:25:41 — 第二实现验证：Python 能读出 Rust 写的 PNG 载体

- **目的**：回答"规范够不够写出一个读取器"，并给出可运行的证据，而不是只做断言。
- **新增 `scripts/spec_extract_png.py`**（只读实现，不复用任何 Rust 代码）：PNG 解码（8-bit/非隔行/filter 0–4）、`pre_salt`、L1/L2/L3、ChaCha12（带 KAT 自检）、前缀/整段 Fisher–Yates、HILL 代价图与候选排序、STC 列向量与 syndrome、AEAD AAD 与微头解析。MiPOD 直接复用 `cost_vectors_check.py` 的管线（那部分本来就有逐段向量兜底）。

  - **同一份载体 → Python 在 Ubuntu/glibc 读出**（跨语言 + 跨 libm）；

## 2026-11-07 00:13:35 — MiPOD 代价管线跨实现向量（Rust ⇄ Python）

- **目的**：字节比对只能说明"最后不一致"，说不出是哪一步。MiPOD 的代价管线补一组**逐阶段摘要**，用来回答"另一个语言的实现是否对齐"以及"这次重构是哪一段动了"。
- **新增 `docs/api/cost-vectors.json`**：固定输入（32×32 RGB，`pixel & 0xF8` 亮度 → `σ²` → `2/σ⁴` → 7×7 盒滤波 → 量化代价）+ 五段 FNV-1a 摘要 + 前 4 个代价的位模式。像素以 hex 内联，任何语言可复算，不依赖图像解码器。
- **Rust 侧**（`stego/png/cost/mipod.rs` 的 `vectors` 测试）：重算五段并与常量摘要比对；`STHIDE_WRITE_COST_VECTOR=1` 时重新生成 JSON。摘要一旦漂移，测试直接报错并指出重生成步骤。
- **Python 侧**（`scripts/cost_vectors_check.py`，新增）：仅用标准库独立实现整条管线（镜像填充、DCT-II 余弦基、Wiener 残差、补空间能量、盒滤波、`ln`/`exp`/Newton 标定、尾数截断），逐段打印 Rust/Python 摘要对照，并给出"分叉发生在哪一段"的提示。运行 0.3 秒。
- **实测**：
  - Windows（Python 3.x / UCRT）：五段**全部逐位相同**；
  - Linux/glibc（Ubuntu 22.04，Python 3.10）：同样五段**全部逐位相同**；
  - Rust 侧在 Linux 上跑 `--lib cost_vector` 也通过（用 Windows 生成的常量），说明这组向量在两个平台、两种语言下一致，可以安全进 CI。
- **文档**：`WIRE_SPEC_CONTENT.md` 新增附录 A.3（向量文件、脚本、阶段定义、用法），§13.11.4 末尾加了指回该向量的说明。
- **验收**：`cargo fmt --all`；`clippy --all-targets --all-features -- -D warnings`；`cargo test --all-features --all-targets`（31 个测试二进制全绿）；`cargo test --lib cost_vector` 在本机与 Linux 均通过；`python scripts/cost_vectors_check.py` 两平台均 PASS。
