## 2. 重新分级标准

不沿用原报告的 P0–P3。分档公式：

> **优先级 = 危害 × 可达性 ÷ 修复成本**

危害权重（高→低）：
1. 不可逆破坏用户数据 / 嵌入成功但永久读不出；
2. 静默失效（用户以为成功）；
3. 安全语义缺陷（认证、nonce、密钥、验证绕过）；
4. 有界 DoS / 内存与耗时；
5. 可维护性、文档、测试资产。

可达性权重（高→低）：
1. 默认参数 / CLI / GUI 常规路径；
2. 非默认参数（显式算法、阈値、大文件、特殊格式）；
3. 库 API 特殊用法 / 构造输入。

分档：
- **P0**：默认或近默认路径即可造成不可逆数据损失或“成功但永久读不出”。
- **P1**：真实数据正确性/安全语义问题，需非默认参数或构造载体；或默认路径的显式自毁操作缺少护栏。
- **P2**：范围受限的静默失效、非默认参数下的正确性问题、有界资源放大、CI/基线完整性。
- **P3**：性能优化、健壮性收尾、文档/测试资产、调试期防御性断言。

## 3. P0（3 条）

### F-01 [P0] HEVC `Balanced` 小载荷：embed 成功但 extract/verify 永久读不出

- **来源**：A `P1-01` + B `D-03`（同一根因合并）。
- **判定**：`real`（两份报告分别静态推演 + 实测；本轮复核代码路径一致，未重跑 HEVC 实测）。
- **证据**：
  - `rust/src/stego/hevc/engine.rs:1217`：`target_slots = hdr_slots + desired_body_slots + 128`，**没有**下限钳制。
  - `rust/src/stego/hevc/engine.rs:1993-1998`：extract 第一阶段 `StopCondition::MinSlots(HEVC_SUPERBLOCK_POOL_SLOTS)`（常量 2048）。
  - `Balanced` 且 `HeifContainer` 时 `factor = 1.0`（`engine.rs:1209-1215`），小载荷的 `target_slots` 可远小于 2048；header 槽位按写入时的池规模分布，extract 按 2048 槽重扫，header 读取位置错位。
- **真实影响/触发**：`--algorithm balanced` + 小载荷 + HEIF/HEIC（或非 Heif 且 `non_ref_fraction` 较大）时，嵌入返回成功，但同参数提取失败；`verify` 也失败。用户的隐藏载荷实际不可取回。
- **原报告方案评估**：A 建议“抽统一 `target_slots` 函数并让 extract 用 min 容错”。统一函数方向正确，但让 extract 用 `min` 会改变旧载具的读取语义，且 extract 在读到 header 前不知道 `ext_len`，不能精确反推池大小。**不建议**让 extract 猜测；最小且确定的修法是让写入侧永远不低于读取侧的常量。
- **建议修法**：
  ```rust
  // engine.rs:1217
  let target_slots = (hdr_slots + desired_body_slots + 128)
      .max(HEVC_SUPERBLOCK_POOL_SLOTS);
  ```
  仅钳制下限，不动容量公式、不动 probe。若担心小载体被 `MaxSlots` 拒绝，改为 `max(MinSlots)` 后再走既有 `enforce_safety`。
- **成本**：S。
- **风险**：不改 wire 格式；但会改变 HEVC 小载荷的槽位布局与输出字节，`baseline_hash` 中相关 HEVC 用例需重建（项目未发布，可接受）。不影响已有载具读取（旧载具仍按原布局，extract 常量不变）。
- **验收**：`cargo test --all-features` 增加/启用 Balanced 小载荷 HEIF/MP4 roundtrip（embed → extract → 字节一致）；`hevc_stress` 全绿；`baseline_hash --check` 对非 HEVC 用例全绿。
- **状态**：**已修复**（commit `49fa875`）。实现为 `hevc_window_target_slots()` 下限；新增单测断言写/读 pool 一致，及 `--safety balanced` 小载荷多画面 roundtrip（`tests/assets/tiny40.hevc`）。实测：去掉下限时写 pool=656、读 pool=2048，读取必然失败；加下限后一致。`baseline_hash --check` 全绿，未重建基线。

### F-02 [P0] `restore` / `remove` 全链路不验证 AEAD，未认证 header 驱动切片与无界 `patch_offset`

- **来源**：B `D-01` + B `D-02`（同一根因“post-injection 坐标不在认证链内”，合并）。
- **判定**：`real`，但**严重度从报告 P0 下调为 P0 的边界**：攻击者只能影响本次 restore 的输出/临时文件与原地目标，不能写任意系统路径；`verify_restored` 在 rename 前执行，哈希不符会中止提交（`engine.rs:2256-2270`）。真正的缺陷是“用于比对的 `orig_host_size/sha256` 本身未认证”，因此 `verified_identical=true` 可被伪造。
- **证据**：
  - `rust/src/structure/engine.rs:2054-2086`：`remove_core` 只 `unpack_with_profile` + `validate_against`，**不调用** `decrypt_metadata`/任何 payload AEAD。
  - `rust/src/structure/envelope.rs:260-331`：`validate_against` 只校验长度加法、`offset_delta`、`patch_offset>=4`，**没有** `patch_offset+4 <= host_len`，也没有 `inject_offset+inject_size <= host_len`。
  - `rust/src/structure/envelope.rs:333-349`：AAD 固定 80 字节，注释明确 post-injection 四个坐标不认证。
  - `rust/src/structure/engine.rs:2256-2259`：`verify_restored` 用 header 中的未认证 `orig_host_sha256` 比对；`2270` 才 rename。
- **真实影响/触发**：构造/篡改一个结构域载体，把 `patch_offset` 设成接近 `u32::MAX`：restore 在临时文件上产生约 4 GiB 稀疏/实际写入再哈希；把 `orig_host_sha256` 改成攻击者期望输出的哈希，可让 `verified_identical=true` 成立。原地 restore 会覆盖原载体（是否有 `.bak` 取决于 CLI 选项）。
- **原报告方案评估**：B 建议“把这些字段纳入 AAD”。不可行/成本高：header 在 `inject()` **之前**已封包（`engine.rs:1305-1330`），而 `patch_offset/inject_offset` 是 inject 之后才知道；scattered 策略（`pe_codebits`）甚至在 inject 期间才写出最终字节。重做 AAD 会牵动所有 payload chunk 封包位置与 wire 字节，属于 L 级改造。
- **建议修法**（两步，均不改 wire）：
  1. **认证前置**：`remove_core` 在 `validate_against` 后调用一次 `decrypt_metadata`（或首个 payload chunk 的 AEAD 校验），用现有 AEAD 验证 header 前 80 字节 AAD（含 `orig_host_size/sha256`）。默认 secret 信封无需密码；加密信封本来就要密码。失败即 `CorruptedData`，不再进入 strip。
  2. **边界钳制**：给 `validate_against` 增加 `host_len` 参数，校验 `inject_offset+inject_size <= host_len`、`patch_offset+4 <= host_len`、`orig_patch_val` 为 4 字节字段不再额外约束。这样即使攻击者改坐标，也只会在合法范围内产生错误输出，随后被已认证哈希拒绝。
- **成本**：M（第 1 步需要把 `remove_core` 的 metadata 读取接上；第 2 步 S）。
- **风险**：不改 wire、不改公开 API（`validate_against` 是 crate 内）。**不重建 baseline**。注意：`remove` 对“无密码默认信封”必须仍能工作，不能要求密码。
- **验收**：新增测试：(a) `patch_offset = host_len+1` → `CorruptedData`，不生成大文件；(b) 篡改 `orig_host_sha256` → AEAD 校验失败；(c) 正常载具 restore 仍 bit-exact；`baseline_hash --check` 全绿。
- **状态**：**已修复**（commit `49fa875`）。`remove_core` 先 `open_authenticated_at`（metadata AEAD），`validate_against(ube_total_size, host_len)` 增加 `patch_offset+4 <= host_len`；注入区间改用已有 `envelope_coordinates_agree()` 校验物理边界（兼容 PNG chunk 位移，未破坏合法 restore）。负面用例覆盖伪造 digest、`patch_offset = u32::MAX-3/u32::MAX/host_len+100`、注入越界/溢出，全部在 rename 前被拒且载体不变。行为变化：加密信封 remove 现需密码（fixplan 已预期），对应 local/lifecycle 测试已同步。

### F-03 [P0] 跨域占用检测缺失：内容域二次嵌入静默覆盖；结构域叠在内容域上；双域复合导致 restore 必失败

- **判定**：`real`（XH-03/XH-08 为静默数据丢失；XH-02 的“原始文件永久丢失”仅在 `--no-backup` 的原地操作成立，属 `partial` 子项，但整体条目按 `real` 计）。

  - `rust/src/structure/engine.rs:2084-2085`：restore 只按结构域 strip；若 IDAT 已被内容域重编码，strip 出来的宿主哈希与写入时记录不一致，返回 `RestoreMismatch`（`engine.rs:2183-2189`）。

  3. 结构域写入前先探测内容域；内容域嵌入前先探测结构域信封；
  4. 不新增全局配置开关，复用现有 `--overwrite`。
- **成本**：M（编排层改造 + 轻量探测；若探测需密码，缺失密码时按“未知但疑似占用”要求显式确认）。

- **验收**：三次 `embed` 无 `--overwrite` → 第二次失败且第一次载荷仍可提取；`embed → structure write` 与反向 → 均失败；带 `--overwrite` → 行为明确且文档说明覆盖；双域复合在入口即被拒绝。
- **状态**：**已修复**（commit `49fa875`）。新增 `StrHide::ensure_domains_free()`（`facade.rs`，复用 `inspect_any`），CLI `embed`/`write` 在预检阶段调用；`structure` 与 `stego` 仍互不 import。测试覆盖内容二次嵌入、结构叠内容、内容叠结构三种拒绝与 `--overwrite` 放行；单域往返不变。

### F-04 [P1] 批量/单条 `read`/`extract` 的输出可覆盖同批输入载体

- **来源**：A `P1-02` + C `XH-05`（单命令 `read -o <同一载体>` 自毁），同一根因合并。
- **判定**：`real`。
- **证据**：

  - 批量模式预先把所有输入载体 canonical path 放入 `HashSet`，输出路径命中即拒绝；
  - GUI 侧调用点同样走该检查。
- **成本**：S。
- **风险**：不改 wire/API/基线。注意 `same_file` 对不存在的输出路径会回退字符串比较，需先规范化父目录。

- **状态**：**已修复**。新增 `core::commit::reject_carrier_output()`（复用 `same_file`，含相对路径/软链/Windows 大小写归一）；结构域 `write_payload_to(..., carrier_path)` 在计算最终输出名后、截断前拒绝；CLI `read` 批量分支与 `extract` 的三条输出分支同样在写前调用。未改 wire/API/基线。测试：`read -o ./carrier --overwrite`、`extract -o carrier --overwrite` 均被拒且载体 SHA-256 前后一致，随后载荷仍可提取。

### F-05 [P1] 结构域 `write` 成功、自检通过，但 `read` 因载荷上限永久失败；读取侧 64 MiB floor 允许有界解压放大

- **来源**：C `XH-01` + C `XH-07` + B `A-04`（同一 `structure_payload_limit` 机制）。
- **判定**：`real`（A-04 的子项为 `partial`：放大上限 64 MiB，且非密码信封才可伪造 metadata）。
- **证据**：
  - `rust/src/structure/engine.rs:1040-1065`：写入只做 deflate 选择，**没有** `raw_size > structure_payload_limit(carrier_len)` 拒绝。
  - `rust/src/structure/engine.rs:1795-1800`：`limit = carrier_len*256`，`clamp(64 MiB, 1 GiB)`。
  - `rust/src/structure/engine.rs:1821-1827`：读取在解密前检查 `raw_size`，超限报错。
  - `rust/src/structure/engine.rs:1381-1387`：写入后的自检只校验 `locate`，不校验 `read` 的载荷上限。
- **真实影响/触发**：小载体 + 高压缩比载荷（例如几 KiB 文本压缩后写入）可让 `raw_size` 超过 `max(carrier_len*256, 64 MiB)` 但小于 1 GiB；写入与 verify 通过，`read` 永久报“exceeds safe decompression limit”。此外，1 KiB 非密码载体可声明 64 MiB `raw_size` 并用公开默认密钥伪造 AEAD，读取时解压到 64 MiB（单文件有界，批量可叠加）。
- **原报告方案评估**：C 建议“写入侧按同一公式校验”。可用且最小；A-04 建议调低 floor，会误伤合法小载体大载荷场景，不建议无条件改。B 建议“把上限与压缩后大小绑定”，方向对但需改 metadata 语义。
- **建议修法**：
  1. `write_core` 在封包前加 `if payload_raw_bytes > structure_payload_limit(host_len) { Err }`（注意用**输出宿主长度**而不是输入长度）；
  2. 自检从 `locate` 升级为“轻量 `read` 校验”（只解密 metadata + 检查 `raw_size`，不读全 payload），防止未来公式再漂移；
  3. A-04 暂不修，文档标注“非密码信封的读取 Draining 上限为 64 MiB”；若威胁模型要求，单独把 `FLOOR` 降到 16 MiB（需评估合法用例）。
- **成本**：S（1+2）；A-04 另计 S。
- **风险**：不改 wire/API/基线。写入侧拒绝会使部分原本“能写不能读”的输入改为“不能写”，属于预期修复。
- **验收**：构造 `raw_size > limit` 的输入 → 写入直接失败且输出文件不存在；`raw_size == limit` 边界 → 写入成功且读取成功；`verify` 与 `read` 结论一致。
