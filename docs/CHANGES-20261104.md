### 2026-11-04 20:38:00 - HEVC 嵌入恢复片级早停（4 KiB 载荷峰值 6.8 GB → 129 MiB）

`0cd75d7`（PR D 跨 GOP 并行解码，2026-10-29 16:41）把 `38b16bd` 原本写在片循环里的 `if should_stop { break; }` 换成「16 GOP 并行 → `collect` → 再判停」。判停结果（最终窗口）没变，但瞬时驻留从 1 片变成 16 个 GOP 的记录表——4 KiB 载荷要 6.7 GB 的根因就在这。本批把片级早停装回去，同时保住大载荷的并行。

#### 代码
- `stego/hevc/engine.rs::decode_gop_slice_range`：新增 `slot_budget`，某批剩余目标达标即停解本 GOP 剩余片（这些片本来就会被 `truncate_to_slices` 丢掉）。
- `stego/hevc/engine.rs::record_carrier_state`：`StopCondition::TargetSlots` 的批次从 1 起按 2 倍爬升到 `EMBED_WINDOW_GOPS`；`All`（32）与 `MinSlots` 不变，`capacity --exact` 的并行度不受影响。
- `stego/hevc/engine.rs::estimate_embed_peak_bytes`：预检窗口同步改为「`80 × 载荷字节`或约 1 片 ＋最多一个批次的富余」，MKV/HEIF 另加 1× 改写副本（窗口瘦身后，那份 `carrier.to_vec()` 成了新的峰值）。
- `stego/io.rs`：拒绝消息改为报「约 X MiB 会被记录」而不是「前 16 个 GOP」；新增 `embed_peak_follows_the_payload_not_the_batch` 回归用例。

#### 实测（4 KiB 载荷，私有内存峰值 MiB）

| 高熵 104 MB MP4 | 6,759.4 | **129.4**（52×） |

### 2026-11-04 20:02:05 - 音频嵌入预检系数 4× 收到 2.5×（实测 2.0×）

`legacy_issues_plan_20261104.md` L-07 修订 A 的收尾。音频（WAV/FLAC）峰值实测就是「载体 + 一次重写副本」：

| 样本 | 大小 | 私有峰值 | 倍率 |
|---|---|---|---|
| WAV 48k/16bit/立体声 | 11.5 MB | 23.7 MiB | 2.06× |
| WAV 同上 | 96 MB | 185.2 MiB | 2.02× |
| WAV 同上 | 366 MB | 735.7 MiB | 2.01× |

#### 代码
- `stego/io.rs`：`WAV_PEAK_FACTOR`/`FLAC_PEAK_FACTOR = 4` 改为分数常量 `(5, 2)`，`whole_file_peak_bytes` 用整数乘除（`saturating_mul/div`），避免浮点。
- 单测：`whole_file_peak_covers_audio_but_not_matroska` 改断言新比例；`over_budget_audio_carrier_is_rejected_with_the_reason` 更新边界（450 MB 仍拒、400 MB 由「4× 下被拒」转为放行），把这次改动钉成回归。

#### 未做（留档）
WAV 峰值还能再降到 1×：`PcmCarrier::apply` 只把 1–4 字节写到已知偏移，可改走已有的 `commit_carrier_patches`（内核级 `fs::copy` + seek，零堆分配）；需要给 `EmbedOutput` 增加 patch 形态并补「patch 结果 == 原字节输出」的逐字节回归，列为独立批次。FLAC 残差是位打包，一次翻转会改变码字长度、`finalize` 可能重写，且校验依赖原始与结果的 PCM MD5/漂移，不建议同批 patch 化。

#### 验证
`cargo clippy --all-targets --all-features -- -D warnings` 无告警；`cargo test --all-features --all-targets` 全绿；`baseline_hash --check` 28/28（基线不含音频样本，音频由 `stego::audio` 单测与往返用例覆盖）。

### 2026-11-04 19:52:37 - HEVC 嵌入内存预检改为窗口口径（修长片误拒、补 MP4 缺口）

`legacy_issues_plan_20261104.md` L-07 阶段一的 `file_size × 64` 口径把「与 16-GOP 记录窗口相关的量」当成「与整文件相关的量」，24 分钟片被高估 11.7 倍（429.5 MB MKV 报 26,279.7 MiB，实测 2,242.6 MiB）；同时 MP4/AnnexB 完全没有预检。本批把预检改为窗口口径并统一入口。

#### 内存模型（实测）
峰值由 `record_carrier_state` 的批处理决定：`StopCondition::TargetSlots` 每批 `16` 个 GOP，`par_iter().collect()` 先把整批记录表同时留在内存，之后才合并/判停/截断窗口。插桩实测高熵 40s 样本：每 GOP 槽位表 356 MB + bin 日志 399 MB，合并后实际只保留 1 片 / 11.7 万槽位（约 2 MB）。拟合公式 `峰值 ≈ 70 B × 窗口字节 + 1×文件 + 64 MiB`。容器不是变量：同内容 MP4/MKV 六组差值 ≤6%，MKV 的 `carrier.to_vec()` 在批次之后，不在峰值路径上。

#### 代码
- `stego/hevc/engine.rs`：新增 `EMBED_WINDOW_GOPS = 16` 并替换批大小字面量；把容器/片跨度解析抽成 `parse_carrier_layout`，供 `record_carrier_state` 与新估算共用，避免两套解析各说各话；新增 `embed_window_bytes` / `estimate_embed_peak_bytes`（窗口 = 前 16 个 GOP 的 VCL 跨度，大载荷按目标槽位抬到整文件）。
- `stego/io.rs`：删除 `MKV_PEAK_FACTOR`；`check_buffered_embed_budget` 拆成 `check_carrier_fits_budget`（读前、任意格式、只拦「连 1× 都放不下」）与 `check_hevc_embed_budget`（读后解码前，覆盖 MP4/MKV/AnnexB/HEIF）；新增 `read_carrier_for_embed` 作为唯一「读取 + 预检」入口。WAV/FLAC 保持整文件 4×。
- `cli/cmd_stego.rs`：`--dry-run` 改用 `read_carrier_for_embed`，与真实写入共用同一预检。
- `stego/hevc/mod.rs`：导出 `EMBED_WINDOW_GOPS`、`EmbedPeakEstimate`、`embed_window_bytes`、`estimate_embed_peak_bytes`。

- `stego/audio/flac/mod.rs` `parse_stream_info`：强制 STREAMINFO 为首个 metadata block 且长度恰为 34，其余位置出现 `block_type == 0` 一律 `CorruptedData`。此前畸形文件可让 `refresh_checksums` 把新 MD5 写进首块 payload，真 STREAMINFO 的 MD5 仍是旧值 → embed 成功、extract 永久失败。
- 新增 `streaminfo_must_be_the_first_metadata_block`（非首块 + 长度 33 两种拒绝用例）。

#### P1-9（读端）PNG 完全不校验 chunk CRC

- `stego/png/engine.rs` `decode_png`：每个 chunk 在分派前用 `crc32fast::hash(ty || body)` 比对存储的 CRC，不匹配返回 `CorruptedData`（带 chunk 类型与偏移）。`png_pre_salt` 把 `ty`/`data` 混入 KDF salt，CRC 错误的载体原本会派生出另一套 locator key，输出"CRC 被悄悄修复但身份已变"的文件。
- 写出端 `write_chunk` 本就按同一 `ty || body` 重算 CRC，合法载体仍逐字节往返；已实测 `testdata` 全部 PNG 的 chunk CRC 合法。
- 新增 `decode_rejects_a_chunk_whose_crc_no_longer_matches`（翻转 IDAT 一个 bit、CRC 不动 → 必须拒绝）。

#### P1-6 release 构建跳过 patch 后带 CRC 的整体复核

- `stego/audio/flac/mod.rs` `refresh_checksums`：删除 `#[cfg(debug_assertions)]`，release 也执行一次带 `verify_crc = true` 的 `analyse` 并比对 PCM MD5。原注释"verified from the exact same decoded samples"是循环论证：CRC 与 MD5 都出自 `verify_crc = false` 的同一次解码，失步时错误样本的校验值自洽。代价是 release 下 embed 多一次全量解码。

#### P1-8 `Err(_)` 吞掉取消 / 凭据 / IO 错误并静默改走另一套引擎

- `stego/engine.rs` 新增 `should_try_bridge(&StrHideError) -> bool`（feature `content-hevc`）：只对 `NoHiddenData` / `UnsupportedFormat` / `TrellisInfeasible` 允许回退到 HEIF 缩略图 bridge；`Cancelled`、`Io`、`Password*`、`SafetyThreshold`、`CorruptedData`、`UnsupportedVersion`、`General` 原样透传。
- `hevc_embed` / `hevc_extract`：`resolve_credential` 从闭包内提到函数开头用 `?` 提前返回，凭据冲突不再可能被 bridge 的错误覆盖；原来单独的 `SafetyThreshold` 特判由 `should_try_bridge` 统一承担。
- `hevc_probe`：`Err(_)` 分支加同一道门；embed / probe 仍保留 `HevcMode::Cabac` 的"禁止回退"判定。
- 新增 `only_a_not_a_scheme_c_carrier_may_fall_back_to_the_bridge`。
