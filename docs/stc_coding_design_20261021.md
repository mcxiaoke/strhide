# STC（综合征网格码）编码层设计与实施计划

> **编制时间**：2026-10-21 00:0x（本机时间见文件末尾）

> **适用对象**：`rust/src/stego/`（PNG 空间域 + JPEG DCT 域共用的编码层）。
> **前置状态**：P1-b（PNG 三元 ±1）已落地（commit `cd177e4`），本文所有设计都以"类内 ±1 + 非对称代价"为输入前提。

## 1. 结论先行

1. **STC 的价值不在"能藏更多"，在"同样的改动预算下少改、且改在更便宜的位置"**。
   当前 `(7,3)` 汉明是固定分块、块内位置由综合症强制决定；STC 是全序列最优（Viterbi），
   能把"改哪个"和"改多少"一起优化。
2. **有一个必须先讲清的语义问题**：STC 的码率**不是**旋钮，而是由"元素数 n 与消息位数 m 的关系"决定。
   带状校验矩阵 `H` 的列宽为 `h` 时，独立综合症位数为 `n - h + 1`，所以 **`n ≈ m + h - 1` 是 STC 的"满速"用法**；
   想降低每元素承载率只能**多给元素**（`n = m / R`），但那会让"独立综合症位"多出来用不上。
   实务做法（Filler 工具箱同款）：**先按成本挑最便宜的 `n = m + h - 1` 个元素**，码率相对于这 n 个元素 ≈ 1，
   每元素改动概率升高、但被改元素是"最便宜的"，**加权失真**反而下降。这一点决定了容量口径必须改，见 §5。
3. **不建议一上来就替换默认编码**。实施顺序：新增 `stc.rs`（穷举对拍验证）→ 以参数灰度（默认仍是 Hamming）
   → 用 `batch_stego` 实测"加权失真/检测分数/耗时"三项 → 三项都优于 Hamming 再翻默认。
4. **性能是硬门槛**：`h=10` 时状态数 512、`n` 按 60 万量级估算约 10^9 次转移，纯 Rust 单线程需数秒；
   `h=8`（128 状态）约 2×10^8 次，约 1 秒量级。首发建议 `h=8` 并把 `h` 做成参数。

## 2. 现状与差距（编码层）

| 维度 | 当前（Hamming k=3） | STC |
|---|---|---|
| 分块 | 固定 7 个槽一桶，桶边界与代价无关 | 全序列一次 Viterbi，无分块边界损耗 |
| 改动率 | `(7/8)/3 = 0.2917` 次/bit | 同载荷下由代价分布决定，实测目标 ≤ 0.22 |
| 湿槽 | 无（非法方向只是"不允许"，不参与优化） | 原生：`ρ = ∞` 即湿槽 |
| 每槽一字 | 二进制（0/1） | 三进制（`{−1,0,+1}`），与 P1-b 的写入门控天然匹配 |
| 块尾 | 不足 7 个槽时退化为 1:1 裸写 | 无块尾概念 |
| 复杂度 | O(n) | O(n · 2^(h−1) · 3) |

## 3. 算法（可直接实现的形式）

### 3.1 校验矩阵与综合症

- 由密钥派生 `h` 位行向量 `ĥ ∈ {0,1}^h`（`h` 建议 7–10）。
- `H` 为 `(n − h + 1) × n` 带状矩阵：`H[i][j] = ĥ[i − j]`（`0 ≤ i − j ≤ h − 1`），其余为 0。
- 综合症 `s = H x`（模 2），`x` 是各槽的 LSB 向量；**`s` 就是消息位**。
- 提取端：`m = H x_stego` —— 只需重算 `x` 的 LSB 与 `H` 的异或和，**不需要代价图**。

### 3.2 嵌入（Viterbi）

按列 `j = 0..n−1` 推进，状态 = "尚未定稿的 `h−1` 行综合症位的异或累积"（`2^(h−1)` 个状态）。

对每个状态 × 每个候选 `x_j ∈ {y_j−1, y_j, y_j+1}`（受 `Move` 合法性约束）：

1. 把 `x_j` 的贡献 `ĥ` 异或进状态（左移后按 `h` 位掩码）；
2. 定稿最老的一位（第 `j − h + 2` 行）：若与目标消息位不等，该转移非法；
3. 累加该候选的失真：`x_j == y_j` 记 0，否则记 `ρ_+` 或 `ρ_−`（`Move` 不允许的方向记 `∞`）。

走完所有列后，取剩余 `h−1` 位等于目标消息尾部的终态，回溯得到 `x`。
回溯只需每列每状态 1 bit（选的是哪个前驱），内存 `n · 2^(h−1)` bits（`n=60万, h=8` → 9.6 MB）。

### 3.3 失真与湿槽

- `ρ_±` 直接复用 P1-b 的 `direction_costs`（HILL 的"向邻域均值移动更便宜"）；
- 非法方向（类底不能 −1、类顶不能 +1）记 `ρ = ∞`，等价于"该三元选项不存在"；
- 若某槽三个选项都非法（理论上不会：可嵌入值域已保证至少一个方向合法），Viterbi 自然把它当湿槽跳过。

### 3.4 密钥化

`ĥ` 由 `password + salt` 派生（与现有 `derive_keys` 同源，域分隔加 `b"strhide-stc-h"`）：
`ĥ` 公开等于把校验矩阵交给攻击者，会显著降低安全性；**必须与 payload 密钥一样保密**。
无密码模式沿用 `Profile::stego.default_secret`（私有方言自动生效）。

## 4. 与现有引擎的衔接

### 4.1 输入（两端一致性要求）

STC **唯一**对两端一致性的要求是：**同一组槽位、同一个顺序、同一个 `ĥ`**。
代价图只在嵌入端使用，因此：

- 槽位集合与排序仍走现有逻辑（可嵌入值域 → 按 `cost` 排序 → 剔除最平滑 `exclusion` → 头部 256 槽密钥化置换 → 正文取最便宜 N 槽 → salt 置换）；
- 代价图必须两端逐位一致（P1-b 已用 `val & 0xF8` 掩码保证），这条不变；
- `ĥ` 与槽位顺序无关，只依赖 `password + salt`。

### 4.2 需要改的接口

```rust
// rust/src/stego/coding/stc.rs
pub struct StcTrellis {
    /// 校验矩阵行向量，长度 = h。
    pub h: u8,
    pub pattern: u32, // 低 h 位有效
}

impl StcTrellis {
    /// 由密钥材料派生（同 salt 必须得到同一 trellis）。
    pub fn from_key(secret: &str, salt: &[u8], h: u8) -> Self;

    /// 嵌入：n = vals.len()，消息位数必须 == n - h + 1。
    pub fn embed(
        &self,
        vals: &mut [u8],
        moves: &[Move],
        rho_plus: &[f64],
        rho_minus: &[f64],
        message: &[u8],
    ) -> Result<usize, StrHideError>;

    /// 提取：返回 n - h + 1 位消息（打包成字节，末字节高位补 0）。
    pub fn extract(&self, vals: &[u8], message_bits: usize) -> Vec<u8>;
}
```

`SpatialParams` 增加 `codec: StegoCodec`（`Hamming` 默认 / `Stc { h: u8 }`），
`JpegParams` 同样字段；CLI 增加 `--codec hamming|stc --stc-h <7..10>`，
配置文件键同名。提取端必须与写入端一致，**因此 codec 与 h 必须随参数一起落盘或由用户显式指定**——
这正是评审 P0-7"参数指纹不可达"的残留风险，STC 落地时应在信封头部 1B 里登记 codec（见 §7）。

## 5. 容量语义：本节初稿的论断是错的，实施后已更正

> **更正说明（实施后回写）**：本节初稿主张"给 STC 多分配槽位（`n = 2.33·bits`）并把多余综合症位填 0，
> 从而保持容量口径不变"。这个方案是**错的**：填 0 的那些位仍然是 `Hx = m` 的约束，
> 2.33 倍的独立综合症位等于让编码器解一个 2.33 倍大的问题，改动数会按比例上升，
> 比"只用 `n = m + h − 1` 个最便宜元素"严格更差。带状矩阵 `H` 的容量是**确定的**：
> `m = n − h + 1`，没有"在同一组元素上降码率"的自由度（真要降码率需把 `u` 列合进一个
> 网格步进，即 `rows = n/u`，属后续项，见 §11）。

### 5.1 实际结论

1. **STC 的每 bit 槽位开销是 ~1，Hamming k=3 是 2.33**，所以同一批候选槽位上
   STC 的最大载荷确实是 Hamming 的 **2.33 倍**（实测 `Special11.png`：
   `--capacity` 由 16 825 B 变 39 285 B）。这不是"假容量"，是真实可达的。
2. 但**"能力变大"不等于"该填满"**：填满时改动数按比例上升，检测面同步上升
   （实测 `Special11.png` 在 84% 占用下 risk 25/100）。因此
   `probe_*_capacity` 的 `max_raw_payload_bytes` 按 codec 给**真值**，
   而 `recommended_max_bytes` 依旧是 `max/2` 不变。
3. `estimated_change_rate` 因此必须按 codec 报告：Hamming 0.2917、
   STC ~0.5（α≈1 时近半元素改变）。这个数字不好看，但它是真的，
   而且它是决定 STC 能否翻默认的关键证据之一（见 §8.5）。

> 一句话（修正版）：**STC 同时降低了加权失真、也提高了容量上限**，
> 代价是改动个数变多、且必须靠"只用最便宜元素"才换得到低失真——
> 填得越满，前一个优势越小。

## 6. 复杂度、内存与性能门槛

| h | 状态数 | 每列转移 | n=60万的总转移 | 预计耗时（Rust 单线程，release） | 回溯内存 |
|---:|---:|---:|---:|---:|---:|
| 7 | 64 | 3 | 1.2×10^8 | ~0.5 s | 4.8 MB |
| 8 | 128 | 3 | 2.3×10^8 | ~1 s | 9.6 MB |
| 10 | 512 | 3 | 9.2×10^8 | ~4 s | 38 MB |

验收门槛：**当前 release 嵌入 33 KB 载荷约 0.1 s**；STC 版本若 > 3 s，需先做内层循环优化
（状态数组用 `u16` 索引 + 定长数组、避免 `Vec` 逐元素边界检查、可选 rayon 按列分段无依赖处并行）。

`h` 上限 10（`2^10` 状态、38 MB 回溯位图）；`h < 7` 会显著削弱编码效率，不建议。

## 7. 参数登记（与评审 P0-7 的联动）——已用更小的改动解决

STC 的 `codec`/`h` 一旦与写入端不一致，提取必然失败（表现为 `NoHiddenData`），
而信封里没有算法位。初稿的方案是改 `strategy_id` 高 4 位，但那要动信封语义与
`MAX_KNOWN_STRATEGY_ID` 的判等逻辑。

**实际采用（零格式变更、向后兼容）**：内容隐写的 32 字节头部是
`[16B salt][12B nonce][4B 字]`，最后那个字原本就是信封长度，而信封长度受
64 MiB = 2^26 上限约束——**高 6 位恒为 0**。于是：

```
bit 26..28  codec（0 = Hamming，1 = STC）
bit 28..32  stc_h（0 = 未使用）
bit  0..26  信封长度（原语义不变）
```

好处：

- 头长度仍是 32 字节，线格式不变、无需版本位；
- 旧载体那 6 位天然是 0 → 解码成 `Hamming`，**无需任何迁移**，向后兼容是"构造出来的"而不是"补出来的"；
- 提取端不需要任何 flag，`--codec` 只出现在 `embed`；
- 不碰 `strategy_id`，P0-7 的结构域风险面不扩大。

解码失败的三种情况（codec id ≥ 2、STC 但 `h` 越界、长度越界）**全部折叠成同一句
`No valid payload found`**，否则会给出"信封存在但布局不对"的判别 oracle。

## 8. 验证方案（缺一不可）

1. **穷举对拍**（`coding/stc.rs` 单测）：`n ≤ 16`、`h ≤ 4` 时枚举全部 `3^n` 候选，
   求满足 `Hx = m` 的最小代价解，与 Viterbi 结果比较代价（允许并列解，比较代价而非具体解）；
   随机 200 组用例必须全部相等。
2. **往返**：`embed` 后 `extract` 必须逐位复现消息；`x` 的每个元素与 `y` 的差 ∈ {−1,0,+1} 且不离开八值类。
3. **湿槽**：`ρ = ∞` 的方向必须一次都不被选中（用刻意构造的代价验证）。
4. **端到端**：`batch_stego` 19 例（含拒绝用例）100% 还原；额外跑一次 `--codec stc` 的全语料回归。
5. **对比基准**（同一载荷、同一语料）：Hamming vs STC 的
   ① 改动数 ② `Σρ`（加权失真） ③ `scan` 分数 ④ 耗时。
   工具：`cargo run --release --example codec_bench -- <carrier.png> <payload> [password]`
   （产出 ①②④ 并写出两份 stego 文件，供 `strhide scan` 取 ③）。
6. **性能门槛**：33 KB 载荷 / 92 万像素载体 ≤ 3 s。

### 8.5 实测结果（2026-10-21，`h=8`，载荷 33 000 B 随机数据，密码 `P@ss!`）

语料 `temp/teststego` 只有 **3 个可用 PNG**（`Blueberry-Flat` 调色板、`s_hair_gre_3_mo1` APNG、
`shop5` 隔行，均被引擎按设计拒绝）。样本量偏薄，是本次**没有翻默认**的主要原因。

| 载体 | 改动数 H / S | `Σρ` H | `Σρ` S | 耗时 H / S (ms) | scan H | scan S |
|---|---:|---:|---:|---:|---:|---:|
| `DC912sk1` 960×960 | 77 216 / 131 945 | 1.14e10 | **2.78e7** | 298 / 369 | 25 LOW | **0 CLEAN** |
| `SSD20210218` 1608×990 | 77 175 / 131 569 | 3.47e11 | **1.70e11** | 239 / 307 | 2 | 27（原图即 27） |
| `ref_minimal_peach` 1920×1920 | 77 037 / 131 571 | **1.20e8** | 1.36e8 | 1276 / 1321 | 0 | 0 |

结论：

1. **加权失真**：STC 在 2/3 载体上大幅领先（408×、2.0×），在 1/3 上略差 12%
   （该图接近均匀噪声，成本图方差小，"挑便宜的"没有优势可捡）。
2. **改动数**：STC 稳定 **+71%**（0.5 次/bit vs 0.2917）。这是它的固有代价，不是实现缺陷。
3. **检测分数**：STC 从未更差。唯一"H 看起来更好"的 `SSD20210218` 是原图自身假阳性
   （risk 27 来自非标准 `iDOT` chunk），嵌入噪声把假阳性抹平，属噪声而非信号。
4. **耗时**：STC 是 Hamming 的 1.2–1.3 倍，最大载体 1.3 s，远低于 3 s 门槛。
5. **容量**：STC 的真上限是 2.33 倍（`Special11` 16.8 KB → 39.3 KB），已用 CLI 端到端验证。

**决策**：以 `--codec stc` opt-in 发布，**默认仍是 Hamming**。改动数 +71% 是用户可感知的
副作用（"你动了多少像素"），而 3 个载体不足以证明它在检测面上永不更差；翻默认需要更大的
PNG 语料，以及 `batch_stego` 在 STC 下的全量回归结果。

## 12. 分组网格：让 STC 真正降码率（`u > 1`）

### 12.1 结构

元素按 `u` 个一组切分，组 `g = j/u` 拥有综合症行 `g`；元素 `j` 的列向量 `cols[s]`（`s = j%u`）贡献到行 `g .. g+h-1`：

```text
s[g] = XOR_{d=0..h-1} cols[s][d] & x[g*u + s]
```

- 每行被 `h` 个组 = `h·u` 个元素影响，`h` 行窗重叠。
- `message_bits(n) = n/u − (h−1)`，`slots_for(bits) = u·(bits + h − 1)`；`u = 1` 退化为原来的 `n − h + 1`。
- 组内 `u` 个列向量由 seed 派生后做 **GF(2) 线性无关校验**（`u <= h` 才可能）。若组内向量相关，`u` 个元素在综合症上的自由度会坍缩成一个 XOR，"每组 1 位"的容量实际上拿不到。
- 每个向量的最低位与最高位仍强制为 1（理由同 §3.1）。最低位这里是"本组即将定稿的那一行"。

### 12.2 状态与实现

状态 = `h−1` 位（行 `g .. g+h−2`）＋（`u > 1` 时）1 位 extra（行 `g+h−1`，组内剩余元素还在往里加）。组内最后一个元素处理完时定稿行 `g`：检查 `st & 1 == want`，然后整体右移一位、把 extra 送进最高位。

`u = 1` 时 extra 在列内即时并入，状态仍是 `2^(h−1)`，转移结构与旧实现**逐位同构**（这是为什么 u=1 的性能没有因为加入分组而翻倍）。

复杂度与 `u` 无关：仍是 `O(n · 2^(h-1+[u>1]) · 2)`，回溯内存 `n · 2^(h-1+[u>1])` bits。实测 `u=2` 在 1920×1920 上 1.53 s（Hamming 1.32 s），`u=3` 2.19 s，仍在 3 s 门槛内。

### 12.3 顺带修掉的 warm-up 回溯缺陷（既有实现）

旧实现的 Viterbi 在 `row = j−(h−1) < 0` 时**跳过约束检查**（`want` 记 0 但不比对），而回溯时却用 `want` 反推前一状态：

```text
st1 = ((new_state & (2^(h-2)−1)) << 1) | want
```

只要前置检查成立（`(st ^ c_low) & 1 == want`），这个反推就精确可逆；warm-up 行不检查时，若某列翻转导致 `(st ^ c_low) & 1 == 1`，反推会强行把该位当 0，路径从此偏离，写出**提取不出来的 stego**。

- 触发条件：warm-up 的 `h−1` 列中任一次翻转。
- 为什么没早发现：warm-up 行不携带信息，Viterbi 没有理由主动翻转（翻转只增加代价），所以真实载体上"恰好没翻"的概率不低；3 张语料的实测与 `batch_stego` 都没踩中。
- 修法：warm-up 行同样按 `want == 0` 约束（去掉 `row >= 0` 前置条件）。提取语义不变，**旧载体仍可读**（提取端从不读前 `h−1` 行）。

### 12.4 实测与结论修正

`examples/codec_bench.rs` 已扩展为 Hamming + STC `u=1/2/3` 四行。33 000 B 载荷、`h=8`、密码 `P@ss!`：

| 载体 | 指标 | Hamming | u=1 | u=2 | u=3 |
|---|---|---:|---:|---:|---:|
| `DC912sk1` 960×960（u=2 占 82% 槽位池） | 改动/bit | 0.2924 | 0.5009 | 0.3063 | 容量不足 |
| | `Σρ` | 1.123e10 | 3.28e7 | **2.85e7** | — |
| | scan | 25 LOW | 0 CLEAN | 0 CLEAN | — |
| `SSD20210218` 1608×990 | 改动/bit | 0.2923 | 0.5016 | 0.3679 | 容量不足 |
| | `Σρ` | 3.49e11 | 1.71e11 | **1.25e11** | — |
| `ref_minimal_peach` 1920×1920（u=2 占 16%） | 改动/bit | 0.2925 | 0.5004 | **0.2758** | **0.2276** |
| | `Σρ` | 1.236e8 | 1.142e8 | 1.230e8 | **1.049e8** |
| | 耗时 ms | 1321 | 1379 | 1534 | 2190 |

**结论（与初稿 §11.1 的差别）**：

1. 分组确实把"每 bit 改动数"从 0.50 压到 0.28/0.23，**在槽位充裕的载体上已经低于 Hamming k=3**（`ref_minimal_peach`：0.2758 / 0.2276 vs 0.2925）。
2. 但**不是"等容量下必然赢"**。`DC912sk1` 上 `u=2` 已占 82% 槽位池，改动率 0.3063 反而略高于 Hamming —— STC 的全部优势来自"挑最便宜的槽"，满载时无便宜槽可挑。
3. 离线仿真（`temp/stc_sim.py`，等槽位预算、n≈640–960、h=8/10）与上表一致：按容量插值到 `u ≈ 2.33` 时每槽改动约 0.15，仍高于 Hamming 的 0.126。**所以严格意义上的"等容量改动数优势"不存在**；真实可用的优势是"**当你愿意给更多槽位时，改动数和加权失真都下降**"，而 Hamming 的槽位率是固定的 2.33，多余槽位闲着。
4. `h` 从 8 提到 10 的边际收益只有 ~3%（0.3568 → 0.3441 flips/bit @ u=2），瓶颈不在 `h`，不必再加。

因此 `--stc-u` 的正确用法是：**载体容量明显大于载荷时取 2 或 3**；载荷接近容量时留在 1（或退回 Hamming）。

## 13. JPEG/UERD 接入

### 13.1 唯一方向约束

UERD 的代价图用 `|c| & !1` 计算块能量，这是为了让提取端在 stego 上重算代价图时**逐位一致**。因此 JPEG 上的 ±1 必须停在系数的 `(2k, 2k+1)` 对内：

| 系数 | 合法方向 | 结果 |
|---|---|---|
| `c > 0` 偶 | `+1` | `2k → 2k+1`，`|c|&!1` 不变 |
| `c > 0` 奇 | `−1` | `2k+1 → 2k` |
| `c < 0` 偶 | `−1` | `−2k → −(2k+1)` |
| `c < 0` 奇 | `+1` | `−(2k+1) → −2k` |

即每个系数**只有一个可翻转方向**，由 `coding::dct_move` 给出。这与空间域的"类底只能 +1、类顶只能 −1"是同一形状，因此 STC 与 Hamming 都能原样复用。

副作用：JPEG 上 STC 实际是二进制 STC（每元素 2 个候选而非 3 个），`ρ` 只有一个方向的值。这是格式决定的，不是实现取舍——真正的三向匹配会改变 `|c|&!1`，提取端代价图漂移，必失败。

### 13.2 parity 载体

系数是 `i16`，量级可超 255，而 `StcTrellis`/`hamming_embed_ternary` 工作在 `u8`。编码层其实只需要"奇偶性"和"能翻转"两件事，所以 body 传给编码层的是 **`{2,3}` 的 parity 载体**（`2 | lsb`）：

- `+1` 恒翻转 LSB（2↔3），不会溢出；
- `Keep` 保持奇偶性；
- 真实移动方向在写回时由 `dct_move(真实系数)` 决定，这也是唯一影响代价图的地方。

### 13.3 重构

`embed_jpeg` / `extract_jpeg` 原本各自复制了一份 60 行的槽位规划（成本排序 → 剔除 → header 置换 → 排除 header → body 候选）。现抽成 `plan_slots()`，embed/extract/probe 三处共用，并顺带让 `probe_jpeg_capacity` 与 `embed` 的候选集定义不可能再漂移。

头部布局与 PNG 完全一致（`stego/header.rs`），所以 `--codec stc --stc-u 2` 写出的 JPEG 与 PNG 用同一套解码逻辑，提取端不需要任何 flag。

## 14. 语料全量回归（`batch_stego`）

`batch_stego` 新增 `STRHIDE_STEGO_CODEC=hamming|stc|stc2|stc3` 开关（同时作用于 PNG 与 JPEG），四档全跑：

| codec | 往返还原 | 满载检出率 |
|---|---:|---:|
| Hamming | 19/19 | 87% |
| STC u=1 | 19/19 | 87% |
| STC u=2 | 19/19 | 80% |
| STC u=3 | 19/19 | 67% |

19 例含 4 例按设计拒绝（调色板 PNG、APNG、Adam7、Progressive JPEG），全部按预期拒绝。
满载检出率随 `u` 单调下降，这既是 §12.4 改动数结论的独立佐证，也是分组网格真正的卖点：**同样"填满容量"时，u=3 比 Hamming 难检出 20 个百分点**。

因此 `batch_stego` 的"满载检出率 ≥ 80%"门槛改为只对默认 codec 生效；非默认 codec 保留 50% 的"检测器未坍塌"下限，避免"藏得越好越算失败"。

## 15. 仍未做

1. **翻默认**：现在有 19 例语料回归与三档检出率，但缺"载荷/容量比 → 改动数"的曲线（本轮只有 3 个载体 × 2 个占用率的数据点），且 `u` 的默认值该不该跟着载荷自动定仍未定。
2. **`probe_carrier_capacity` 的建议值**：目前 `recommended_max_bytes` 仍是上限一半，与 `u` 无关。若 `u=3` 的上限本来就只有 Hamming 的 70%，"一半"的实际占用率会被动抬高，可能需要按 `u` 调整比例。
3. **自动选 `u`**：按"可用槽位 / 需要位数"自动取 `u = clamp(floor(slots/bits), 1, 3)` 更符合 §12.4 的结论，但会引入"提取端必须复算同一 `u`"的一致性问题；目前选择显式参数、`u` 写进头部，代价是用户要自己判断。
