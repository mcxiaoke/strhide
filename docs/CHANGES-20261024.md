**实测验证的关键事实**（全部经实验确认，非阅读推测）：

1. **`rust_h265` 已在 crates.io 发布** v0.1.0（月下载 115 911），许可证 `MIT OR Apache-2.0`

   系数元数据）**公开 API 全部不可得**。

   `cabac_tables::HEVC_CONTEXTS = 179`）。仅"TU 尺寸/系数坐标"因位于 `cu_tree` 私有函数

4. **CABAC 编码器归属 `oxideav-h265` 而非 `rust_h265`** —— 后者只有解码器。

### [2026-10-24 17:31:21] fix(hevc): EPB 冲突改为按 slot 精确禁用，修复整片封禁导致的 STC 不可行崩溃

**背景**：`hevc_matrix_bench` 在 IMG_7547.HEIC + payload-16k 上随机失败，报
`HEVC stego cannot resolve EPB conflict: Embedding infeasible: a group has no legal element`
并触发 `STATUS_STACK_BUFFER_OVERRUN` 崩溃。实测定位到真正机制：某个旁路符号位翻转把码字字节
`0x58` 变成 `0x00`，与其后的 `00 01` 组成 `00 00 01`，使 RBSP→NAL 的防竞争字节（EPB）多插入
一个 `0x03`，NAL 长度与载体 span 不再相等（36305 → 36306）。旧代码的对策是把**整个 slice**
（该例中 7805 次翻转、16 个 substream）拉黑重解；由于 STC 分组 `u=2`，整片封禁会让大量分组两个
元素同时非法，必然出现 “no legal element”，于是同一 bug 表现为“偶发失败”。

**改动**（`src/stego/hevc/engine.rs`）：
1. **禁止粒度从 slice 改为 slot**：`banned_slices: HashSet<usize>` 换成 `forbidden: Vec<bool>`
   （长度 = needed_slots），只把真正破坏 `00 00 xx<=3` 窗口的那几个 slot 代价置为 `INFINITY`，
   其余 slot 保持原失真代价，STC 始终可行。
2. **冲突检测等价于 NAL 长度**：EPB 插入是 `00 00 xx<=3` 窗口的纯函数，故直接逐字节比较翻转前后的
   窗口集合（`now_starts_epb != cover_starts_epb`），比只比 NAL 长度更强，可发现“删一个加一个”
   的长度不变型错位（那会破坏多 substream 的 entry point 偏移）。
3. **槽位反查**：新增 `encode_substream()`，在重编码时记录每次翻转旁路 bin 在码字中的
   `[bit_lo, bit_hi)` 位置，换算成 RBSP 字节区间（`SlotBitTrace`），把冲突窗口映射回具体 slot。
   因旁路 bin 只影响 1 bit，位置与翻转取值无关，故一次编码即可确定。
4. **重试策略**：最多 `MAX_EPB_ROUNDS = 6` 轮，搜索半径按 `8 << round` 递增；若窗口附近没有任何
