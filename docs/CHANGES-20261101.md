### 2026-11-01 19:40:00 - 内容域新增 FLAC 残差隐写引擎（content-audio 特性）

- **背景**：方案阶段三（`content_stego_mkv_hevc_wav_flac_plan_20261101.md`）。FLAC 是内容域唯一"压缩但无损"的载体：残差用 Rice 码存储，改一个残差只改一个采样，且码字宽度可以保持不变，因此能做到严格 Δ=0。该特性在 `content-audio` 下与 WAV 一起提供。
- **改动**：
  1. 新增 `rust/src/stego/audio/flac/`：
     - `bits.rs`：MSB-first 位读写器（绝对位偏移，跨字节）；
     - `frame.rs`：帧头解析（含 UTF-8 帧号、CRC-8）、四种预测器子帧解码（CONSTANT/VERBATIM/FIXED/LPC）、残差槽位收集、**预测器补偿链**、CRC-16、立体声去相关（left/side、right/side、mid/side）；
     - `mod.rs`：`STREAMINFO` 解析、整文件校验解码（PCM MD5 对账）、`FlacCarrier`（槽位抽象实现）、CRC-16 与 `STREAMINFO` MD5 刷新、`max_sample_drift`；
     - `e2e.rs`：内存内自建 FIXED-order-2 FLAC 载体做端到端测试（不依赖 `temp/`）。
  2. `formats/sniff.rs` 识别 `fLaC`；`capability.rs` 增加 `StegoKind::FlacResidual`；`params.rs` 增加 `flac_format()`；`engine.rs` 注册 `FlacEngine`。
  3. `stego/audio/core.rs` 新增 `Mapping::BodyPermuted`（头部槽位固定、正文按密钥置换）；`Move` 增加 `None`（不可移动槽位），STC 侧按"奇偶固定"处理。
  4. 安全档位沿用音频的"槽位修改百分比"语义。
- **关键设计（本轮实测推翻了原方案的两处假设）**：
  1. **单步补偿不够，必须整条链**。原方案设想"改残差 r_i 后同时改 r_{i+1} 抵消预测反应"。实测（`temp/flactest.flac`）这样做仍然把波形打散：修改率 92%、SNR 7.2 dB、`max|Δ|` 达数万。原因是预测窗是滑动的：改 x_j 会依次影响 x_{j+1}…x_{j+order}，只补一个位置等于把误差推迟一步。现改为对 `order` 个后继残差逐个补偿，补偿量按"把 x_j 平移 ±1 时的预测增量"精确求解（`predict_at` 支持任意滞后），补偿后波形与原始逐采样相同，只剩被移动的那一个采样。
  2. **槽位集合必须"只依赖合法移动不改变的量"**。提取端只能看到 stego 文件，因此槽位选择只能用 `k`、`u>>k` 桶、桶内可移动方向这类不变量；补偿链是否"塞得下"依赖残差值（会被写操作改变），只能用来否决**移动方向**（`Move::None`），不能用来否决槽位本身。
  3. **512 槽头部放在"子帧最后一个残差"**。头部位无法重定向，必须保证可写：子帧末尾残差没有后继，天然零补偿、`has_legal_move` 又是合法移动的不变量，所以头部槽位池（每个子帧 1 个）在两个端完全一致且必定可写。正文用 `Mapping::BodyPermuted` 打散，避免"安静段落挤满不可移动槽位"把 STC 的整组卡死。
  4. **不可行时换种子重试**（最多 4 次），否则安静段落会让同一份载体随机成败。
- **实测**（`temp/testaudio/ZerocreationGame - Child and the Wind.flac` 9.2 MB / 24-bit / 48 kHz，4 KiB 载荷）：
  - 文件长度完全不变（9,220,309 B）；`STREAMINFO` MD5 与 ffmpeg 解码 PCM 完全一致（外部可校验）；ffmpeg 解码零告警；
  - 5,568,000 个采样中 12,335 个改动（0.22%），`max|Δ| = 2`，SNR 139.5 dB；
  - 4 KiB 载荷写入 2.4 s、提取 1.5 s；错误口令返回 `NoHiddenData`；篡改帧 CRC 后提取被拒绝。
  - 16-bit 音乐样本（`12_Deep_Space_Pyramid.flac`）：修改率 0.021%、`max|Δ| = 2`、SNR 110.5 dB。
- **能力边界（已写入方案文档）**：
  - 容量 = 合格残差数 / (预测阶数 + 1)，且只有约一半在安静段落能补偿；8 MB 级 16-bit 音乐约 2.5–7 KiB 推荐容量；
  - 头部需要 512 个子帧末尾残差，太短的文件（约 25 秒以下立体声）会被明确拒绝；
  - 预测器过于激进（安静段落补偿塞不进 Rice 桶）的载体会在重试后给出可读原因，而不是产出坏文件。
- **验证**：`cargo test --all-features --lib` 449 通过；语料 `flac_corpus_validates` 16/16（解码 PCM 与 `STREAMINFO` MD5 逐字节一致）；`cargo fmt`、`cargo clippy --all-targets` 零告警；`baseline_hash.py --check` 58/58 不变。

  2. `HevcCarrierKind` 增加 `MkvContainer`；新增 `label()` / `has_hvcc_parameter_sets()` 收敛此前散落在 5 处的格式名 match 与容器判断（原 12 处 match 点减少到 8 处）。

  4. 新增 `MkvEngine`；`capability.rs` 让 MKV 同时具备结构域与内容域能力。
  5. **CRC-32 刷新**：实测样本的每个 `Cluster`/`Info`/`Tracks`/`Tags`/`Cues`/`SeekHead` 都带 `CRC-32`（0xBF），补丁后必须重算，否则 ffmpeg/mkvmerge 报 "CRC-32 mismatch"。实现中按元素逐一**探测字节序**（libavformat 写小端、mkvmerge 写大端），并只重写覆盖范围与改动区间相交的校验和；原本就失效的校验和保持原样（把它改成"有效"反而是更明显的痕迹）。
  6. 抽出 `HevcCarrierKind::label()`，把 5 处重复的格式名 match 合并。
- **实测**（`temp/testhevc/HDRSample.mkv` 2.7 MB，`temp/videosamples/TEST2__hevc_mkv_1080.mkv`）：
  - 文件长度完全不变；ffmpeg 解码零告警；
  - 9/9、7/7 个 CRC-32 在嵌入后依然有效（嵌入前也全部有效）；
  - 载荷往返一致；`TEST2__hevc_12bit.mkv`（RExt profile）与 `TEST2__h264_mkv_1080.mkv` 被明确拒绝并给出原因。
