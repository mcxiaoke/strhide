## 3. 关键改动说明

### 3.1 错误枚举是最高优先级的护栏

`StrHideError` 是库最核心的契约面：下游写 `match err { ... }` 是最常见用法，1.0 后新增一个
错误变体就会打断所有下游。改造成本很低——`#[non_exhaustive]` 只对下游 crate 生效，
crate 内 `kind()` / `category()` / `detail()` 三处穷举 `match` 不受影响；GUI 侧只有构造与
单模式匹配，没有穷举 `match`。

### 3.2 音频门面不对称（`StegoTuning::Audio`）

`content-audio` 早已完整支持 WAV PCM 与 FLAC 残差域，但公开门面只有 `Png` / `Jpeg` / `Hevc`
三臂。这是**现存功能不对称**，且 1.0 后再补变体就是 breaking change，所以在冻结前补齐。

`AudioParams` 目前是空结构体（与 `HevcParams` 同构）：音频引擎的容量、槽位顺序、漂移预算
全部由载体采样格式与安全档位推导，提取端不读代价模型，确实没有可调项。它的价值是预留
字段位，并让 `applicable_to` 能把音频域显式钉住。

### 3.3 为什么必须先补 builder 再加属性

`non_exhaustive` 对 struct 的约束是双向的：外部 crate 既不能用结构体字面量构造，也不能用
`..Default::default()` 补救。`DualOptions` 等 4 个类型此前只有字面量构造路径，B5 批次因此
跳过了它们。本批按「补 `new()`/`with_*` → 改调用点 → 加属性」的顺序执行，GUI 的
`commands/{diag,stego,batch}.rs` 与 `state.rs` 已全部迁移。

### 3.4 容量契约修复（不是纯文档问题）

`CORRECTIONS.md` F 节前两条都是"探测报得出、写入写不进"：

- `riff_chunk` 的 `capacity_bytes` 原为 `None`，引擎会填入自身载荷上限（最大 1 GiB），
  而 RIFF 的 `u32` 大小字段决定了接近 4 GiB 的载体实际只能再写几百字节。现在报
  `u32::MAX - declared_size - 8`，余量为 0 时直接标记不可用。
- WebP 的静态表（`reader = None`）无法区分 Extended / Simple Format，原先只报"支持
  `riff_chunk`"，不说适用范围。现在 note 明确为 "Extended Format (VP8X) only"。

普通载体上这些改动不改变任何数值：新值远大于引擎上限，`apply_engine_payload_limit` 取小值后
报告与写入字节都不变（基线 28/28 已验证）。

## 4. 故意不加护栏的类型（重要）

`rust/src` 中仍有 70 余个带 `pub` 字段的 struct 未标注 `#[non_exhaustive]`。**这不是遗漏**，
其中多数加上去会直接破坏既有用例：

| 类型 | 理由 |
| --- | --- |
| `PngFormatProfile` / `JpegFormatProfile` / `HevcFormatProfile` / `AudioFormatProfile` / `WireCipherProfile` / `HeaderLocatorKeys` / `GridRule` | **私有方言配方**。`docs/api/STEGO-API.md` §3 的定制示例就是 `const STEGO_PNG: PngFormatProfile = PngFormatProfile { .. }` 字面量；加 `non_exhaustive` 会让 crate 外无法这样构造，直接废掉核心用例 |
| `MagicPair` | 8 字节前后魔数是物理定型契约，不扩展（计划 §3.3 特例） |
| `ErrorDetail` | 已加（本批），此处仅说明其 serde 形状未变 |
| `cli/args.rs` 的 21 个 clap 结构体 | 模块已 `#[doc(hidden)]`，是解析内部结构，不构成库契约 |
| `EnvelopeHeader` / `UnpackSecrets` / `JpegSegment` / `TrailerCtx` / `FinalizeCtx` / `SpatialHeaderV4` / `Tlv` | 位于 `#[doc(hidden)]` 模块，属实现细节 |
| `Control` / `Payload` / `FileConfig` / `StegoConfig` | 外部仍有字面量构造点（tests、GUI），要加需先逐点迁移；当前各自都有 `none()` / `bytes()` / serde 入口，风险低，列为后续可选 |

**结论**：不要按"还剩多少个 struct 没加"这个数字去批量清理，会踩到方言配方和测试构造点。

## 5. 决策记录与剩余项

### 5.1 `StegoCapacityInfo.format` —— 已决策：保持 `String`

评审报告 P1-6 建议改成 `FileFormat`。实测后**不采纳**，理由：

- 该字段当前承载的是**人类可读载体描述**，不只是格式名。`rust/tests/local/local_media.rs:314`
  断言的值是 `"HEIF (JPEG Thumbnail Bridge)"`，`:410` 是 `"HEIF/HEVC"`；
- 强类型化会丢失这类信息，需要额外引入 `carrier_label: String` 才能保留；
- GUI 已经不再依赖该字符串做逻辑判断（`gui/src-tauri/src/commands/stego.rs:109` 的注释记录了
  此前用 `info.format` 比较导致的漂移，现改用 `tier_limits`）。

已在 `ARCHITECTURE.md` §9 写明：该字段是展示用字符串，**不要按枚举值匹配**，需要机器可读格式
请用 `FileFormat`、`formats::sniff::*` 或 `MediaInfo`；1.0 后保持 `String` 定型。

### 5.2 模块级 `pub(crate)` —— 已决策：保持 `doc(hidden)`

计划要求把 `structure::adapters`、`stego::{hevc,jpeg,png,coding,wavelet,...}` 从 `pub mod`
收紧为 `pub(crate) mod`。实际执行时走了折中路线：约 150 个**条目**下沉为 `pub(crate)`，
模块本身保留 `pub mod` + `#[doc(hidden)]`。

原因是硬约束：**42 个文件**（`rust/tests/**`、`rust/examples/**`，均为独立 crate）依赖这些
内部模块做白盒验证（`test_pe/codebits.rs` 12 处、`local_media.rs` 7 处、`test_media/hevc_stego.rs`
6 处等）。改成 `pub(crate)` 会让它们全部编译失败。

**最终决策**：不搬迁测试，保持 `doc(hidden)`，并在 `lib.rs` 的 crate 文档与
`ARCHITECTURE.md` §9 明确声明"`#[doc(hidden)]` 模块不属于 SemVer 稳定面，1.x 内可自由重构"。
语义上仍是 `pub`，但契约边界已经写清楚。

### 5.3 UBE 版本表述 —— 已决策：统一为 `UBE v2`

`structure/envelope.rs:59` 是 `CURRENT_VERSION: u8 = 0x02`，读侧 `version != 0x02` 直接拒绝。
此前文档写 "UBE v2.2"，容易被误读成"线格式有 2.0/2.1/2.2 三个版本、代码区分不了"。

**该 2.2 是文档修订号，不是线格式版本号**。线格式只有 `0x02` 一个值，不存在粒度不足的问题。
已把 22 处 `UBE v2.2` 统一为 `UBE v2`（含 `WIRE_SPEC_STRUCTURE.md` 的手写目录锚点），
源码注释同步；历史工程日志保留原样。

### 5.4 不适用：`cargo-semver-checks`

当前 crates.io 上 `strhide` 最高版本是 `0.6.0`，与本地 0.9.3 差异过大，跑 semver 检查只会
产生大量噪音。**1.0 发布之后**再把它接入 CI，用于约束 1.0.x → 1.1 的兼容性。

### 5.5 时间项：格式静默期

最近三次写侧/读侧不兼容变更：

| 日期 | 变更 |
| --- | --- |
| 2026-11-05 | `hvcC` 统一只保留 VPS/SPS/PPS，含 prefix SEI 的旧 MP4 载体不可读 |
| 2026-11-05 | STC 参数调整，55 处 `stego_sha256` 变化 |
| 2026-11-07 20:48 | PNG 派生盐改为只绑定关键块，旧规则嵌入的带辅助块文件不可读 |

建议至少观察 2–4 周零不兼容变更，再考虑打 `v1.0.0`。

### 5.6 CLI 程序名（已完成）

五个二进制共用同一套 clap 定义，`Cli` 的 `name` 是编译期常量 `"sth"`，导致
`strhide.exe --version` 输出 `sth 0.9.3`、`--help` 的 usage 写 `sth`、`--json` 的 `banner`
字段也固定为 `"sth …"`。这与 Release 产物名和 `rust/README.md` 的命令示例不一致
（而 11-08 新增的 `docs/CLI_GUIDE.md` 又全篇用 `sth`）。

改为从 `argv[0]` 的 `file_stem` 取程序名写入 `OnceLock`，供 clap 的 `name` / `bin_name`
与运行时 `banner()` 使用。实测 `strhide.exe --version` → `strhide 0.9.3 (…)`，
`sthc.exe` → `sthc 0.9.3 (…)`。

`docs/CLI_GUIDE.md` 的命令示例仍是 `sth`，需要产品侧确认主命令名后统一（本次未改）。
