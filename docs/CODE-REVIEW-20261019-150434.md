## 1. P1 级缺陷

### A-1 ｜ 发布流水线完全没有质量门禁：打 tag 即发布

- **位置**：`.github/workflows/crates.yml`、`.github/workflows/release.yml`
- **状态**：**已核实**

三个 workflow 中 `cargo test` / `cargo clippy` / `cargo fmt --check` / `cargo audit` **一次都没出现**（`rg -n "cargo (test|clippy|fmt)" .github` 零命中）。

具体后果：

1. **打 tag 即发布**：`crates.yml` 在 `push: tags: v*` 时直接 `cargo publish`，**不跑任何测试**；`release.yml` 同理，只 `cargo build --release --locked`。任何回归都会直接变成已发布产物（GitHub Release 二进制 + crates.io 包）。
2. **无格式/lint 门禁**：`cargo fmt` 与 `cargo clippy` 是 AGENTS.md 明文要求的提交前流程，但没有任何自动化强制。
3. **无依赖漏洞扫描**。
4. `rust/README.md` 提到的交叉编译目标（`x86_64/aarch64-unknown-linux-musl` 等）在 `release.yml` 里都覆盖了，这部分没问题；问题纯粹在于「构建前没有关卡」。

> 注：`python/` 已冻结，`python/tests/test_rust_cross_compat.py` 与 Rust 的分叉属预期，**不应**把它接回 CI 作为门禁——那等于要求一个冻结实现跟随主线迭代。

#### 修复建议

新增 `ci.yml`（`push` + `pull_request` 触发），并让两个发布 workflow `needs: rust`：

```yaml
jobs:
  rust:
    steps:
      - cargo fmt --all --check
      - cargo clippy --all-targets -- -D warnings
      - cargo test --locked --all-targets
      - cargo build --release --locked
      - cargo install cargo-audit && cargo audit
```

## 2. P2 级缺陷（均已复现）

### A-2 ｜ 写入权限探针检查的是「载体所在目录」而非「实际输出目录」，导致 `-o` 到可写位置被误拒

- **位置**：`rust/src/rejection.rs:263-303`（`run_all_rejection_checks(carrier_path)`），调用点 `engine.rs:521`
- **机制**：引擎把临时文件建在 `target_path`（即 `-o` 指定的输出）旁边（`engine.rs:761`），但权限探针却在**载体**的父目录创建 `.strhide_write_probe_<pid>`。两者不是同一个目录时，探针结论与真实写入位置无关。
- **复现**：

```
# 载体目录被 ACL 设为不可写，输出目录可写：
icacls rosrc /deny "<user>:(D,W)"
> strhide write -c rosrc\ro.png -t x -o review2\out2.png
[ERROR] Rejection error: No write permission on target directory
        'C:\...\rosrc': 拒绝访问。 (os error 5)          ← 拒绝了一个完全合法的操作
exit=1
```

- **影响**：从只读介质 / 只读挂载 / `C:\Program Files\...` 取载体、输出到用户目录的合法工作流被直接拒绝。反之，输出目录不可写时探针通过、直到 `File::create` 才失败（见 A-4）。
- **修复**：`run_all_rejection_checks` 增加 `target: &Path` 参数，探针建在 `target.parent()`；或更彻底地删掉探针，改为在真正创建 `.strhide.tmp` 失败时把 `io::Error` 包装成友好 `Rejection` 错误（顺带解决 A-4 与探针残留问题 A-10）。

### A-3 ｜ 配置文件里的 `hint` 会让 `write --stealth` 无条件硬失败

- **位置**：`rust/src/cli.rs:433`（`let hint = args.hint.clone().or_else(|| cfg.hint.clone());`）+ `engine.rs:490-494`
- **复现**：

```
# strhide.toml:  hint = "my usual one"
> strhide write -c b.png -t x --stealth -p pw123 --config hint.toml
[ERROR] Password hint is not supported in --stealth mode (stealth mode requires password to locate envelope).
exit=1

# 同样的命令去掉 --config：
[OK] Successfully embedded into 'b.png' ...                    ← 成功
```

- **影响**：用户本轮**没有**要求写提示，是配置默认值触发的互斥检查。错误文案把锅甩给 `--stealth`，用户会去排查密码/stealth 参数，想不到是配置文件。CLI 层已经知道 `stealth` 标志，完全可以在合并配置前就处理。
- **修复**：`handle_write` 中当 `stealth` 为真时忽略（或按显式 `--no-hint` 禁用）配置来源的 hint；并在 `--stealth` 与 `-H` 同时**显式**给出时报一条明确的互斥错误。

### A-4 ｜ `remove` 忽略配置项 `backup`，与 `write` 行为不对称

- **位置**：`rust/src/cli.rs:538`（`let backup = !args.no_backup;`）vs `cli.rs:435`（`let backup = !args.no_backup && cfg.backup.unwrap_or(true);`）
- **复现**：

```
# strhide.toml:  backup = false
> strhide write  -c a.png -t x  --config strhide.toml
files: a.png                                        ← 正确：配置生效，未产生 .bak

> strhide remove -c a.png      --config strhide.toml
files: a.png, a.png.bak                            ← 错误：配置被忽略，仍然备份
```

- **文档矛盾**：`rust/src/config.rs:19` 的注释明写 `backup = true  # write/remove: .bak backup default`，即配置**本应**对 remove 生效。实现漏了。
- **修复**：`cli.rs:538` 改为 `let backup = !args.no_backup && cfg.backup.unwrap_or(true);`，并补一条 CLI 级回归测试。

### A-5 ｜ `read` 用字符串切分从错误消息里回读密码提示，含 `'` 的提示被截断

- **位置**：`rust/src/cli.rs:475-483`
- **机制**：引擎把提示拼进错误文案 `"...Hint: '{h}'."`，CLI 再用 `split("Hint: '").nth(1).and_then(|s| s.rsplit('\'').nth(1))` 反解。提示本身含 `'` 时切分点错位。
- **复现**：

```
> strhide write -c h.png -t secret -p pw -H "Bob's usual one"
     Password Hint: 'Bob's usual one'.

> strhide read -c h.png --stdout
[INFO] Password hint: s usual one                ← 引擎文案是对的，CLI 解析错了
[ERROR] Password error: Password required ...
```

- **影响**：低成本但明确的用户可见错误。提示是用户自己写的任意文本，出现 `'`、`Hint: '` 等内容的概率不低。
- **修复**：把提示从错误消息里结构化传递出来。最小改动是 `handle_read` 先独立调一次 `inspect_carrier` 取 `password_hint`，不靠解析消息文本。注释里写着「Discriminate by error variant, not by message text」，实际却在解析 message text——注释与实现已经背离。

### A-6 ｜ Windows 控制台编码：CLI 输出 UTF-8 非 ASCII 字符，在中文系统控制台显示为乱码

- **位置**：`rust/src/adapters/mod.rs:75,141`（`≤`）、`rust/src/cli.rs:612` 与多处 `—`（em dash）、`rust/src/rejection.rs:99`（**整条中文消息**）
- **复现**：

```
> strhide list-strategies   （简体中文 Windows，控制台代码页 936）
Format   Strategy        Limit
-------- --------------- ------------------------------------------------
PNG      chunk           �?2,147,483,647 B (2 GiB - 1)     ← "≤" 变成乱码
PNG      eof             unlimited (f...
```

- **影响**：README 首推的下载平台就是 Windows x64 / ARM64。`≤`（容量上限）、`—`（策略注释分隔符）是 `inspect` / `list-strategies` 的核心输���，一律乱码。`rejection.rs:99` 的「APK 格式不在支持列表中（不支持作为载体文件进行修改）。」是全项目唯一的中文消息，既与其它全英文错误风格不一致，也会同样乱码。
- **修复**（二选一，推荐前者）：

### A-7 ｜ MP4 探测只接受 5 种首 box，`styp` / `moof` / `uuid` 开头的合法 ISO-BMFF 被判为「不支持」

- **位置**：`rust/src/adapters/mp4.rs:78-81`
- **复现**（构造合法的最小 BMFF）：

```
styp + moof + mdat  → [ERROR] Unsupported format ... is not a supported carrier format
moof + mdat + ftyp  → [ERROR] Unsupported format ...
uuid + ftyp + mdat  → [ERROR] Unsupported format ...
```

- **机制**：`detect` 只比对 `bytes[4..8] ∈ {ftyp, moov, mdat, wide, skip}`。
- **影响**：DASH/CMAF 媒体分片（首 box 为 `styp`）和无前置 `ftyp` 的 fragmented MP4（首 box 为 `moof`，ISO/IEC 14496-12 允许）是真实存在的形态，全部被拒。README 把 MP4 列为支持载体，用户会预期这些能用。
- **修复**：把白名单扩到 `{ftyp, styp, moov, moof, mdat, free, skip, wide, uuid, pdin, sidx, emsg}`，或改成「读第一个 box 头，只要 box size 自洽且 type 是 4CC 就认为是 ISO-BMFF」——后者更稳，且 `verify_structure` 已会做完整的 box 树校验兜底。

### A-8 ｜ `-o` 指向不存在的目录、或单载体时 `-o` 指向已有目录 → 裸 OS 错误（且被本地化）

- **复现**：

```
> strhide write -c c.png -t x -o nope\c.png
[ERROR] I/O error: 系统找不到指定的路径。 (os error 3)        ← 不存在的父目录

> strhide write -c c.png -t x -o outdir                    ← outdir 是已存在目录
[ERROR] I/O error: 拒绝访问。 (os error 5)                  ← 以为 "-o 目录" 是 batch 专属
```

- **两个问题**：
  1. `batch_output_dir` 只在 `multi` 时校验 `-o` 是目录，单载体传目录会一路走到 rename 才炸。README 的 batch 说明让用户以为「单载体 `-o <目录>`」能用（`read` 就是这个语义）。
  2. 错误直接透传 `io::Error`，**消息被 OS 本地化**成中文，与项目其它全英文错误风格严重不一致（`cli.rs` 里专门为 password-file 做过「补全上下文」的同类改进，这次漏了）。
- **修复**：`batch_output_dir` 的目录校验下沉到 `!multi` 分支（单载体 `-o` 是已存在目录时，落到 `outdir/<carrier 名>`，与 batch 行为对齐）；并把 `File::create(&tmp_target)` 失败包装成 `Rejection("No write permission on target directory '<dir>': <e>")`。

## 3. P3 级问题（资源 / 一致性 / 文档）

### A-9 ｜ 解压路径无输出上限（对不可信载体的防御缺口）
- **位置**：`rust/src/crypto.rs:364-384`（`decompress_stream` 无 limit）、`engine.rs:1102-1108`（解到 `Vec::new()`）、`engine.rs:1116`（SHA-256 在**解压之后**才比对）
- **实测**：8 MiB 全零载荷 → UBE 仅 **8,381 字节**（1000:1）。
- **含义**：一个构造过的载体可以让 `read` 试图分配远超其体积的内存。`meta.raw_size`（真实大小）虽然存在，但当前只用于最终比对，**没有用于上限校验**。
- **修复**：`decompress_stream` 增加 `limit: u64` 参数；`read_carrier` 传入 `meta_obj.raw_size`，超限即返回 `CorruptedData`。成本极低，属于对不可信输入的必要防御。

### A-10 ｜ PE `.text` 在单次操作中被重复 profile 2–3 次 + 写探针文件残留
- **A-10a 重复 profile**：调用点统计——`inspect` = 2 次（`strategy_capacities` + `locate_codebits`）；`read` = 3 次（`locate` + `open_ube_reader`→`extract_ube` 内部 2 次）；`remove` = 3 次；`write` = 2 次。实测 32.6 MB 的 PE：`inspect` 384 ms / `write` 789 ms / `read` 554 ms / `remove` 1057 ms。
  - 最小改动：`extract_ube` 里 `parse_channel_header` 与紧随其后的 `profile` 是同参数同结果，合并即可白赚一次全量 decode。
- **A-10b 写探针残留**：`rejection.rs:292-302` 的探针名只带 PID（`.strhide_write_probe_<pid>`），**同一测试二进制内的多个测试线程共享 PID**，会互相创建/删除同一文件；进程被强杀或 `remove_file` 失败时残留。对一个主打 stealth 的工具，在用户目录明文创建临时文件会被文件监控/EDR/备份软件看到。
  - 修复：改用 `tempfile::Builder::new().prefix("strhide").tempfile_in(dir)`（随机名 + 自动删除），或随 A-2/A-8 一起删掉探针。

### A-11 ｜ ZIP `strip` 的 `patch_offset + 4` 存在 u32 溢出（补充既有报告 P2-2）
- **位置**：`rust/src/adapters/zip.rs:339` → `stego_in.seek(SeekFrom::Start((header.patch_offset + 4) as u64))`
- **机制**：`patch_offset: u32` 未对文件大小做任何上界校验；损坏/篡改的信封头若使其接近 `u32::MAX`，`+4` 在 debug 构建 panic、release 构建回绕为 3。与既有报告指出的 `bytes_before_patch` 下溢是同一类问题，但发生在**不同的表达式**上，修一处不能覆盖另一处。
- **修复**：`patch_offset` 与 `bytes_before_patch` 一起改成 `checked_*`，统一返回 `CorruptedData`。

### A-12 ｜ `next_backup_path` 用 `format!("{}.bak", path.display())` 构造路径
- **位置**：`rust/src/engine.rs:444,455,457,463`
- **机制**：`display()` 对非 UTF-8 路径是有损的（Windows 上是未配对 UTF-16 代理项，Linux 上是任意非 UTF-8 字节），会渲染成 U+FFFD，从而构造出一个**不存在的**路径，`std::fs::copy` 随即以 `NotFound` 失败。
- **影响**：边缘但真实的失败——合法路径被改成非法路径，且错误信息完全误导。
- **修复**：
  ```rust
  let mut os = carrier.as_os_str().to_os_string();
  os.push(".bak");
  PathBuf::from(os)
  ```
  （`.bak-<时间戳>` 等分支同样处理。）

### A-13 ｜ ZIP / PDF 适配器未实现 `suspicious_structures`，stealth 信封叠加无任何提示
- **状态**：既有报告与 `docs/CHANGES-20261019.md` 已记录为「已知未修复」，本轮实测确认：

```
pw1 写 stealth → pw2 再写 stealth：
  png  → 有 WARNING      jpg → 有 WARNING      mp4 → 有 WARNING
  pdf  → 无 WARNING（信封静默叠加）
  zip  → 无 WARNING（信封静默叠加）
```

- **影响**：用户在 PDF/ZIP 上叠加了第二个 stealth 信封后，只有等到 `remove` 时 SHA-256 校验失败才可能发现（`remove_carrier` 的诊断分支会提示「还有另一个信封」，但那是事后）。写入时的预警是唯一低成本的机会。
- **修复**：PDF 用「`%%EOF` 之后出现 `N 0 obj << /Type /Metadata /Length L >> stream` 且以信封结尾」作为结构信号；ZIP 用「EOCD 之前存在一段长度 ≥ 136 且 CRC 自洽的疑似信封区」。

### A-14 ｜ `MIN_UBE_PLAIN` / `MIN_UBE_ENCRYPTED` 是手算硬编码常量
- **位置**：`rust/src/envelope.rs:47-49`（`178` / `214`）
- **问题**：这两个值被 `PeAdapter::strategy_capacities` 用来判断 `pe_codebits` 是否「可用」，直接影响 `inspect` 输出与 `choose_auto_strategy`。它们由 `1+2+0+1+32+5 = 41` 字节紧凑元数据等式手算得出，**任何元数据布局或 varint 宽度变化都不会自动反映**，只会静默失准。
- **修复**：改为实际构造一个最小信封测出（`compact_meta.rs` 里已有 `smallest_envelopes_match_the_documented_minimums`，把常量改成从该测试导出的 `fn` 即可）。

### A-15 ｜ `decrypt_metadata` 把**所有**失败都映射成 `Password` 错误
- **位置**：`rust/src/crypto.rs:156`
- **影响**：无密码模式下解元数据失败（数据损坏 / AAD 不匹配 / 版本漂移）也会报 `Password error: Invalid password or corrupted metadata`，在没有密码的场景下这个词具有误导性；`inspect_carrier` 的 `{"error": "Invalid password"}` 分支同理（`engine.rs:1399`）。
- **修复**：拆成 `Password` 与 `CorruptedData` 两个变体，让调用方按场景选择。

### A-16 ｜ 体积膨胀告警的文案自相矛盾
- **位置**：`rust/src/engine.rs:724-729`
- **复现**（68 字节的最小 PNG）：

```
[WARNING] Hidden data envelope size (214 bytes) exceeds 50.0% of carrier file size
          (68 bytes, 314.7%). Noticeable file size inflation may compromise stealthiness!
```

文案把阈值 `50.0%` 写死在句子里，括号里却是 314.7%，读起来自相矛盾。对任何 < 428 字节的载体都会触发（阈值退化为 `orig_host_size / 2` 的整数除法）。
- **修复**：阈值走文案插值（`exceeds {threshold_pct:.0}%`），并对极小载体改用绝对字节数表述。

### A-17 ｜ 已核查、确认无问题的两点（避免下轮重复排查）
- **`strip_codebits` 的 `read_at(slack_off, CHANNEL_HEADER_LEN + ube_len)`**：`ube_len` 虽来自不可信的通道比特，但 `validate_header` 已强制 `positions >= (14+ube_len)*8`，而 `positions ≲ text_scan_len/2`，因此 `diff_len` 被限制在 `.text` 的约 1/16 以内；`slack_off` 的越界 seek 会被 `read_exact` 的 `UnexpectedEof` 挡住。**不构成内存耗尽攻击**。
- **PNG CRC 重算时的 `vec![0u8; 4 + ube_total_size]`**（`engine.rs:829`）：峰值额外增加一个信封大小的副本。当前容量下可接受，但和 A-9 的限流一并处理更好。
