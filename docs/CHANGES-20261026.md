**3. 视频帧类型两级门控（关键设计修正）**

- **规则**：码流中存在非参考图（nal_type ∈ {0,2,4,6,8}）→ 只录这些；不存在 → 录全部 VCL（静图全 IRAP、以及部分安卓编码器产出的全 `TRAIL_R` 流）。判据只依赖 `nal_unit_type` 序列，两端推导一致，**不入 wire 头、不改 `HevcFormatProfile`**。
- **踩到的坑（重要）**：门控只能决定「哪些切片贡献槽位」，**不能**决定喂给解码器的切片集合。第一版只把非参考切片喂给解码器，`IMG_0033.MOV` 直接 0 槽——解码器在未见到 IRAP 前按 H.265 §8.1.3 跳过全部非 IRAP 切片，且 P/B 图需要参考图在 DPB。修正：全量按解码顺序喂（未入选切片走 `push_nal` 无 observer 路径），仅对入选切片挂 observer 并吸收槽位。
- **实测代价**（iPhone 4K 3 秒 / 78 帧）：关闭门控 2,780,623 槽 → 门控后 38 帧 381,977 槽（约 14%，非原文估计的「约一半」）。原因：非参考帧的旁路符号本就更少（参考帧 100~170 万 bin/帧 vs 非参考帧 20~28 万 bin/帧）。
- **已知边界（诚实记录）**：极短片段在 A 级下会低于 40 字节头部门槛，容量归零——`bear.hevc`（320×180，15 个非参考帧）368 槽、`bear-opengop.hevc` 400 槽，均无法承载任何载荷；`test-25fps.hevc`（114 KB，250 帧）38,480 槽 / 2.3 KiB 正常。这是门控的既定代价，未引入「非参考槽位不足则回退」之类的二次判决（会引入新的两端一致性负担）。受此影响，`local_hevc_annexb_roundtrip_on_a_real_stream` 从固定 `bear.hevc` 改为在语料中选择首个容量足够的流。

### 2026-10-26 08:10:00 - 旁路槽位实测盘点：指南 12 个位置的可用性与容量（另见 `docs/HEVC-BYPASS-CHANNELS-MEASURED-20261026.md`）

用 `CabacObserver` 计数在真实语料上量化了"还有多少可写"（主仓与 vendor fork **零净改动**，测量用钩子已回滚）：

- 4K 78 帧片段：全部 bin 4,174 万，旁路 1,056 万，当前符号槽 362 万（引擎去 DC/EPB 后 278 万）——已占旁路位的 26%。
- **指南"通道 C"（`coeff_abs_level_remaining` 定长后缀 LSB）实测仅 +5%**（24.2 万后缀 bin / 18.1 万 LSB），远低于指南估算的 +130%：`coeff_abs_level_remaining` 只在 `base == threshold` 时出现，`c_rice_param >= 1` 在真实片段里不常见。**不做**（槽池变化 = 线格式身份变化，收益过低）。
- 剩余 670 万普通旁路位的大部分是该语法元素的 **unary 前缀**，改它会改变码字长度（Δ ≠ 0 + 失步），不可写。
- 仍可挖的只有 `mvd_sign_flag`（需 MVP 最优性守卫防 MVPO 检测）与 SAO（容量小）；SEI / 尾随填充是 Δ ≠ 0 的容器写路径，另立里程碑。

**优先级结论**：先做性能（`syntax_only` + 并行）而不是继续扩容通道。
