### 2026-10-26 19:55:02 - HEVC 视频容量重构：二元帧型门改为漂移分层阶梯 + 容量口径按图片数修正

**1. 帧选择：Tier A/Tier B 二元门 → 两层漂移阶梯（`engine.rs`、`slot.rs`）**
- **问题**：流中只要存在非参考图就**只**收录非参考图，`IMG_0033.MOV` 丢掉 89.2% 槽位（7.76 M → 0.84 M）；而全 `TRAIL_R` 的 `VID_20261007` 走 Tier B 全收——同一个 `TRAIL_R` 在一处被整类剔除、在另一处全量使用，容量随编码器输出抖动，同规格视频差 45 倍。
- **方案**：`picture_band()` 取代 `selectable()`。无任何非 IRAP 图（静图/全帧内）→ 全部 band 0；否则非参考图 → band 0（零漂移），非 IRAP 参考图 → band 1，IRAP（nal_type 16..=23）→ 排除。
- **依据（ffmpeg PSNR 实测，见 `docs/hevc_video_capacity_quality_audit_20261026.md`）**：IRAP 只占 25% 槽位，但同等载荷下纳入会让 PSNR 从 48.4 dB 掉到 34.9 dB（5 KB）/27.6 dB（25 KB）；非 IRAP 参考图可用，代价约为非参考图的 8 倍/比特。
- **实现**：`StegoSlot` 增 `band` 字段，`CabacRecorder::with_slice(slice_idx, band)` 打标；池按 band 稳定分区并重映射 `slot.slot_idx` 与 `SliceContext.slot_map`；`slot_positions()` 换成 `band_positions()`（逐层 Weyl、前缀稳定、层间不交错，能装进 band 0 的载荷绝不动参考图）。

**2. 容量口径：单帧像素 → 像素 × 图片数，视频改用阶梯预算（`engine.rs`、`mp4_boxes.rs`、`params.rs`）**
- **Bug**：`total_elements = width × height`（只有一帧），导致 `bpp_limit × 像素` 恒为 207,360 bit，**任意 1080p 视频推荐容量都被钉死在 25.3 KiB**（13.6 s 的 40 MB 视频与 6.4 s 视频等同）。
- **修复**：`Mp4HevcTarget` 暴露 `picture_count`（`stsz` 样本数）；图片数用 `first_slice_segment_in_pic_flag` 统计（多切片图片只算一张），HEIF 恒为 1（grid 分块同属一张图）。
- **视频推荐值**：不再用 `min(bpp×像素, 槽位/6.9)`，改为阶梯计价 `non_ref_fraction × N_band0 + min(ref_flips_per_picture × P_band1 × 4, N_band1)`，档位参数见新增 `SafetyLevel::video_budget()`（paranoid 0.35/110，high 0.60/220，balanced 0.95/450）。静图口径完全未变。

**3. 探测与规范同步**
- `probe_hevc_slots_count()` → `probe_hevc_pool()`：分层采样，每层按各自字节比缩放（参考图符号密度是非参考图的 2~3 倍，全局单一比例会系统性偏差）。
- `docs/api/WIRE_SPEC.md` §13.11.4（分层 Weyl）与 §13.11.7（漂移阶梯 + 推荐容量公式）重写，含实测对照表。

- **规则**：码流中存在非参考图（nal_type ∈ {0,2,4,6,8}）→ 只录这些；不存在 → 录全部 VCL（静图全 IRAP、以及部分安卓编码器产出的全 `TRAIL_R` 流）。判据只依赖 `nal_unit_type` 序列，两端推导一致，**不入 wire 头、不改 `HevcFormatProfile`**。
- **踩到的坑（重要）**：门控只能决定「哪些切片贡献槽位」，**不能**决定喂给解码器的切片集合。第一版只把非参考切片喂给解码器，`IMG_0033.MOV` 直接 0 槽——解码器在未见到 IRAP 前按 H.265 §8.1.3 跳过全部非 IRAP 切片，且 P/B 图需要参考图在 DPB。修正：全量按解码顺序喂（未入选切片走 `push_nal` 无 observer 路径），仅对入选切片挂 observer 并吸收槽位。
- **实测代价**（iPhone 4K 3 秒 / 78 帧）：关闭门控 2,780,623 槽 → 门控后 38 帧 381,977 槽（约 14%，非原文估计的「约一半」）。原因：非参考帧的旁路符号本就更少（参考帧 100~170 万 bin/帧 vs 非参考帧 20~28 万 bin/帧）。
- **已知边界（诚实记录）**：极短片段在 A 级下会低于 40 字节头部门槛，容量归零——`bear.hevc`（320×180，15 个非参考帧）368 槽、`bear-opengop.hevc` 400 槽，均无法承载任何载荷；`test-25fps.hevc`（114 KB，250 帧）38,480 槽 / 2.3 KiB 正常。这是门控的既定代价，未引入「非参考槽位不足则回退」之类的二次判决（会引入新的两端一致性负担）。受此影响，`local_hevc_annexb_roundtrip_on_a_real_stream` 从固定 `bear.hevc` 改为在语料中选择首个容量足够的流。

### 2026-10-26 08:30:00 - 性能实测：syntax_only 跳过像素重构 1.8~4.2x，rayon 空间很小，CLI 存在双次扫描（另见 `docs/HEVC-SYNTAX-ONLY-PERF-20261026.md`）

release、16 线程主机、2 KiB 载荷，主仓与 fork 零净改动（临时计时/补丁已回滚）：

- **阶段拆分**：record（解码+录日志+建槽）是绝对大头（50%~80%），STC 求解仅 2.5~3 ms（成本随载荷长度而非 3800 万槽的池子），replay 占 3%（小文件）~20%（40 MB）。
- **syntax_only**：解码器自带 `Ablate`(MC/INTRA/RESIDUAL) 给 1.45~2.05x；再把**环路滤波（去块+SAO）也跳过**（fork 一行守卫）可达 **1.81~4.23x**；三个语料槽位数在开关两种模式下**逐项相同**，证明熵解析不依赖重构样本 ⇒ 槽池不变，无需 bump 方言。embed 墙钟：iPhone 4K 20.36→5.30 s、MOV 13.79→4.33 s、40 MB 68.55→38.67 s。
- **rayon 按切片并行收益很小**：真正独立的只有 replay 阶段，8 线程也只再快 3%~15%；record 是单一解码器状态机，帧级并行需要 fork 改造（ablation 后解析不再需要参考像素，理论可行）。
- **意外发现（更大）**：CLI 在非 `--quiet` 嵌入前会先跑一次完整容量探测只为打印告警，等于**扫两遍**（iPhone 4K：引擎内 10.47 s vs 墙钟 20.36 s）。改为嵌入后按返回槽池规模告警即可 ~2x，零风险。

**优先级**：P0 CLI 单次扫描 → P1 syntax_only（含 fork 跳过滤波） → P2 日志内存瘦身 → P3 帧级并行解码。
