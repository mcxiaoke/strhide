### 1.2 独立实测：`|c|=2` 到底占多少（复现评审数字）

方法：PIL 解码 → 逐对齐 8×8 块正交 DCT-II → 除以量化表取整（误差 ±1 量级），统计 Y 通道直方图。

```

  |c|>=2（含 DC）          :   740,907     评审：741,260  ✓
  |c|==2                   :   171,690     评审：171,457  ✓
```

**评审 P0-1 的事实基础成立**：在方案 §三.3 的边界规则下，池内**约 24%** 的槽位只剩单向自由度（`+2` 只能 `+3`，`-2` 只能 `-3`），池外 48 万个 `|c|=1` 永远进不来。

## 三、评审自身需要修正的两处

### 3.1 第 7 条：改 `dct_move` 不会让旧载体"提取全线瘫痪"

`dct_move` 只有两个调用点，**都在写路径**：

* `jpeg/engine.rs:332`：正文写回；
* `jpeg/engine.rs:358`：`embed_dct_lsb`（头部 1 bit/槽写入）。

**提取路径从不调用 `dct_move`**——`extract_jpeg` 只读 `coeff & 1`，再重算代价图重建池（`engine.rs:380`）。因此已发布的 0.5.0 载体，其提取只依赖"载体上的值 + UERD 代价"，与 `dct_move` 的取值无关，改它**不会**让旧载体读不出来。

真正的风险是两个：
1. **写侧语义**：若 `--format-version v2` 仍可选，V2 写入必须继续维持 `|c| & !1` 不变（否则新写的 V2 载体，其池在提取端重建时规模/成员变化 → 自失步）。所以必须**按版本分流**，评审的方向正确，只是理由要换成"写侧/格式 v2 兼容"，而不是"旧载体解码崩溃"。
2. 更重要的是 §四.1 的问题：`dct_move` 一改，写回代码会**静默丢弃**所有三元决策。

### 3.2 第 2 条："根本没有自由度"应改为"改动量被码率锁定"

`u=1, h=8` 时 R≈1.0，`expected_stc_change_rate(1) = 0.501 flips/bit`（`coding.rs:296-309`，80 张图标定）。这个数字与代价无关——说明在 R≈1 下**改动数量是码率决定的常数**，Viterbi 只能在 h 个窗口位置里挑"改哪个"，无法降低"改多少个"。所以准确表述是：截选后**改动量不可优化、位置只有窗口内局部选择权**，等价于带一点局部最优的随机 LSB 替换。这个措辞差异不影响结论，但写进文档要经得起追问。

## 四、评审遗漏的 4 个硬约束（决定"照建议改"是否可行）

### 4.1 引擎的"奇偶载体 + 写回"结构**无法表达真三元**（P0 级）

现状（`jpeg/engine.rs:294-304`）：

```rust
let mut slot_vals: Vec<u8> = body_slots.iter()
    .map(|&(bi, k)| 2 | ((coeffs...[bi][k] as i32) & 1) as u8)  // 只保留奇偶
    .collect();
let moves = vec![Move::PlusOnly; count];
let rm = vec![f64::INFINITY; count];                            // 负向恒 ∞
```

三个后果：

1. **方向信息在传给内核前就丢了**。`slot_vals` 只有 `2/3`，内核回溯出的 `Kind::{Plus,Minus}` 只在 `vals[j] = y±1` 上体现奇偶变化，引擎拿不到"我在这个槽位选的是 +1 还是 -1"。
2. **写回把 `Both` 当空操作**：`engine.rs:332-338` 的 `Move::Both => {}`，注释写着"Unreachable"。V3 一旦让 `dct_move` 返回 `Both`，所有需要改动的槽位都会**什么也不做**，系数保留原奇偶 → 校验子错 → 提取全乱。
3. **`i16` 边界内核看不见**：内核在合成的 `2/3` 上做 `y±1`，永远安全；真实系数 `+1024` 的 `+1` 溢出、`-1024` 的 `-1` 溢出，必须在写回侧按真值判合法性。

> **结论**：Phase 1 的工作量不是"改 `dct_move` 一个函数"，而是**重做槽位表示与写回契约**（内核返回每槽 delta 向量，或写回侧按 `rho_plus/rho_minus` 复算方向并处理 ±1024/0 边界）。方案的 Phase 1 描述严重低估了这一块。

### 4.2 `u ≤ h` 是内核硬约束，`u≈N/m` 不是"放宽常量"能解决的

评审建议"扩展 `stc.rs` 使其具备大 u（≈N/m）能力"，方向对，但真实阻力比它写的多一层：

* `stc.rs:206-210`：`if u > h { return Err(...) }`，需要每个元素有**独立的列向量**（`add_to_basis` 秩检查），h 位空间最多只有 h 个线性无关列 → u 天然 ≤ h ≤ 10。
* `stc.rs:89`：`cols: [u32; MAX_STC_U as usize]`，定长 3。
* 参考实现**没有这个约束**：`stc_embed_c.cpp:109-137` 用 `invalpha = n/m`、`widths = floor/ceil(invalpha)`，列向量是随机取（允许相关），靠"无解则换置换重试"兜底（`stc_ml_c.cpp:493-505`）。所以 32,768 比特 / 703k 槽 → `u≈21`，在 C++ 里合法，在本项目内核里**必被拒**。

要真正拿到全图能力，需要三处改动：放宽 `u ≤ h` 与秩检查（改用经典随机列构造）、`cols` 改 `Vec`、把"无解"从报错改成"换置换重试"。**此外**注意：`embed` 的精确填充约束意味着 `u` 不是自由参数，而是由 `(N, bits)` 唯一决定的：`u = ⌊N/(bits+h-1)⌋`。这条恰好给出一个免费的工程简化——**u 不需要存进头部，两端都能从 N 和 bits 算出来**。

### 4.3 基准的"1.94 s"与本项目内核的代价模型不可比（对方案有利，对采信方式不利）

* 基准用的是 `h=10`（`stc_interface.cpp:24`）→ 状态数 2¹⁰=1024；本项目默认 `h=8` → 128（`u>1` 时 256）。
* 本项目内核每元素开销与 `u` **无关**（内层是 `states × 2`），`stc.rs:55-63` 自己写了"600k 槽 ≈ 2·10⁸ 次转移 ≈ 1 秒"。
* 所以真实全图成本大概在 **0.3~1.5 s**（2.4M 个 AC 位置时 1~2 s），比方案引用的 1.94 s 更乐观；但**这个数字不能用来证明方案自己的设计**，因为方案设计的是截断 K 槽。

### 4.4 V3 头部还漏了 FeatureWord 与"鸡生蛋"问题

* V2 是 **512 槽**（256 头 + 256 FeatureWord，`header.rs:104-110`），`codec/u/h/class_rule` 全在 FeatureWord 里。方案只给 128 槽、只规划 64 比特，等于**连 codec/u/h 的自描述都没了**。
* 头部置换种子必须能在**不知道 salt**的前提下派生（salt 在头部里面），V2 用 `derive_header_perm_seed`（`envelope.rs:112-128`）解决了这个循环依赖；方案的 §三.2 只说"用 `stego_key`"，没区分"头部种子（无 salt）"与"正文种子（有 salt）"。

## 五、复核后的结论：评审是"对了一半的处方"

评审的诊断基本都对，但它的第一条修正建议（"要么扩内核大 u，要么老实承认上限"）与第二条（"恢复 36 字节头部"）**都还不够**——因为它们默认保留了方案 §三.1 的 `|c|>=2` 内容相关候选池。而**池的内容相关性才是 P0-1 与 P0-2 的共同病根**。

### 5.1 病根

方案为了"提取端能重建同一个池"，把池定义成 `|c|>=2`（值相关）；值相关就必然要求"改动不能改变池成员"→ 只能加边界锁 → 造出新的单向门。这是一个**自证循环**：池不变性要求本身，就是新指纹的来源。

### 5.2 正确的处方（V3′）

**把槽位集合做成内容无关的固定网格，代价只决定"改不改"，不决定"有没有这个槽"。**

```
槽位集  ：全部 AC 位置（每块 k=1..63），共 38400×63 = 2,419,200（1920×1280）
          不做任何 |c| 值筛选 —— 这是与方案 §三.1 的唯一但决定性的区别
代价    ：UERD；仅 DC、|c| 已达 ±1024 置 ∞
置换    ：key 派生 ChaCha12 Fisher-Yates（复用 prng.rs）
u       ：u = ⌊(N - header_slots) / (bits + h - 1)⌋   32,768 比特 → u≈73
提取    ：按固定几何重建同一网格 → 同一置换 → 读奇偶 → 校验子
         不重算代价、不重建池、不查 |c| —— 失步在结构上不可能发生
```

这一改，四条问题同时消解：

| 问题 | 消解方式 |
| :--- | :--- |
| P0-1 单向门 | 值不再参与池的构成；只有 ±1024 有界，其余 0↔1、1↔2 双向对称，无边界赤字 |
| 池不变性规则 | 不需要了（无池可失步），§三.3 整节删除 |
| P0-2 截断丢自适应 | 用全网格 + `u≈N/m`，与 pySTC 同构 |
| P1-5 槽位算术 | 头部 u=1 独立实例，精确 295 槽 |

**头部布局（修正后）**：

```
16B Salt + 12B Nonce + 4B (26b len | 2b codec | 4b h) + 4B Magic
= 36 B = 288 bit  →  u=1, h=8 下 slots_for(288) = 288 + 7 = 295 槽
（m = 295 - 8 + 1 = 288 = bits，精确填充，不触 stc.rs:327 的拒绝分支）
```

`u` 不入头部（由 N、bits 推出）；`Magic` 保留 32 位用于 V3/V2 分流（误报 2⁻³²）。

### 5.3 落地顺序（替换方案 §六）

* **Phase 0（新增，先做）**：写一个"槽位契约"单测——给定 (N, bits)，两端算出同一 `(u, header_slots, body_slots)`；先不碰编码内核。
* **Phase 1**：改内核（放 `u ≤ h`、`cols` 动态、无解改重试）+ 改引擎槽位表示与写回契约（§四.1），V2 写路径按 `format-version` 分流保留原 `dct_move` 语义。
* **Phase 2**：门禁改为评审建议的措辞——"原 `|c|>=2` 的槽位在嵌入后无一跌到 `|c|<=1`"在 V3′ 下不再需要（结构上不依赖值），改成更强的：**"同一 (几何, 密码) 下，嵌入端与提取端算出的槽位序列逐项相等"**（直接测契约，不测现象）。
* **Phase 3**：DCTR/PSNR 复测；此时因为 R≈1/73，改动密度从"随机子集的一半"降到全图百分之几，PSNR 与 DCTR 才有可比性。

### 5.4 空域（评审第 8 条）建议的处理

不建议同期改造。理由：空域 `val & 0xF8` 类规则的 9σ 赤字已有独立的 `spatial_move_safe`（`coding.rs:383-390`，r∈[1,6] 安全规则）在压，且空域的"槽位集合"本来就是固定像素网格（内容无关），**不存在 JPEG 这套池失步问题**；它的改造动机是直方图，不是同步性。方案文档里应显式写一句"本期不含空域，空域按独立议题推进"，避免读者误以为 JPEG 改完就通吃。

## 六、给方案作者的处置建议

1. **§三.1 候选池定义整体重写**（值无关网格），§三.3 边界规则整节删除——这是唯一能让"0 赤字"成立的路径。
2. **§三.4 头部改 36 字节 / 295 槽**，并补 FeatureWord（或明确 V3 用固定 codec，省掉自描述）。
3. **§四 表注 3 删除"pySTC/HStego 同理"**：`pystc.py:89` 之后是 `cover_array[64:]` 全量 + `widths≈n/m`，与"前 K 槽截选"不是一回事。
4. **§六 Phase 1 扩写**：内核 `u` 能力 + 引擎写回契约 + 二元载体表示，三项都不是"改 `dct_move`"。
5. **§二 基准重跑**：至少补两条口径——(a) 非均匀代价（UERD），(b) 写回 JPEG → 落盘 → 重新读系数 → 重建槽位 → 提取的完整往返。
