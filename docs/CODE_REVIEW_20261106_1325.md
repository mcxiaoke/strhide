## 1. 执行摘要

### 1.1 总体判断

这是一个**工程完成度相当高**的项目：分层边界有 CI 门禁守护，结构域写侧有"精确预算 → 加密后交叉核对 → 写后自检 → 还原 SHA-256 兜底"四道闸，读侧有 `confine_location` / `validate_against` / `validate_header` / 解压硬上限，线格式有 793 行规范，测试约 2.7 万行并含字节级基线。**没有发现无条件触发、必然损坏正常文件的致命缺陷**（P0 级 0 条）。

但审查确实找到一批**在特定但合法的输入下会产出损坏文件或错误结果**的路径，集中在容器解析的"信任边界"上：

- **没有最终哈希兜底的域**（内容域 HEVC / MKV / MP4）风险最高：MP4 样本偏移不校验 `mdat` 归属、MKV 未知大小 Cluster 的 CRC 覆盖范围、公开 patch API 漏刷 MKV CRC、CABAC 重编码变短时用 0 填充 RBSP 尾部——这四条都可能产出"引擎自己认为成功、第三方解码器却拒绝"的文件。
- **结构域**的缺陷多为"校验不对称 / 诊断被吞"：`verify_restored`（`structure/engine.rs:2386`）在提交前用全量 SHA-256 兜底，绝大多数坐标伪造最终不会产生损坏文件，但 ZIP 分卷、写后自检不核对坐标、CRC 损坏被吞成"无信封"仍会造成诊断失真或误判。
- **参数与容量口径**存在若干双轨：JPEG probe 用 SOF 理论网格、embed 用实际解码块数；统一入口容量减 256 而专家面不减；`extract` 错误统一折叠为 `NoHiddenData`；只读文件入口用"运行时可用内存 60%"做准入。
- **测试覆盖**对 PNG/JPEG/结构域/PE/CLI 很扎实，但对 HEVC 最复杂的 EPB 24 轮重试、真实 MKV 载体、FLAC CONSTANT/VERBATIM 子帧、IO 故障注入、>4 GiB 真实文件、内容域头逐字段篡改，基本是空白；`heavy/` `local/` 套件在缺少 `../temp/` 外部语料时静默跳过，可能让覆盖率看起来虚高。

但 CRC 采集仍用 `element.end()`（`mkv_boxes.rs:492`），而 `collect_crc` 把它当成 parent_end（`mkv_boxes.rs:516-522`）：

```rust

        return;
    }
```

对未知大小 Cluster，`element.end()` ≈ `segment.end()` ≈ 文件尾，于是该 CRC 的覆盖范围吞掉后续所有 Level-1 元素，多个 CRC 的 `covers` 互相重叠。`refresh_crcs` 按范围排序重算时会写出覆盖范围错误的校验值（或最终校验失败、embed 报 "MKV checksum refresh failed"）。内联测试 `mkv_boxes.rs` 覆盖的是"未知大小 Cluster 不吞后续 Cluster 的 slice span"，**不是 CRC covers**。

- **建议**：把迭代器求得的隐式 Cluster 结束偏移传给 `collect_crc` 作为 parent_end；或明确拒绝对未知大小 Cluster 内的 CRC 做刷新。

### F-29 (P2, A) ISO-BMFF L1 结构校验每轮 box 循环都重读文件尾 24 字节

`structure/adapters/isobmff.rs:263-266`：

`trailing_envelope_len`（`isobmff.rs:44-49`）每次 `seek(End(-24))` + `read_exact` + `seek(Start(offset))`；box 数上限为 1,000,000（`isobmff.rs:330-335`）。含大量顶层 box 的 MP4/MOV/HEIF 在每次 `verify` 与写前结构检查时，最坏产生约 3×10⁶ 次额外系统调用。建议把尾部 trailer 解析提到循环外一次完成，循环内只做数值比较。

`png/engine.rs:625-629`：


### F-31 (P3, A) 其余性能观察

- `stego/io.rs` 的文件级 embed 先 `sniff_file`（读文件头）→ `fs::read`（全读）→ `sniff_bytes`（再解析），三次 IO/嗅探；两个 sniff 结果在边界情况下若不一致，预算检查与引擎会使用不同 `format`。
- `stego/mod.rs:96` `compute_default_threads` 的 `.max(4)` 使 `total = 6` 时返回 4（> 3），与注释"otherwise half of the total cores"不符；仅影响默认 Rayon 池大小，已有测试钉死实际值。
- `stego/mod.rs:271-274` `filename_safe_capacity` 只把 `tier_limits` 与 `recommended_max_bytes` 做 `min`，未同步 `available_slots`，小容量载体上三档可能全等、展示层不自洽。
- 正面证据：`docs/CHANGES-20261106.md` 记录了 FLAC `scan_stream`/`analyse_with_tails` 去重解析与 drift 复用（embed −12~15%、extract −26~30%），以及 WAV working-set ceiling 回退修复；`core/crypto.rs:704-708` 的解压硬上限、`crypto.rs:660-694` 的 256 KiB 分层压缩采样都是有明确实测依据的优化。

### F-32 (P2, A) release `panic = "abort"` 与 814 处 `unwrap()/expect()`

**但第三方报告的后果部分不成立**：批量目录模式实际走 `cmd_structure.rs:400-402` 的 `batch_payload_name`（文本载荷为 `<stem>.txt`）+ `unique_batch_path` 去重，`structure/engine.rs:2026` 还有 `check_overwrite`；`extracted.bin` 只出现在 `write_payload_to` 的 `out_p.is_dir()` 单文件分支（`engine.rs:2003-2009`）。因此是"批量状态丢失"而非"必然同名覆盖"，需按真实影响定级。

#### N-09（P3，A）库级全局状态与公开结构体的不变量缺口

`core/i18n/mod.rs:47-49` 的进程全局语言变量被 `errors.rs:300-302` 的 `detail_i18n()` 直接读取，多线程宿主无法按请求隔离语言；`stego/mod.rs:121-127` 的 `init_default_thread_pool()` 确实是 `rayon ... build_global()`，但注释明确是 **opt-in**、仅 `cli/mod.rs:204` 调用、且**没有** `stack_size`（第三方报告所称"库 API 自动设置 8 MiB 栈"不成立）。`structure/envelope.rs:160-165` 的 `EnvelopeHeader` 全部字段 `pub`，外部可直接构造 `hint_len`/保留位非法的头并调用 `.pack()`，绕过 `validate_against`。建议字段私有化 + 构造器校验。

#### N-10（P3，A）Linux 内存探测忽略 cgroup；派生密钥 `Copy` 语义不清零

`core/sysmem.rs:58-64` 在 Linux 下只读 `/proc/meminfo` 的 `MemAvailable:`，全仓 `cgroup`/`memory.max`/`memory.limit_in_bytes` 0 命中；容器内会按宿主机内存放行大载体（叠加 `panic = "abort"`，见 v1 F-32，可能触发 OOM Killer）。`structure/envelope.rs:698-701` 的 `UnpackSecrets` 与 `core/crypto.rs:219-226` 的 `PasswordSecrets` 均 `#[derive(Clone, Copy)]` 且含 32 字节密钥/76 字节掩码，全仓无对应 `Zeroize`/`Drop` 实现，按值传递产生的栈拷贝不会清零。（第三方报告称 `create_carrier_backup` 覆盖已有 `.bak` **不成立**：`commit.rs:198-205` 用 `copy_file_to_new` + `create_new(true)` + `AlreadyExists` 换名重试。）

#### N-11（P3，A）MKV 结构校验每元素重复 seek

`structure/adapters/mkv.rs:176-178,195-196` 的 `verify_structure_with_magic` 在每个顶层元素循环内调用 `read_from_tail`（内部两次 seek）并 `seek(Start(offset))`，数万帧的 MKV 会产生数万次额外系统调用。注：真实实现在 `mkv.rs`，**不在**第三方报告所指的 `ebml.rs`（该文件仅 155 行、无 `seek`）。建议把尾部 24 字节解析提到循环外（与 v1 F-29 的 isobmff 问题同构）。

#### N-12（P3，A）`rust/README.md` 示例代码与依赖版本失真

`rust/README.md:64-69` 依赖写 `strhide = "0.8"`（5 处），而 `Cargo.toml:3` 为 `0.9.1`；`:128` 用 `write_res.envelope_size`（真实字段 `ube_size`，`structure/engine.rs:521-522`）；`:234` 用 `cap_info.capacity` / `cap_info.safety_tier`（真实为 `max_raw_payload_bytes` / `recommended_max_bytes` / `safety_level`，`stego/mod.rs:369,376,396`）。这三个示例字段全仓 0 命中，示例无法编译。已同步补入 §9。

#### N-13（P3，A，设计脆弱性）`png_pre_salt` 绑定了全部非 `IDAT`/`prIv` 辅助块

`rust/src/stego/png/engine.rs:1152-1166`（真实代码，第三方报告机制属实但触发策略是伪造的）：

```rust
pub fn png_pre_salt(
    image: &RawImage,
    spatial: &crate::stego::format::PngFormatProfile,
) -> [u8; 32] {
    ...
    for chunk in &image.chunks {
        if chunk.ty == *b"IDAT" || chunk.ty == *b"prIv" {
```

L1 派生把 `tEXt`/`iTXt`/`zTXt`/`eXIf` 等所有辅助块的内容纳入哈希。**当前不存在触发路径**：`STRATEGY_REGISTRY`（`structure/registry.rs:90-104`）里 PNG 只有 `chunk`（插 `prIv`，已豁免）与 `eof`（不改 chunk 列表），报告所称 `png_text` 策略与 `StructureProfile::png_chunk_type` 在仓库中 0 命中。但这意味着**任何第三方工具在 embed 之后编辑/新增一个辅助块**（如 Exif 工具写 `eXIf`、图像软件写 `tEXt`），都会改变 L1 派生并使内容域载荷永远无法提取——一个过宽的不变量。建议按第三方报告的思路把 pre_salt 收敛到 `IHDR`（及调色板图的 `PLTE`/`tRNS`）。

### 12.2 双域共存契约的边界澄清（N-14，不列为 P0 缺陷）

第三方报告把 F-01~F-04 全部定为 P0，核心论据是"先 `write` 后 `embed` 导致 `restore` 失败"。核实后：

1. **项目文档已明确声明这是设计边界**。`README.zh.md:28`："还原保证只适用于结构域信封"；`:32`："若写入后载体被重编码（例如叠加内容域隐写），则以 `RestoreMismatch` 失败关闭"。`verify_restored`（`structure/engine.rs:2264`）无条件比对全量 SHA-256 与 `orig_host_size`，正是该承诺的实现。把"按文档失败关闭"称为 P0 缺陷是误读。
2. **代码已对 PNG `chunk` 策略做了偏移豁免**。`engine.rs:2772-2779` 注释与实现：
   ```rust
    // PNG `chunk` envelopes can be physically relocated by content-domain
    // embedding: re-compressing IDAT changes the length of the stream before the
    // private chunk, so the envelope trailer still carries the write-time
    // coordinate. ... accept a shift for that strategy only ...
    let relocated = expected_offset != ube_offset;
    if relocated && strategy != "chunk" {
   ```
   第三方报告引用的 `envelope_coordinates_agree` 位置（`:2125-2146`）与判据（`stego_size - actual_inject_size == orig_host_size`）均不存在；真实函数在 `:2740`，比较的是 `inject_offset + offset_delta == ube_offset` 与 `ube_total_size <= inject_size`，**不引用 `orig_host_size`**。
3. **但确有一处超出已声明边界的空白（B 级，需夹具验证）**：`eof` 策略的信封追加在 `IEND`/`EOI` 之后，`stego/png/engine.rs:858` 会 `out.extend_from_slice(&image.tail)` 原样保留这些字节，而 `structure/adapters/png.rs:319-322` 的 eof 定位只校验 `t.ube_offset + t.ube_total_size == Some(file_size)`。若 `embed` 重压缩 IDAT 使长度变化 Δ≠0，新 `file_size = 旧 ube_offset + Δ + ube_total_size`，等式不再成立，结构域 `read`/`verify`/`inspect` 会定位失败——这不只是 `restore` 失败，而是"双域可分别提取"承诺的破口。`heavy/heavy_coexistence.rs:375-412` 只验证 `read_file` + `extract_carrier_file_payload`，**:462 标记 `#[ignore]`**，且默认策略不是 `eof`，该组合无测试覆盖。建议在文档中把 `eof` 排除出双域共存支持矩阵，或为 `eof` 增加基于容器尾边界的重定位逻辑（与 `chunk` 策略对称）。

### 12.6 方法学结论

第三方报告提供了若干 v1 未覆盖的**正确切入点**（容量三轨、iinf 不对称、PDF 词法解析、PE 数据目录、CLI 批量状态、流式 inspect），这些已全部实证并合并；但它把"引用不存在的策略/错误类型、把已知设计边界当缺陷、把已修复的守卫当成漏洞"混在一起，且行号大面积错位。**若直接合并其结论会引入约 15 条伪缺陷**。本报告采用"逐符号 Grep → 分组核查 → 关键片段本人二次回核 → 只采纳成立项 → 反证单列"的流程，v1 的证据链保持原样，v2 的所有新增引用均重新对应当前干净工作树。
