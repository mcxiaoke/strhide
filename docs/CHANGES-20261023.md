### [2026-10-23 12:29:46] 策略：自动位图回溯上限放宽至 4 GiB，彻底释放超大图承载力，auto 真正自动选择最优 u

**问题**：超大分辨率载体（如 50 MP、100 MP）原本物理槽位高达 5000 万 ~ 1 亿个，在 1 MB 甚至更大载荷下完全有充裕网格空间，但在 `auto` 模式下报 `predicted capacity exceeded`，逼迫用户手动计算 `--slot-budget` 传参；而手动指定 `u=3` 或 `u=4` 却能耗时仅 15 秒、100% 还原且检出评分 0/100 完美嵌入。

**根因**：原先设置的 `MAX_AUTO_BACKTRACK_BYTES = 256 MiB` 与 `MAX_GROUPED_BACKTRACK_BYTES = 512 MiB` 过于保守。对于 100 MP 图，1 MB 载荷在 $u=3$ 下需要约 768 MiB 回溯位图，原 512 MiB 截断使得系统误认为内存超限而将超大图在 1MB 载荷下直接拒嵌。

**改动**：
- `rust/src/stego/params.rs`：
  - `MAX_AUTO_BACKTRACK_BYTES` 与 `MAX_GROUPED_BACKTRACK_BYTES` 均放宽至 **4 GiB**（`4 << 30`）。现代硬件与工作站完全足以承载，在 $h=8$ 下允许最多 1.34 亿槽位，彻底解锁 50 MP ~ 100+ MP 巨型载体的物理容量；
  - `auto` 模式在大载荷下能够自动买到 $u=3$、$u=4$ 或更大分组，实现“auto 自动最优”，用户无需手动介入；
  - 更新单元测试 `max_grouped_backtrack_slots` 及 24 MP 物理容量边界判定。
- `scripts/stego_capacity_matrix.py`：
  - 同步放宽内存预测上限至 4 GiB；
  - 修复 `run_scan` 退出码逻辑：支持 `returncode in (0, 1)`（被判定为 suspicious/likely-hidden 时 exit code 为 1 但正常输出报告，现可正确提取得分，不再误标为 `scan-fail`）。
- **验证**：`cargo fmt --check`、`cargo clippy`、`cargo test --all-targets` 全绿；`batch_corpus` 及对超大图跑全满载（2M~4M+ 极限真实嵌入）的 `batch_stego`（333 秒）全部通过。

### [2026-10-23 11:20:00] 修复：Huffman 过优化载体的大载荷嵌入不再靠盐值掷硬币，容量探测不再虚报

**问题**：24 MP 载体（亮度 AC 表仅 75/162 符号，缺高零跑×高类别组合如 `(15,2)=0xF2`）嵌入 512 KiB 载荷时报「Huffman table is over-optimised … for this payload size」，而同载体 128K/256K 正常。**不是回归**：用改动前提交（01e7f62）构建的旧二进制复现了完全相同的失败；反倒是昨天 22:51 的中间提交（2.4M 槽上限）会把 256K 也打到 `u=1`，今天 08:54 的提交已修复该区间。7 个 12MP~100MP 测试载体**全部**是过优化表，u=1 掷硬币在每个载体的大载荷上复现。

**根因**（三环相扣）：
1. 过优化表使 23.6M 槽位中出现 **4 个死槽位**（±1 两方向均不可编码），且跨零翻转可与缺失符号相撞；
2. 载荷 >约 369 KB 时布局回落到 **`u=1`**——`(1,1)` 奇偶码，解唯一、零路由自由度、约 50% 强制翻转率；
3. 于是每次尝试都是掷硬币：死槽位落进使用的 419 万槽位（概率约 54%/盐）直接硬错误；或多块翻转交互把某个 cat≥2 系数推到 15 零跑后、索要表中缺失的 `(15,2)`（实测每次尝试 1~6 个坏块），3 次重试仍全败。24 MP + 512 KiB 实测：`u=1` 0/9，`u=2` 4/10，`u=3` 10/10。

**改动**：
- `rust/src/stego/params.rs`：新增 `MAX_GROUPED_BACKTRACK_BYTES = 512 MiB`（正确性路径的回溯位图上限，与失真启发式的 256 MiB 分开）、`max_grouped_backtrack_slots(h)`、纯函数 `grouped_body_budget(body_grid, bits, h, auto_budget)`——自动预算已买到 `u>=3` 时原样返回，否则抬到 `3*window`；**`u=2` 不做回退**（该负载区间实测仍是硬币），放不下返回 `None`。
- `rust/src/stego/jpeg/engine.rs`：
  - `embed_once`：`table.is_some() && layout.u < 2` 时应用分组下限；连 `u=3` 都放不下时**立即**返回可操作的诊断（不再跑完数秒再输掉掷币）；
  - `probe_capacity_with_format`：表过优化时最大原始载荷改报分组码上限（24 MP：2,953,009 B → 699,028 B），`StegoCapacityInfo` 新增 `max_raw_is_grouped`，CLI 两处输出附说明行；
  - `layout_for_payload` 同步应用同一规则，诊断与实嵌一致；
  - `EMBED_ATTEMPTS` 3 → 6（u=3 也有残余跨零链风险，如 100 MP 载体 1M@u=3 仍偶发）。
- 新增测试：`stego::params::tests::grouped_body_budget_*`（5 个，钉住 24 MP+512K⇒u=3、700K/1M/h=10⇒拒绝、小载体抬升、已分组不改动）；`v3_over_optimised_table_keeps_a_grouped_body`（显式小预算强制 u=1 ⇒ 抬升后往返成功）、`v3_over_optimised_table_refuses_when_no_group_fits`（连 u=3 都放不下 ⇒ 立即拒绝）；`batch_stego` 的 oversize 断言改为接受两种拒绝模式（几何容量 / 分组上限），22/22 通过。

**效果**（img24mp.jpg）：512 KiB 修复前 0/6 → 修复后 **4/4 成功且往返逐字节一致**（自动选 u=3，约 7 s，回溯位图约 403 MiB）；700K 起确定性即时拒绝；`--capacity` 报 699,028 B 并注明「Huffman 表过优化，u=1 不可用」。完整表载体行为完全不变（分组下限只在 `table.is_some()` 时生效；MVIMG.jpg 512K 3/3 + 往返验证通过）。

### [2026-10-23 08:51:57] 策略：STC 组宽改为按载体比例自动伸缩，高分辨率大载荷不再回落到 u=1

**问题**：25 MP 载体嵌入 200 KB 载荷时 `u = 1`。`u = 1` 不是「编码器」——两条分支条件互补（列向量最低位恒为 1）、解唯一，**代价图无法改变任何一个翻转位置**（实测翻转集合差异为 0，仅 ±1 方向随代价变化），等价于关闭内容自适应：`distortion/bit = 0.7277`，是 `u = 3`（0.0251）的 **29 倍**。

**根因**：上限设在「槽位数」维度上。`effective_slot_budget` 用 `MAX_DEFAULT_SLOT_BUDGET = 2_400_000` 封顶，而 `u = 槽位预算 / (bits + h - 1)`，于是**窗口越大（载荷越大）u 越小**，与「大图余量更多、应该用更大 u」的意图完全相反。

**改动**（`rust/src/stego/params.rs`）：
- 删除 `MAX_DEFAULT_SLOT_BUDGET`，新增 `MAX_AUTO_BACKTRACK_BYTES = 256 MiB`（约束回溯位图，而不是槽位数）。
- `effective_slot_budget` 改为 `max(1_200_000, min(body_slots / 4, MAX_AUTO_BACKTRACK_BYTES / bytes_per_slot(h)))`，即 **`u ≈ ratio / 4`**（`ratio = body_slots / (bits + h - 1)`）：组宽跟随载体的余量比例自动伸缩。
  - 下限沿用 1.2M 槽，小载体行为不变（网格 ≤ 9.6M 的载体计算结果与之前完全一致）；
  - 上限换成内存：`h = 8` 时约 8.4M 槽；「每槽字节数」与「每槽状态数」同阶，因此最坏内核耗时约 1 s **且与 `h` 无关**。
- 同步更新 `--slot-budget` 的 CLI 帮助与中英文案；新增回归测试 `stego::params::tests::large_carrier_with_large_payload_keeps_a_grouped_trellis`（断言 24 MP + 200 KB ⇒ `u = 3`，并验证接近满载的载荷仍能优雅降级）。

**效果**（5933×4209，24.68M 网格，200 KB 载荷）：

| 配置 | 旧内核 | 新内核 |
|---|---:|---:|
| `u=1`（旧默认） | 1.97 s | 1.75 s |
| `u=2` | 3.33 s | 2.56 s |
| **`u=3`（新默认）** | 5.40 s | **3.1~3.5 s** |

- 质量：`flips/bit` 0.5001 → **0.3735**，`distortion/bit` 0.7277 → **0.0251**（29×）；
- 64 KB 载荷（同一载体）：`u` 由 4 升到 12，`distortion/bit` 0.0170 → ~0.008；
- 端到端时间从 1.97 s 升到 3.1~3.5 s，这是换取 29× 抗检指标提升的代价；需要速度时仍可用 `--slot-budget` 显式压低。

**边界与已知代价**：
- 载荷大到 `窗口 > body_slots/4`（该载体上约 >770 KB）时仍会回落 `u = 1`：分组码所需槽位会突破内存上限，这是纯容量场景，与本次策略无关。
- Huffman 表过优化的载体：分组码铺得更开，会触及更多 `(run, category)` 符号。批测中 `DSC_20260403_161503_1794.jpg` 的高载荷场景从「可嵌入」变为「按既有文档化限制跳过」（该载体即使 200 KB 载荷也会因缺失 `0xF2` 符号而失败）。`batch_stego` 仍 19/19 通过，跳过数 4 → 5。

**验证**：`cargo test --release --all-targets` 全绿（162 单元测试）；`batch_stego` 19/19 通过；`cargo fmt --check` 与 `cargo clippy --all-targets` 0 警告；25 MP 载体嵌入 200 KB 后提取 200000 字节，`cmp` 与原始载荷逐字节一致。
