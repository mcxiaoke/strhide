# 变更记录 - 2026-10-23

### [2026-10-23 08:51:57] 策略：STC 组宽改为按载体比例自动伸缩，高分辨率大载荷不再回落到 u=1

**问题**：25 MP 载体嵌入 200 KB 载荷时 `u = 1`。`u = 1` 不是「编码器」——两条分支条件互补（列向量最低位恒为 1）、解唯一，**代价图无法改变任何一个翻转位置**（实测翻转集合差异为 0，仅 ±1 方向随代价变化），等价于关闭内容自适应：`distortion/bit = 0.7277`，是 `u = 3`（0.0251）的 **29 倍**。

**根因**：上限设在「槽位数」维度上。`effective_slot_budget` 用 `MAX_DEFAULT_SLOT_BUDGET = 2_400_000` 封顶，而 `u = 槽位预算 / (bits + h - 1)`，于是**窗口越大（载荷越大）u 越小**，与「大图余量更多、应该用更大 u」的意图完全相反。

**改动**（`rust/src/stego/params.rs`）：
- 删除 `MAX_DEFAULT_SLOT_BUDGET`，新增 `MAX_AUTO_BACKTRACK_BYTES = 256 MiB`（约束回溯位图，而不是槽位数）。
- `effective_slot_budget` 改为 `max(1_200_000, min(body_slots / 4, MAX_AUTO_BACKTRACK_BYTES / bytes_per_slot(h)))`，即 **`u ≈ ratio / 4`**（`ratio = body_slots / (bits + h - 1)`）：组宽跟随载体的余量比例自动伸缩。
  - 下限沿用 1.2M 槽，小载体行为不变（网格 ≤ 9.6M 的载体计算结果与之前完全一致）；
  - 上限换成内存：`h = 8` 时约 8.4M 槽；「每槽字节数」与「每槽状态数」同阶，因此最坏内核耗时约 1 s **且与 `h` 无关**。
- 同步更新 `--slot-budget` 的 CLI 帮助与中英文案；新增回归测试 `stego::params::tests::large_carrier_with_large_payload_keeps_a_grouped_trellis`（断言 24 MP + 200 KB ⇒ `u = 3`，并验证接近满载的载荷仍能优雅降级）。

**效果**（5933×4209，24.68M 网格，200 KB 载荷）：

| 配置 | 旧内核 | 新内核 |
|---|---:|---:|
| `u=1`（旧默认） | 1.97 s | 1.75 s |
| `u=2` | 3.33 s | 2.56 s |
| **`u=3`（新默认）** | 5.40 s | **3.1~3.5 s** |

- 质量：`flips/bit` 0.5001 → **0.3735**，`distortion/bit` 0.7277 → **0.0251**（29×）；
- 64 KB 载荷（同一载体）：`u` 由 4 升到 12，`distortion/bit` 0.0170 → ~0.008；
- 端到端时间从 1.97 s 升到 3.1~3.5 s，这是换取 29× 抗检指标提升的代价；需要速度时仍可用 `--slot-budget` 显式压低。

**边界与已知代价**：
- 载荷大到 `窗口 > body_slots/4`（该载体上约 >770 KB）时仍会回落 `u = 1`：分组码所需槽位会突破内存上限，这是纯容量场景，与本次策略无关。
- Huffman 表过优化的载体：分组码铺得更开，会触及更多 `(run, category)` 符号。批测中 `DSC_20260403_161503_1794.jpg` 的高载荷场景从「可嵌入」变为「按既有文档化限制跳过」（该载体即使 200 KB 载荷也会因缺失 `0xF2` 符号而失败）。`batch_stego` 仍 19/19 通过，跳过数 4 → 5。

**验证**：`cargo test --release --all-targets` 全绿（162 单元测试）；`batch_stego` 19/19 通过；`cargo fmt --check` 与 `cargo clippy --all-targets` 0 警告；25 MP 载体嵌入 200 KB 后提取 200000 字节，`cmp` 与原始载荷逐字节一致。
